## 1. 设计原则

| # | 原则 | 依据 |
| --- | --- | --- |
| S1 | 状态变更必须由**明确事件**触发，并**写入 Review Record** | 第 8 条 |
| S2 | **AI 可建议状态、可完成 AI 阶段流转，但无权执行最终批准、法务签名、风险关闭** | 第 1、8 条 |
| S3 | 前端按钮、后端接口、数据库权限**遵守同一套授权规则**，不能只在界面隐藏按钮 | 第 8 条 |
| S4 | 品牌/市场/设计/业务**不能代替法务**关闭风险或批准上线版本 | 第 2 条 |
| S5 | 关键状态变更记录**操作者、时间、原状态、新状态、原因、关联版本** | 第 8 条 |
| S6 | 状态名可调整，但**不得省略**"待人工判断、整改中、已重新提交、AI 复审、法务终审、已关闭、误判留痕"语义 | 第 8 条 |
| S7 | 高风险动作需**二次确认并展示影响范围** | 第 13 条 |

**命名约定**：本文全部使用大写蛇形枚举，与 `01` 文档的 `CHECK` 约束、触发器、`risk_status_transition` 表**逐字一致**。

## 2. 审核任务 Case 状态机

### 2.1 状态定义

| 状态 | 含义 | 进入条件 |
| --- | --- | --- |
| `DRAFT` | 草稿：已建任务，材料未齐或未确认审核要求 | 创建 Case |
| `PARSING` | 解析中：至少一个物料在解析 | 上传物料后自动进入 |
| `READY_FOR_REVIEW` | 待启动初审：材料解析完成、审核要求已确认 | 全部物料解析结束（含失败）且要求已确认 |
| `AI_REVIEWING` | AI 初审中 | 用户点击「开始 AI 初审」 |
| `FEEDBACK_PENDING` | 反馈区待法务判断：AI 初审完成，存在待人工处理项 | AI 初审完成 |
| `REMEDIATION` | 整改中：已有风险确认需修改并进入终审区 | 至少一个 Risk Case 进入 `AWAITING_REVISION` |
| `FINAL_REVIEW` | 终审中：所有阻断性风险均已复审通过，待法务终审签名 | 所有阻断性风险处于 `LEGAL_FINAL_REVIEW` |
| `APPROVED` | 已批准：存在已批准物料版本 | 法务完成签名与物料批准 |
| `REJECTED` | 已驳回：本批不予通过 | 法务驳回 |
| `ARCHIVED` | 已归档 | 用户归档 |

### 2.2 状态流转图

```
                    ┌──────────┐
                    │  DRAFT   │
                    └────┬─────┘
              上传物料    │
                         ▼
                    ┌──────────┐   解析失败需补料
                    │ PARSING  │──────────────┐
                    └────┬─────┘              │
       全部解析结束+要求确认│                    │
                         ▼                   │
              ┌──────────────────────┐       │
              │  READY_FOR_REVIEW    │◄──────┘
              └──────────┬───────────┘
        点击「开始 AI 初审」│
                         ▼
                 ┌───────────────┐
                 │ AI_REVIEWING  │   ← AI 在此阶段可自行流转
                 └───────┬───────┘
                         ▼
              ┌──────────────────────┐
              │  FEEDBACK_PENDING    │   ← 反馈区：法务逐条判断
              └──────────┬───────────┘
      存在确认需整改的风险 │
                         ▼
                 ┌───────────────┐
                 │  REMEDIATION  │   ← 终审区：上传新版本、Diff、AI 复审
                 └───────┬───────┘
    阻断性风险全部复审通过 │
                         ▼
                 ┌───────────────┐
                 │ FINAL_REVIEW  │   ← 法务终审 + 签名
                 └───┬───────┬───┘
            签名批准  │       │ 驳回
                     ▼       ▼
              ┌──────────┐ ┌──────────┐
              │ APPROVED │ │ REJECTED │
              └────┬─────┘ └────┬─────┘
                   └─────┬──────┘
                         ▼
                   ┌──────────┐
                   │ ARCHIVED │
                   └──────────┘
```

> **AI 的权限边界在图上很清楚**：`AI_REVIEWING → FEEDBACK_PENDING` 是 AI 可自行完成的流转；`FINAL_REVIEW → APPROVED` 必须由法务触发。

### 2.3 状态跃迁表

| From | To | 触发事件 | 允许主体 | 守卫条件 |
| --- | --- | --- | --- | --- |
| `DRAFT` | `PARSING` | `MATERIAL_UPLOADED` | 提交人/法务 | 至少 1 个物料 |
| `DRAFT` | `ARCHIVED` | `CASE_ARCHIVED` | 法务/管理员 | 无物料 |
| `PARSING` | `READY_FOR_REVIEW` | `PARSE_ALL_FINISHED` | 系统 | 全部物料解析结束（成功或失败）且 `requirement_confirmed_at` 非空 |
| `READY_FOR_REVIEW` | `PARSING` | `MATERIAL_UPLOADED` | 提交人/法务 | 新增物料后重新解析 |
| `READY_FOR_REVIEW` | `AI_REVIEWING` | `START_INITIAL_REVIEW` | 法务 | ≥1 个物料 `parse_status='SUCCEEDED'`；审核要求已确认 |
| `AI_REVIEWING` | `FEEDBACK_PENDING` | `AI_REVIEW_COMPLETED` | AI/系统 | 全部可审物料已产出结论；Risk Case 已生成 |
| `AI_REVIEWING` | `READY_FOR_REVIEW` | `AI_REVIEW_FAILED` | AI/系统 | 全部失败且不可重试 |
| `FEEDBACK_PENDING` | `REMEDIATION` | `RISK_TO_REMEDIATION` | 法务 | ≥1 个 Risk Case 进入 `AWAITING_REVISION` |
| `FEEDBACK_PENDING` | `FINAL_REVIEW` | `ALL_RISKS_RESOLVED` | 法务 | 无阻断性风险、无待人工项 |
| `REMEDIATION` | `FINAL_REVIEW` | `ALL_RISKS_REREVIEW_PASSED` | 法务/系统 | 所有阻断性风险处于 `LEGAL_FINAL_REVIEW` |
| `REMEDIATION` | `FEEDBACK_PENDING` | `NEW_RISK_FOUND` | 法务 | 复审发现新增风险需回反馈区判断 |
| `FINAL_REVIEW` | `APPROVED` | `MATERIAL_APPROVED` | **法务（需签名权限）** | 物料所有阻断性风险 `CLOSED`；签名记录已生成 |
| `FINAL_REVIEW` | `REJECTED` | `CASE_REJECTED` | **法务** | 二次确认 |
| `APPROVED` | `FINAL_REVIEW` | `APPROVAL_REVOKED` | **法务** | 二次确认；记录撤销原因（`AGENTS.md` 第 13 条高风险动作） |
| `REJECTED` | `REMEDIATION` | `RESUME_REMEDIATION` | 法务 | — |
| `APPROVED`/`REJECTED` | `ARCHIVED` | `CASE_ARCHIVED` | 法务/管理员 | — |

## 3. Risk Case 状态机

### 3.1 状态定义

| 状态 | 含义 | 语义要求（第 8 条不得省略） |
| --- | --- | --- |
| `OPEN` | 新建：AI 识别出且置信度高、依据充分 | — |
| `PENDING_LEGAL_DECISION` | **待人工判断**：证据不足/事实无法核实/解释有空间/规则冲突/低置信度高影响 | ✅ 强制保留 |
| `CONFIRMED` | 法务确认存在风险 | — |
| `AWAITING_EVIDENCE` | 要求补充证明材料 | — |
| `AWAITING_REVISION` | **整改中**：已转入终审区等待新版本 | ✅ 强制保留 |
| `RESUBMITTED` | **已重新提交**：新版本已上传 | ✅ 强制保留 |
| `AI_REREVIEW` | **AI 复审中** | ✅ 强制保留 |
| `LEGAL_FINAL_REVIEW` | **法务终审** | ✅ 强制保留 |
| `CLOSED` | **已关闭**：已解决并签名 | ✅ 强制保留 |
| `REJECTED_FALSE_POSITIVE` | **误判**：记录保留，理由必填 | ✅ 强制保留（误判留痕） |

### 3.2 状态流转图

```
                          ┌────────┐
                          │  OPEN  │
                          └───┬────┘
          ┌───────────────────┼───────────────────┐
          │                   │                   │
   法务确认风险          低置信度/依据不足      法务判误判
          │                   │                   │
          ▼                   ▼                   ▼
   ┌────────────┐  ┌──────────────────────┐  ┌────────────────────────┐
   │ CONFIRMED  │  │ PENDING_LEGAL_       │  │ REJECTED_FALSE_        │
   └─────┬──────┘  │ DECISION（待人工）    │  │ POSITIVE（误判留痕）    │
         │         └──────────┬───────────┘  └────────────────────────┘
         │             法务处理后│                    ▲
         │         ┌──────────┼──────────┐           │
         │         ▼          ▼          ▼           │
         │   ┌──────────┐ ┌────────┐ ┌───────────────┘
         │   │CONFIRMED │ │AWAITING│ │
         │   └──────────┘ │EVIDENCE│ │
         │                └───┬────┘ │
         │                    │      │
         ├────────────────────┤      │
         │  转入整改           │      │
         ▼                    ▼      │
   ┌──────────────────────────────────┴──┐
   │        AWAITING_REVISION（整改中）    │
   └───────────────┬──────────────────────┘
        新版本上传  │
                   ▼
            ┌─────────────┐
            │ RESUBMITTED │（已重新提交）
            └──────┬──────┘
                   ▼
            ┌─────────────┐
            │ AI_REREVIEW │（AI 复审三问）
            └──────┬──────┘
        复审通过   │   仍有剩余风险
                   │        └──────────► 回 AWAITING_REVISION
                   ▼
        ┌────────────────────┐
        │ LEGAL_FINAL_REVIEW │（法务终审）
        └─────────┬──────────┘
      法务确认+签名│
                  ▼
             ┌─────────┐
             │ CLOSED  │（已关闭）
             └─────────┘
```

> **新增风险的走向（第 7 条）**：若复审发现"原风险已解决但产生新增风险"，**必须新建关联 Risk Case**（`risk_case` 新增行，`parent_risk_id` 自引用外键关联原风险），**不得悄悄改变原风险的含义**。
>
> **配套的数据保障**（见 `01` §4.6）：① `risk_case.parent_risk_id` + `fk_risk_parent` 建立可追溯的父子关系；② 任何对 `risk_text` / `risk_level` / `confidence` / `suggestion` / `recommended_copy` / `required_evidence` 的修改，都会由 `trg_risk_case_revision_snapshot` 触发器把**旧值快照**写入 `risk_case_revision`（append-only）。因此"悄悄改写原风险"在**数据层面不可能发生**——旧值一定留痕，且由数据库而非应用层纪律保证。

### 3.3 状态跃迁表

| From | To | 触发事件 | 允许主体 | 守卫条件 |
| --- | --- | --- | --- | --- |
| `OPEN` | `PENDING_LEGAL_DECISION` | `LOW_CONFIDENCE_OR_MISSING_BASIS` | AI/系统 | `confidence < 阈值` 或 `unsupported_claims` 非空 或 `rule_refs` 为空 |
| `OPEN` | `CONFIRMED` | `LEGAL_CONFIRM` | **法务** | 权限 `risk.confirm` |
| `OPEN` | `REJECTED_FALSE_POSITIVE` | `LEGAL_FALSE_POSITIVE` | **法务** | **`opinion` 必填**（DB 约束 `ck_rr_false_positive_opinion`） |
| `OPEN` | `AWAITING_EVIDENCE` | `REQUEST_EVIDENCE` | 法务 | — |
| `PENDING_LEGAL_DECISION` | `CONFIRMED` | `LEGAL_CONFIRM` | **法务** | 权限 `risk.confirm` |
| `PENDING_LEGAL_DECISION` | `REJECTED_FALSE_POSITIVE` | `LEGAL_FALSE_POSITIVE` | **法务** | `opinion` 必填 |
| `PENDING_LEGAL_DECISION` | `AWAITING_EVIDENCE` | `REQUEST_EVIDENCE` | 法务 | — |
| `CONFIRMED` | `AWAITING_REVISION` | `RISK_TO_REMEDIATION` | 法务 | 权限 `risk.to_remediation`；上传人或责任方已指定 |
| `AWAITING_EVIDENCE` | `CONFIRMED` | `EVIDENCE_PROVIDED` | 法务 | 补充材料已审核通过 |
| `AWAITING_EVIDENCE` | `AWAITING_REVISION` | `EVIDENCE_INSUFFICIENT` | 法务 | 材料不足需改文案 |
| `AWAITING_REVISION` | `RESUBMITTED` | `NEW_VERSION_UPLOADED` | 品牌/设计/业务/法务 | 新版本已上传且解析成功；`current_version_id` 已更新 |
| `RESUBMITTED` | `AI_REREVIEW` | `START_REREVIEW` | 系统/AI | **必须携带 `review_scope` 且 ≠ `FULL`** |
| `AI_REREVIEW` | `LEGAL_FINAL_REVIEW` | `REREVIEW_COMPLETED` | AI/系统 | 复审三问结论已产出 |
| `AI_REREVIEW` | `AWAITING_REVISION` | `REREVIEW_NOT_RESOLVED` | AI/系统 | 原风险未解决或仍有剩余风险 |
| `LEGAL_FINAL_REVIEW` | `CLOSED` | `LEGAL_CLOSE_WITH_SIGNATURE` | **法务** | **必须存在 `legal_signature`(RISK_CLOSE)**（DB 触发器强制） |
| `LEGAL_FINAL_REVIEW` | `AWAITING_REVISION` | `LEGAL_REJECT_REREVIEW` | 法务 | 法务不认可 AI 复审结论 |

**绝对禁止的跃迁**（由 `01` 文档的 `risk_status_transition` 白名单 + 触发器保证）：

- 任何状态 → `CLOSED`，除 `LEGAL_FINAL_REVIEW → CLOSED`；
- `OPEN` / `PENDING_LEGAL_DECISION` 直接 → `CLOSED`（**待人工判断的风险只有经法务处理后才能继续流转**，第 5 条）；
- 任何从 `REJECTED_FALSE_POSITIVE` 出发的跃迁（误判是终态，只留痕不改写）。

## 4. 角色与权限点

### 4.1 角色定义

| 角色 | 代码 | 职责 | **明确不具备** |
| --- | --- | --- | --- |
| 法务 | `LEGAL` | 设置审核关注点、确认风险、处理争议、提正式修改意见、终审、签名 | — |
| 品牌 | `BRAND` | 提交物料、查看与自己有关的整改意见、上传修改版本 | **不能关闭风险、不能批准上线版本** |
| 设计 | `DESIGN` | 同上 | 同上 |
| 业务 | `BIZ` | 同上 | 同上 |
| 管理员 | `ADMIN` | 维护权限、知识库来源、企业规则、产品参数、审计配置 | **不应具备业务审批权**（职责分离） |

> **管理员不得拥有 `risk.close` / `material.approve`**。这是职责分离要求：系统管理员不应能替代法务完成法律批准。若企业规模小、同一人兼任，则**必须使用两个独立账号**并在审计中区分，而不是给 `ADMIN` 叠加法务权限。

## 5. 三处一致的落地实现

`AGENTS.md` 第 8 条：**"前端按钮、后端接口和数据库权限都必须遵守同一套授权规则，不能只在界面上隐藏按钮。"**

三层各自的定位必须说清楚——**只有中间层是安全边界**：

| 层 | 作用 | **是不是安全边界** |
| --- | --- | --- |
| 前端 | 体验：不显示无权操作的按钮 | ❌ **不是**。可被绕过，仅提升可用性 |
| 后端 | **安全边界的唯一实现**：接口鉴权 + 领域守卫 | ✅ **是** |
| 数据库 | 兜底：阻止绕过应用层直接改库、阻止非法状态 | ✅ 是（第二道） |

### 5.1 前端：权限指令与路由守卫

```ts
// src/directives/permission.ts
// 用法：<el-button v-perm="'risk.close'">关闭风险</el-button>
export const permission: Directive<HTMLElement, string> = {
  mounted(el, binding) {
    const perms = useUserStore().permissions;      // 登录时由后端下发
    if (!perms.includes(binding.value)) el.remove(); // 直接移除，不留占位
  },
};

// src/router/guard.ts —— 路由级
router.beforeEach((to) => {
  const required = to.meta?.perm as string | undefined;
  if (required && !useUserStore().permissions.includes(required)) {
    return { name: 'forbidden' };
  }
});
```

> ⚠️ **前端权限列表必须由后端下发**（`/api/me/permissions`），**不得在前端硬编码角色到权限的映射**。否则后端调整权限时前端不同步，会出现"按钮能点但接口 403"或更糟的"按钮藏了其实有权限"。

### 5.2 后端：双层校验（接口层 + 领域层）

**只做接口层注解是不够的**——内部调用（定时任务、回调、AI 编排链路）会绕过 Controller，直接进 Service。因此领域层必须有守卫。

```java
// 路径前缀按四模块划分，与 04 §2.0 对齐：
//   /api/assistant | /api/intake | /api/feedback | /api/final-review
@RestController
@RequestMapping("/api/final-review/risks")
public class RiskController {

    @PostMapping("/{riskId}/close")
    @PreAuthorize("@perm.has('risk.close')")          // 接口层
    public Result<Void> close(@PathVariable Long riskId,
                              @RequestBody @Valid CloseRiskRequest req) {
        riskAppService.closeRisk(riskId, req);         // 交给应用层
        return Result.ok();
    }
}

// ── 第 2 层：领域守卫（gw-domain，不依赖 Spring Security，内部调用同样生效）
public class RiskCase {

    private RiskStatus status;
    private boolean hasLegalCloseSignature;

    /** 关闭风险：唯一合法路径 */
    public void close(Actor actor, String opinion) {
        // 守卫 1：只有法务可以关闭
        if (actor.type() != ActorType.HUMAN || !actor.hasPermission(Perm.Codes.RISK_CLOSE)) {
            throw new DomainException(ErrorCode.AI_CANNOT_CLOSE_RISK,
                "AI 与非法务角色无权关闭风险");
        }
        // 守卫 2：必须来自法务终审状态（AGENTS.md 第 7 条）
        if (this.status != RiskStatus.LEGAL_FINAL_REVIEW) {
            throw new DomainException(ErrorCode.ILLEGAL_TRANSITION,
                "仅法务终审中的风险可以关闭，当前状态：" + this.status);
        }
        // 守卫 3：必须有签名
        if (!this.hasLegalCloseSignature) {
            throw new DomainException(ErrorCode.SIGNATURE_REQUIRED, "关闭风险必须先完成法务签名");
        }
        this.status = RiskStatus.CLOSED;
    }
}
```

```java
// ── 状态跃迁集中管理，禁止在 Service 里散写 setStatus
@Component
public class RiskStateMachine {

    private final Map<RiskStatus, Set<RiskStatus>> allowed;   // 由 risk_status_transition 表加载

    public void transit(RiskCase risk, RiskStatus target, Actor actor, String reason) {
        if (!allowed.getOrDefault(risk.getStatus(), Set.of()).contains(target)) {
            throw new DomainException(ErrorCode.ILLEGAL_TRANSITION,
                risk.getStatus() + " → " + target + " 不是合法跃迁");
        }
        // 所有状态变更必须留痕（S1）
        reviewRecordRepo.append(ReviewRecord.statusChange(risk, actor, reason, risk.getStatus(), target));
        risk.setStatus(target);
    }
}
```

**代码评审强制检查项**：
- 禁止在任何地方直接调用 `riskCase.setStatus(...)`，必须走 `RiskStateMachine.transit(...)`；
- 用 ArchUnit 测试断言"`gw-domain` 不依赖 Spring"且"没有类直接调用 `setStatus`"。

### 5.3 数据库：兜底（见 `01` 文档 §7）

三道触发器把安全性下沉到存储层，杜绝"绕过应用直接改库"：

1. `trg_risk_case_close_requires_signature`：进 `CLOSED` 必须存在 `legal_signature`；
2. `trg_signature_requires_privilege`：签名人必须持 `LEGAL` 角色；
3. `trg_risk_case_transition_guard`：跃迁必须命中白名单，且 `CLOSED` 只能来自 `LEGAL_FINAL_REVIEW`。

> **一致性保障**：写一个集成测试，从 `risk_status_transition` 表读出全部跃迁，与 `RiskStateMachine` 加载的集合、以及本文档 §3.3 表格做三方比对。任一不一致即测试失败。这样"三处一致"就从口头承诺变成**可执行的断言**。

## 6. 高风险动作的二次确认

`AGENTS.md` 第 13 条：高风险动作需**二次确认并展示影响范围**。

| 动作 | 二次确认文案要求 | 必须展示的影响范围 |
| --- | --- | --- |
| **标记最终批准版本** | 明确"这将作为对外发布的最终版本" | 批准针对的**版本号与文件哈希**、已关闭风险数、仍未关闭的非阻断风险数 |
| **关闭风险** | 明确"关闭后该风险视为已解决并留痕" | 原风险、新版本内容、AI 复审结论、签名人 |
| **驳回** | 明确"驳回后任务退回整改" | 将被退回的风险数、涉及的物料数 |
| **撤销批准** | 明确"撤销后该物料回到未批准状态" | 受影响的物料与版本、已下线的对外版本提示 |
| **标记误判** | 明确"误判记录将保留并用于模型优化" | **必填误判理由**（DB 约束强制） |

**技术实现**：前端 `ElMessageBox.confirm` 弹出确认框并展示影响范围数据（由后端 `GET /api/.../impact` 预取），**后端必须独立校验前置条件**，不能因为前端确认过就跳过检查。二次确认是体验措施，不是安全措施。

**"通过"文案规范（第 13 条）**：禁止只显示含义模糊的"已通过"，必须写明是：
- `AI 初审通过`（蓝灰色系，且必须附注"不等于法务最终批准"）
- `AI 复审通过`（蓝灰色系）
- `法务最终批准`（绿色系，唯一可表示可对外发布）

**视觉编码分离**：风险等级（HIGH/MEDIUM/LOW）与流程状态使用**两套不同的视觉编码**——例如风险等级用**色块/标签底色**（红/橙/灰），流程状态用**描边标签**（不同边框色），避免用户把"高风险"误读成"流程卡住了"。

## 7. 并发控制

| 场景 | 方案 |
| --- | --- |
| 同一 Risk Case 被两人同时确认 | `risk_case.lock_version` 乐观锁；更新时 `WHERE id=? AND lock_version=?`，影响行数为 0 则返回 409 并提示刷新 |
| 同一 Case 同时上传新版本 | `uk_version_material_no` 唯一键；冲突则自动取下一版本号重试（最多 3 次） |
| AI 复审与人工操作竞争 | 状态前置条件校验：若状态已不是 `RESUBMITTED`，复审任务直接放弃并记录 |
| 重复触发 AI 初审 | `parse_job.idempotency_key` / `async_task.idempotency_key` 唯一键拦截 |
| ASR 回调重复投递 | `uk_async_external`（`task_type + external_task_id`）唯一键拦截 |
| 同一文件重复上传 | `uk_version_sha`（`material_id + file_sha256`）复用已有版本，不新建 |

**测试要求**（`AGENTS.md` 第 15 条明确列出"并发修改"）：必须有多线程并发测试，验证乐观锁与唯一键在真实竞争下正确生效，而不是只测单线程路径。

## 8. Review Record 的写入时机（S1/S5 落地）

**每一次状态变更都必须在同一事务内写入 `review_record`**，记录：操作者（AI 还是人工）、时间、原状态、新状态、原因、关联版本。

```java
@Transactional
public void confirmRisk(Long riskId, String opinion) {
    RiskCase risk = repo.getForUpdate(riskId);
    Actor actor = Actor.current();

    riskStateMachine.transit(risk, RiskStatus.CONFIRMED, actor, opinion);  // 内部已写 record
    riskRepo.save(risk);
}
```

**必须落 Review Record 的动作清单**：

| action | 主体 | 关键 payload |
| --- | --- | --- |
| `AI_INITIAL_REVIEW` | AI | 模型、pipeline/prompt/ruleset 版本、token 用量 |
| `LEGAL_CONFIRM` | HUMAN | 意见、确认的锚点 |
| `LEGAL_FALSE_POSITIVE` | HUMAN | **误判理由（必填）** |
| `REQUEST_EVIDENCE` | HUMAN | 所需材料清单 |
| `TO_REMEDIATION` | HUMAN | 责任方、期望完成时间 |
| `UPLOAD_VERSION` | HUMAN | 版本号、哈希、修改说明 |
| `AI_REREVIEW` | AI | **复审三问结论 + `review_scope`（证明未做全量初审）** |
| `LEGAL_FINAL_REVIEW` | HUMAN | 终审意见 |
| `SIGN` | HUMAN | 签名哈希、签名时文件哈希 |
| `CLOSE` | HUMAN | 关闭原因 |
| `APPROVE_MATERIAL` | HUMAN | 版本号 + 文件哈希 |
| `REVOKE_APPROVAL` | HUMAN | 撤销原因 |

**AI 复审的 `review_scope` 必须持久化**（`AGENTS.md` 第 7 条要求"不得把终审区重新做成一次无差别的全量初审"）。`review_scope` 取值：

- `CHANGED_REGION_ONLY`：仅变化区域
- `CHANGED_REGION_WITH_CONTEXT`：变化区域 + 必要上下文（**默认**）
- `FULL`：全量（**服务端拒绝**，用于证明系统不会退化为重复初审）

服务端在 `RISK_REREVIEW` 入口强制校验 `scope != FULL`，否则返回 400。这样"没做全量初审"这件事有据可查，而不是靠承诺。

## 9. AI 状态建议与人工决策的边界（S2 落地）

AI 在流水线中可以：
- ✅ 产出 `recommended_status`（建议状态）
- ✅ 触发 `OPEN → PENDING_LEGAL_DECISION`（低置信度/缺依据时自动转人工）
- ✅ 触发 `RESUBMITTED → AI_REREVIEW → LEGAL_FINAL_REVIEW / AWAITING_REVISION`
- ✅ 触发 `AI_REVIEWING → FEEDBACK_PENDING`

AI 绝对不可以：
- ❌ `CONFIRMED`（确认风险是法务判断）
- ❌ `REJECTED_FALSE_POSITIVE`（误判认定是法务判断）
- ❌ `CLOSED`（关闭需签名）
- ❌ `material.approve`（最终批准）
- ❌ 任何签名行为

**实现方式**：`Actor` 抽象上区分 `ActorType.AI` / `ActorType.HUMAN`，领域守卫检查 `actor.type()`。DB 触发器再做一层（`trg_risk_case_close_requires_signature`）。**AI 编排链路拿不到 `LEGAL` 角色的凭据**——AI 任务使用独立的服务账号，该账号不具备上述权限点，从凭据层面就做不到。

## 10. 测试要点（对应 `AGENTS.md` 第 15 条）

状态机与权限的测试必须覆盖：

| # | 用例 | 期望 |
| --- | --- | --- |
| T1 | AI 服务账号直接调 `POST /api/final-review/risks/{id}/close` | 403，且**领域层也不被执行** |
| T2 | 绕过接口，直接调 `riskAppService.closeRisk(...)` 并传 AI actor | 抛 `AI_CANNOT_CLOSE_RISK` |
| T3 | 绕过应用层，直接 SQL 把 `risk_case.status` 改为 `CLOSED` | **触发器报错**（无签名） |
| T4 | 从 `OPEN` 直接改 `CLOSED` | 触发器报错（非法跃迁） |
| T5 | `BRAND` 角色尝试 `risk.confirm` | 403 |
| T6 | `ADMIN` 角色尝试 `material.approve` | 403（职责分离） |
| T7 | `LEGAL` 标记误判但不填理由 | DB 约束拒绝 + 接口返回校验错误 |
| T8 | `LEGAL` 关闭处于 `AWAITING_REVISION` 的风险 | 领域层拒绝（必须经 `LEGAL_FINAL_REVIEW`） |
| T9 | 两人并发确认同一风险 | 一个成功，一个 409 |
| T10 | 复审请求携带 `scope=FULL` | 400 拒绝 |
| T11 | 文档跃迁集合 == `risk_status_transition` 表 == `RiskStateMachine` 集合 | 三方一致（CI 断言） |
| T12 | 尝试 `DELETE FROM review_record` | 触发器拒绝 |
| T13 | 尝试 `UPDATE material_version` | 触发器拒绝 |
| T14 | 无签名直接 `UPDATE risk_case SET status='CLOSED'` | 触发器拒绝 |

> **T3 / T4 / T12 / T13 / T14 是"数据库权限真实生效"的证明**。若不做这几个测试，"三处一致"就只是文档里的一句话。
