## 1. 设计原则

| # | 原则 | 依据 |
| --- | --- | --- |
| A1 | 流水线采用「内容解析 → 候选风险识别 → 规则与证据检索 → 风险判断 → 结构化输出」五阶段 | 第 11 条 |
| A2 | 任何高风险结论都必须关联**具体原文、位置和依据** | 第 11 条 |
| A3 | 模型无法获取关键事实/证据/规则时，输出**待人工判断或要求补充材料**，不得编造确定答案 | 第 11 条 |
| A4 | 结构化结果必须**稳定、可校验、可持久化**，字段覆盖第 11 条列举的 14 个字段 | 第 11 条 |
| A5 | 自然语言报告**只能基于已校验的结构化结果**生成，不能让报告与库中数量/状态矛盾 | 第 11 条 |
| A6 | **风险等级、置信度、审核状态是三个独立维度**，不得混用 | 第 11 条 |
| A7 | 所有 AI 输出必须经过 Schema 校验、异常处理与可重试设计；耗时任务异步化并展示真实进度 | 第 14 条 |
| A8 | 避免重复提交导致重复 Risk Case（文件哈希、任务幂等键、规则命中去重） | 第 14 条 |

## 2. Provider 抽象与能力声明

### 2.1 强制要求

**业务代码不得直接调用百炼端点。** 所有调用经过 `AiProvider` / `ParsePort`，理由：模型型号与能力差异极大（是否支持结构化输出、Batch、缓存各不相同），硬编码会导致每换一个型号就要改业务逻辑。

### 2.2 模型能力声明表

不同千问模型的能力差异很大，**必须用配置声明，不能靠假设**。这张表是编排逻辑的输入：

| model_id | 结构化输出 | Function Calling | Batch | 上下文缓存 | 输入模态 | 地域 |
| --- | --- | --- | --- | --- | --- | --- |
| `qwen3-vl-8b-thinking` | ✅ | ✅(北京) | ❌ | ❌ | Text/Image/Video | 北京 |
| `qwen-vl-ocr` | ❌ | ❌ | ✅ | ❌ | Text/Image | 北京 |
| `qwen3.5-ocr` | ❌ | ❌ | ❌ | ❌ | Image | 北京 |
| `qwen3-asr-flash-filetrans` | — | — | — | — | Audio | 北京/新加坡 |
| `text-embedding-v4` | — | — | ✅ | — | Text | 北京 |
| `qwen3-rerank` | — | — | — | — | Text | 北京 |

> 依据见 `00` 文档 §2.1–§2.3（均为官方文档核实结果）。

```java
/** 能力声明：决定编排策略 */
public record ModelCapability(
    String modelId,
    String region,
    boolean supportsJsonObject,   // response_format={"type":"json_object"}
    boolean supportsToolCall,
    boolean supportsBatch,

@Component
public class ModelRegistry {
    /** 从配置/DB 加载，禁止在业务代码里硬编码模型名 */
    public ModelCapability get(String modelId) { ... }
}
```

### 2.3 结构化输出的策略选择（关键设计）

**问题**：OCR 模型明确**不支持**结构化输出，而 OCR 是锚点的主要来源。因此不能依赖 `response_format`。

**策略：无论模型是否支持，服务端校验都是唯一可信关口。**

```
if (capability.supportsJsonObject()) {
    // 路径 A：模型级 JSON 模式 + 服务端校验
    request.responseFormat = jsonObject();
} else {
    // 路径 B：Prompt 约束 + 服务端强校验
    //   - prompt 中给出完整 JSON 结构与示例
    //   - 明确要求"只输出 JSON，不要任何解释文字"
}
// 两条路径汇合：服务端一律执行 §7 的校验流程
validateAndRepair(rawOutput);
```

`qwen-vl-ocr` / `qwen3.5-ocr` 走路径 B。路径 B 必须配套 §7.3 的容错解析。

## 3. 阶段 1：内容解析

目标：把任意格式物料转成**统一可审核的内容 + 可定位的证据锚点**。

### 3.0 进度必须从第一天就定义成"可计量单位"

`AGENTS.md` 第 14 条要求"向用户展示真实进度"。真实进度的前提是**有可计量的分母**：

| 物料类型 | 进度分母 |
| --- | --- |
| 视频 | 已处理毫秒 / 总毫秒（按音频偏移回报） |
| PDF / PPTX | 已处理页数 / 总页数 |
| 图片 | 单图（0% 或 100%，可细分 OCR / VLM 子阶段） |
| 批量 Case | 已完成物料数 / 总物料数 |

**若一开始不这样定义，后续把"假进度动画"换成"真百分比"会导致前端语义返工**——用户对"卡在 87%"的容忍度与对动画的容忍度完全不同。详见 `06` §4.5。

### 3.1 图片解析

```
原件 ─► ① 格式识别（按文件实际内容，不看扩展名）
      ─► ② 尺寸规范化 → 记录 scale_ratio
      ─► ③ 在【规范化后图片】上跑 OCR → 文字 + bbox + 置信度
      ─► ④ 同一张规范化图片送视觉模型 → 画面语义
      ─► ⑤ 合并为锚点集
```

**约束（`00` §3.3）**：③ 与 ④ 必须基于**同一张图**。OCR 在原图、VLM 看缩放图会导致坐标必然错位。落地方式：流水线先决定 `canonical_image` 与其 `scale_ratio`，之后所有步骤只认这一张。

**③ OCR 调用要点**
- 模型选择：默认 `qwen-vl-ocr`（支持 Batch，成本约半价）；质量不达标时用 `qwen3.5-ocr` 重跑
- 需要的能力：**文本定位**（`qwen-vl-ocr-2025-11-20` 起"文字定位能力全面升级、幻觉大幅降低"）
- 输出映射：OCR 返回的文字行 → `evidence_anchor`，`anchor_type='TEXT_LINE'`，`locator` 填 §6 结构，`confidence` 填模型给的置信度
- ⚠️ **待确认**：`qwen-vl-ocr` / `qwen3.5-ocr` 的**具体调用端点与参数名**尚未核实（官方模型信息页未含调用示例）。**M0 阶段必须先按官方 OCR 调用文档确认，不得凭猜测编码。** 已确认的是能力与限制（输入模态、上下文长度、Batch 支持、价格）。

**④ 视觉模型调用要点**
- 模型：`qwen3-vl-8b-thinking`（支持视觉 2D/3D 定位、空间感知）
- **prompt 中必须携带 OCR 行清单（含 `anchor_id` 与文本）**，让模型直接引用行号，而不是让它描述文字再回头匹配。这是把定位从"模糊匹配"变成"ID 查表"的关键（`00` §3.2）
- 图片 token：每图上限 1024，缩放到约 1300×1300 后计费。**不要把分辨率压得太低**——小字漏识是最高等级的漏检风险（ADR D-11）

### 3.2 视频解析

```
视频 ─► ① ffmpeg 抽音轨（16k 单声道；噪声大时先降噪）─► ASR ─► SPEECH_SENTENCE 锚点
     ─► ② 场景检测 + 关键帧抽取 ─────────────────────► KEY_FRAME 锚点
     ─► ③ 硬字幕区域 OCR（带时间戳）────────────────► SUBTITLE_LINE 锚点
     ─► ④ 关键帧送视觉模型做画面语义 ────────────────► 画面风险候选
     ─► ⑤ 三轨对齐到统一毫秒时间轴
```

**ASR 调用（已核实的接口形态）**

```http
POST /api/v1/services/audio/asr/transcription
Authorization: Bearer $DASHSCOPE_API_KEY
Content-Type: application/json
X-DashScope-Async: enable

{
  "model": "qwen3-asr-flash-filetrans",
  "input":  { "file_url": "{YOUR_AUDIO_URL}" },
  "parameters": {
    "channel_id": [0],
    "enable_words": true,          // true=字级时间戳，false(默认)=句级
    "diarization_enabled": false    // 说话人分离，仅单声道，建议 ≤2h
  }
}
```

查询：`GET /api/v1/tasks/{task_id}` → 取 `transcription_url` → 下载 JSON。

**结果映射为锚点**

```java
// transcription JSON → SPEECH_SENTENCE 锚点
for (Sentence s : transcript.getSentences()) {
    anchors.add(new Anchor(
        anchorId,                         // A-0001 递增
        "SPEECH_SENTENCE",
        new SpeechLocator(s.getBeginTime(), s.getEndTime(), s.getSentenceId(),
                          s.getSpeakerId(), s.getEmotion(), "zh"),
        s.getText(),
        /* confidence */ null,            // ASR 未提供逐句置信度
        "qwen3-asr-flash-filetrans", modelSnapshot
    ));
}
```

**⚠️ 四个必须处理的陷阱（`00` §2.2）**

| # | 陷阱 | 处理 |
| --- | --- | --- |
| 1 | `qwen3-asr-flash` 走 OpenAI 兼容接口**不返回时间戳** | **强制使用 `qwen3-asr-flash-filetrans` 异步接口**（ADR D-12）；在 `AsrClient` 里直接不提供兼容接口方法，从 API 层面杜绝误用 |
| 2 | 任务级 `end_time`（日期字符串）与音频内 `end_time`（毫秒整数）**同名不同义** | 用不同类型承载：任务完成时间 → `Instant`；音频时间戳 → `long`。**禁止都用 String 或 Object 接** |
| 3 | `transcription_url` **仅 24 小时有效** | 提交后立即下载落盘 MinIO 并存 `parse_artifact.raw_object_key`；写 `source_expires_at` 供过期告警 |
| 4 | 异步结果字段路径因模型而异 | 按模型分派：`qwen-audio-3.0-asr-flash-filetrans`/`fun-asr`/`paraformer` → `output.results[].transcription_url`；`qwen3-asr-flash-filetrans` → `output.result.transcription_url`。usage 字段 `duration` vs `seconds` 同理 |

**回调 vs 轮询**

- 优先用 EventBridge 回调（轮询查询接口默认 20 QPS，高并发易限流）
- **回调必须校验 `X-Eventbridge-Signature*` 请求头**。官方明确警示：不校验则**任意外部 IP 可伪造 `AsyncTaskFinish` 事件注入虚假识别结果**。对法务审核系统这是不可接受的注入风险
- 回调幂等：以 `data.id` / `data.task_id` 去重（`async_task.uk_async_external`）
- 回调延迟约 1–90 秒，需容忍
- 生产环境：音频上传 OSS 后用 URL 调用；**本地文件上传调用上限 100 QPS 且不可扩容**

**硬字幕与关键帧**
- 抽帧用 ffmpeg + 场景检测；关键帧数量设上限（按视频时长线性取，避免长视频产生海量帧）
- 硬字幕 OCR 复用图片 OCR 能力，`locator` 同时带 `begin_ms/end_ms` 与 `bbox`
- **"口播与字幕不一致"本身就是风险信号**，所以口播与字幕必须是**两种独立锚点类型**，可被同一条 Risk Case 同时引用

### 3.3 文档解析

```
PDF/PPTX/DOCX ─► ① 判定是否含文本层
                 ├─ 有文本层 ─► 抽取文字 + 页码/段落/句子锚点
                 └─ 扫描件   ─► 页面渲染为图 ─► OCR（行 + bbox）─► 锚点
              ─► ② 图片/图表区域单独送视觉模型做语义理解
              ─► ③ 合并锚点集
```

**混排必须双路**：PPT 一页多图 + 文字是最常见的广宣形态，只走文本层会漏掉"图片里的宣传语"。

**⚠️ 待确认**：千问是否提供**文档（PDF/Word/PPT）原生解析端点**，以及文本层抽取的坐标粒度。官方视觉模型列表显示 `qwen3-vl` 系列输入模态含 "文件"，但**具体文件类型与解析粒度需在 M0 核实**。若文本层坐标不可得，降级方案是"页面渲染为图 + OCR 定位"（对可编辑文档会损失文本精度，但定位仍可用）。

## 4. 阶段 2：候选风险识别（宽召回）

**目标：宁可多出待人工判断，不可漏。**（`AGENTS.md` 第 15 条明确"涉及高风险漏检的测试应优先于文案风格优化"）

输入：解析文本 + 锚点清单（`anchor_id` + `text`）+ 本次审核要求
输出：候选风险列表（允许含噪声，不做严格判定）

```jsonc
{
  "candidates": [
    {
      "risk_type": "ABSOLUTE_CLAIM",
      "risk_text": "行业第一",
      "evidence_anchor_ids": ["A-0012"],
      "preliminary_reason": "疑似绝对化用语",
      "needs_rule_lookup": true
    }
  ]
}
```

**关键约束**：
- 只允许引用**已存在的 `anchor_id`**。prompt 中必须给出完整锚点清单，并明确"不得引用清单外的 ID"
- 此阶段**不判定等级、不下结论**，避免与阶段 4 的目标冲突
- 模型参数：`temperature` 在此阶段可略高以提升召回（**注意：千问部分模型思考模式下采样参数行为需实测确认**）

## 5. 阶段 3：规则与证据检索（可审计）

**这是"依据从哪来"的唯一答案来源。**

### 5.1 检索流程

```
候选风险 ─► ① 构造查询（风险原文 + 风险类型 + 适用业务/产品）
         ─► ② 混合检索：dense(语义) + sparse(关键词) → 各取 topN
         ─► ③ qwen3-rerank 重排 → Top 5–10
         ─► ④ 过滤生效期与治理状态 → 现行规则 / 历史规则 分开返回
         ─► ⑤ 返回 rule_id + kb_item_version_id + 条文 + 生效期 + 来源
```

### 5.2 已核实的检索参数

| 项 | 值 |
| --- | --- |
| 向量模型 | `text-embedding-v4`，维度 **1024**（CMTEB 70.14，性能与成本平衡点） |
| 向量类型 | **`dense&sparse` 混合**（稀疏做条款号精确匹配，稠密做语义） |
| 批次限制 | 批次 ≤10 条，**单条 ≤8,192 token** |
| `text_type` | 查询用 `query`，知识入库用 `document`（**仅 DashScope SDK/API 支持，OpenAI 兼容接口不支持**） |
| 重排 | `qwen3-rerank`，最多 500 文档、单条 ≤4,000 token、单次 ≤120,000 token |
| 官方推荐流程 | Embedding 检索 50–100 候选 → Rerank 筛 Top 5–10 → 送 LLM |

**为什么必须混合检索**：法务检索有两种截然不同的意图——"《广告法》第九条第几款"是**精确关键词**需求（稀疏向量强），"绝对化用语的合规边界"是**语义**需求（稠密向量强）。纯稠密检索会漏掉条款号匹配。

**已下线的模型**：`gte-rerank-v2` 于 **2026-05-30 下线**，必须用 `qwen3-rerank`。若沿用旧示例代码会直接失败。

### 5.3 防虚构机制（硬约束）

**`rule_references` 只允许存知识库 ID，不允许存模型生成的字符串。**

```java
// 正确：模型选择"哪条依据"，而不是"写出哪条依据"
record RuleReference(long kbItemVersionId, String ruleCode, String quotedText) {}

// 服务端校验：每个 kbItemVersionId 必须来自本次检索结果集
if (!retrievedIds.contains(ref.kbItemVersionId())) {
    // 模型引用了未检索到的依据 → 不是"依据"，而是幻觉
    moveToUnsupportedClaims(ref);
}
```

**模型想引用但检索不到依据时**，只能写入 `unsupported_claims`，服务端据此**强制将该风险转 `PENDING_LEGAL_DECISION`**（`AGENTS.md` 第 11 条：模型无法获取适用规则时应输出待人工判断，而不是编造）。

### 5.4 检索结果的分层返回

必须区分并**在界面分别展示**（`AGENTS.md` 第 10 条）：

| 类别 | 处理 |
| --- | --- |
| **现行规则** | 可作为依据 |
| 历史规则（已失效） | 仅提示，**不得作为依据** |
| 企业内部规则 | 可作为依据，但需标注适用范围 |
| 历史案例 | **不得直接视为当前场景必然通过**；必须同时校验车型、时间、渠道、数据来源、统计口径、必需免责声明 |
| `APPROVED_CLAIM` | **必须检查适用条件是否匹配**（`applicable_product` / `effective_date` / 渠道 / 数据来源），条件不符即不可引用 |

## 6. 阶段 4：风险判断

输入：候选风险 + 检索到的依据 + 产品真实参数 + 审核要求
输出：风险等级、置信度、推荐状态、理由、建议、推荐表达、所需材料

### 6.1 三个维度的严格区分（A6）

| 维度 | 含义 | 取值 |
| --- | --- | --- |
| `risk_level` | **潜在影响**有多大 | `HIGH` / `MEDIUM` / `LOW` |
| `confidence` | **AI 对识别结果的把握** | `0.0` – `1.0` |
| `recommended_status` | **流程应走向哪** | `OPEN` / `PENDING_LEGAL_DECISION` / `AWAITING_EVIDENCE` |

**三者不可互相推导**。典型组合：

| 组合 | 含义 | 处置 |
| --- | --- | --- |
| HIGH 等级 + 高置信度 + 依据充分 | 明确的严重风险 | `OPEN` → 法务确认 |
| HIGH 等级 + **低置信度** | 可能是高风险但没把握 | **`PENDING_LEGAL_DECISION`**（第 11 条：低置信度但潜在影响高的，优先人工，不得忽略） |
| HIGH 等级 + 依据缺失 | 涉嫌违规但查不到适用规则 | `PENDING_LEGAL_DECISION` + `unsupported_claims` |
| LOW 等级 + 高置信度 | 轻微问题 | `OPEN`，可低优先级展示 |

### 6.2 强制转人工的触发条件（服务端判定，不交给模型自觉）

```java
boolean mustGoToHuman(RiskDraft d) {
    return d.confidence() < CONFIDENCE_THRESHOLD        // 阈值由 ruleset 配置，默认 0.6
        || d.ruleReferences().isEmpty()                 // 无依据
        || !d.unsupportedClaims().isEmpty()             // 模型想引用但检索不到
        || d.evidenceAnchorIds().isEmpty()              // 无处定位
        || anchorValidationFailed(d)                    // 锚点校验未通过
        || d.riskLevel() == HIGH && d.confidence() < HIGH_RISK_CONFIDENCE_THRESHOLD;
}
```

命中任一条 → `recommended_status = PENDING_LEGAL_DECISION`，且 `review_record` 记录触发原因。**这样"待人工判断"的判定标准是可复现的代码，而不是模型的一句话。**

### 6.3 修改建议与沟通话术

- `suggestion`：说明问题是什么、为什么需要改、建议怎么改
- `recommended_copy`：直接可用的替换文案
- `required_evidence`：保留原表达需要补充哪些材料
- 沟通话术（给设计/品牌/市场/业务看）由阶段 5 后基于**已校验结果**生成，**不得由模型自由发挥**（否则可能与风险记录矛盾）

### 7.3 服务端校验流程（唯一可信关口）

```java
public ValidatedRisks validate(String rawModelOutput, ValidationContext ctx) {
    // ① 容错提取 JSON（路径 B 必需：OCR 模型不支持结构化输出）
    String json = JsonExtractor.extract(rawModelOutput);
    //   - 剥离 ```json 代码块围栏
    //   - 截取首个 '{' 到末个 '}'
    //   - 容忍尾随逗号、单引号、注释
    //   - 提取失败 → RepairFailed → 重试或降级

    // ② JSON Schema 校验（networknt/json-schema-validator）
    Set<Violation> violations = schemaValidator.validate(json);
    if (!violations.isEmpty()) → 记 ai_invocation，重试；连续失败 → 降级为待人工

    // ③ 锚点存在性校验（§3.3 约束 3）
    for (RiskDraft d : drafts) {
        for (String aid : d.location().anchorIds()) {
            if (!ctx.anchorIdsOfThisVersion().contains(aid)) {
                markLocationInvalid(d, "锚点ID不存在：" + aid);
                d = forcePendingHuman(d, "定位校验失败");
            }
        }
    }

    // ④ 依据真实性校验（§5.3 防虚构）
    for (RiskDraft d : drafts) {
        d.ruleReferences().removeIf(r -> {
            boolean ok = ctx.retrievedKbItemVersionIds().contains(r.kbItemVersionId());
            if (!ok) d.unsupportedClaims().add("未检索到的依据：" + r.quotedText());
            return !ok;
        });
    }

    // ⑤ 强制转人工判定（§6.2）
    drafts.forEach(d -> { if (mustGoToHuman(d)) d.setRecommendedStatus(PENDING_LEGAL_DECISION); });

    // ⑥ 去重（§8.3）
    return deduplicate(drafts, ctx);
}
```

**校验失败绝不静默丢弃**：每条被丢弃/修改的草稿都必须留下原因，最终体现为「待人工判断」而不是「通过」。

### 7.4 报告生成只能基于已校验结果（A5）

```
已校验的 Risk Case（数据库） ─► 生成报告措辞 ─► Markdown 报告
```

**禁止**让模型"看着原文再总结一遍风险"——那样报告与库中数量/状态必然漂移。正确做法是：把已落库的 Risk Case 结构化数据交给模型，只让它**组织语言**，并明确要求"不得新增、删除或改变任何风险的数量、等级与结论"。

**一致性断言**（建议做成测试）：报告中的风险条目数、各等级数量、物料分类数量，必须与数据库查询结果**逐项相等**。不等即测试失败。

## 8. 阶段间契约与幂等

### 8.1 版本标识落库

每条 Risk Case 与每次 AI 调用都必须记录：

| 字段 | 含义 | 为什么必须有 |
| --- | --- | --- |
| `model_id` | 产出该判断的模型 | 模型升级后解释结论差异 |
| `pipeline_version` | 流水线版本 | 阶段增减/顺序调整可追溯 |
| `prompt_version` | 提示词版本 | same prompt 变了要能定位 |
| `ruleset_version` | 规则集版本 | 规则变了结论变了要能解释 |

**缺了这四个，审计上就无法回答"为什么同一份材料这次判得不一样"。**

### 8.2 三层幂等

| 层 | 键 | 表/约束 | 效果 |
| --- | --- | --- | --- |
| 文件 | `material_id + file_sha256` | `uk_version_sha` | 同文件重复上传 → 复用版本，不新建 |
| 任务 | `case_id + material_id + version_id + pipeline_version + prompt_version + ruleset_version + model_id` | `uk_parse_idem` / `uk_async_idem` | 同配置重复提交 → 返回已有结果 |
| 风险 | `version_id + risk_type + 主锚点ID + 归一化原文哈希` | `uk_risk_dedup` | 同风险不重复建单 |

**归一化规则**（用于 `dedup_key` 的原文哈希）：去首尾空白 → 全角转半角 → 去标点 → 统一小写。**注意不要把原文直接存进键里**（键是哈希），避免敏感信息扩散到索引。

### 8.3 规则命中去重

同一版本内，若两条草稿满足"`risk_type` 相同 + 主锚点相同"，则合并：

- 保留 `confidence` 较高者作为主记录
- 合并 `evidenceReferences` 与 `anchorIds`（全部保留，不丢失证据）
- 若两条的 `riskLevel` 不同，取较高等级并在 `reason` 中记录合并来源
- 合并过程写 `review_record`，保证可追溯

## 9. 失败处理与降级矩阵

| 失败点 | 处理 | 最终状态 |
| --- | --- | --- |
| 文件格式不支持/损坏 | 阻止进入初审，明确告知重传 | `parse_status=FAILED`，不计入通过率分母 |
| OCR 返回格式抖动（路径 B） | 容错提取 → 重试（最多 3 次，指数退避） | 仍失败 → 该物料转待人工，标注"解析未通过校验" |
| ASR 结果 URL 过期未落盘 | 视为解析失败，需重跑；**提前告警** | `parse_status=FAILED` |
| Schema 校验失败 | 重试；连续失败降级 | `PENDING_LEGAL_DECISION` |
| 锚点 ID 不存在 | 该风险定位无效，转人工并记录原因 | `PENDING_LEGAL_DECISION` |
| 检索无结果 | 不阻断，但 `ruleReferences` 为空 → 强制转人工 | `PENDING_LEGAL_DECISION` + `unsupportedClaims` |
| 429 / 限流 | 指数退避 + 抖动；队列层全局令牌桶 | 重试 |
| 回调验签失败 | **拒绝该回调**并告警（防注入） | 保持轮询兜底 |
| 批量任务部分失败 | 逐条记录，成功的照常入库，失败的单独重试 | `parse_status=PARTIAL` |

**统一铁律**：任何 AI 环节失败都**降级为「待人工判断」，绝不降级为「通过」**（ADR D-08）。降级方向唯一，不允许例外。

## 10. Prompt 分层与版本管理

### 10.1 分层结构

```
┌─ L0 固定前缀（跨任务、跨物料字节级一致）─────────────────┐
│  角色定义、审核准则、风险类型字典、输出契约说明与示例      │
│  变更频率极低；任何改动都必须提升 prompt_version          │
├─ L1 规则集（ruleset_version 维度）───────────────────────┤
│  本次启用的风险规则与常用法条要点                        │
├─ L2 任务级────────────────────────────────────────────┤
│  本次审核要求（用户确认过的）、项目/产品上下文            │
├─ L3 物料级────────────────────────────────────────────┤
│  解析文本 + 锚点清单（anchor_id + text）+ 检索到的依据    │
└──────────────────────────────────────────────────────┘
```

### 10.2 关于"分层省钱"的重要更正

`00` 文档已核实：**`qwen3-vl-8b-thinking`、`qwen-vl-ocr`、`qwen3.5-ocr` 均不支持上下文缓存**。因此：

- ❌ **分层不再带来"缓存命中省 50 倍"的收益**——这一点必须说清楚，不能沿用面向支持缓存模型的乐观假设
- ✅ 分层仍然有价值：**可维护性**（改契约不污染知识库部分）、**可审计性**（`prompt_version` 能精确定位改动）、**Batch 场景下的重复传输更少**，以及**将来切换到支持缓存的模型时可自动受益**

**成本优化应改走 Batch**（见 §11），而不是指望缓存。

### 10.3 Prompt 版本管理纪律

| 规则 | 说明 |
| --- | --- |
| Prompt 存于版本化文件，不硬编码在 Java 里 | 如 `resources/prompts/{stage}/v{n}.md` |
| 任何改动必须提升版本号 | 包括"只改了个错别字" |
| 版本号随每次调用落库 | `ai_invocation.prompt_version` |
| 支持按版本回放 | 用旧 prompt + 旧 model 复现历史结论，用于争议复盘 |
| 改动需过评测 | 高风险召回率不得下降，否则不予上线（`AGENTS.md` 第 15 条） |

## 11. 成本核算

### 11.1 记录粒度

每次调用写 `ai_invocation`：`stage`、`model_id`、`region`、`batch_mode`、`input_tokens`、`output_tokens`、`latency_ms`、`success`、`request_id`。

按 `case_id` 归集得到单 Case 成本，用于：
- 预算控制与异常告警
- 判断某个阶段是否值得换更便宜的模型

### 11.2 成本优化优先级

| 优先级 | 手段 | 依据 |
| --- | --- | --- |
| 1 | **OCR 走 Batch**（`qwen-vl-ocr` Batch File 输入 $0.022 vs 实时 $0.043） | 约减半，是当前最有效手段 |
| 2 | **专用小模型分工**（OCR/ASR 用专用模型，不用旗舰多模态硬扛） | OCR 输出 $0.072–0.275/百万量级 |
| 3 | **检索层收口**（50–100 候选 → rerank Top 5–10 再送 LLM） | 显著压缩送入 LLM 的 token |
| 4 | **地域锁定北京**（RPM 600 vs 新加坡 60） | 吞吐差 10 倍，避免为达吞吐而扩容 |
| 5 | ~~上下文缓存~~ | ❌ 关键模型不支持，不可用 |

### 11.3 成本监控指标

- `batch_mode=1` 的调用占比（**这才是当前的成本杠杆指标**）
- 单 Case 平均 token 与费用
- 各阶段 token 占比（定位异常膨胀的阶段）
- 解析重试率（重试即重复计费）

❌ **不要用"缓存命中率"作为核心成本指标**——关键模型不支持缓存，这个指标会长期为 0 并误导判断。

## 12. 效果评测方法

`AGENTS.md` 第 15 条要求不能只看整体准确率，必须分项评估。

### 12.1 指标定义

| 指标 | 计算方式 | 说明 |
| --- | --- | --- |
| **高风险召回率** | 人工标注的高风险项中，被 AI 识别出来的比例 | **最高优先级**，漏检代价最大 |
| 误报率 | AI 报出的风险中，被法务标记误判的比例 | 直接影响法务负担 |
| 风险定位准确率 | `evidence_anchor_ids` 指向的位置确实包含该风险的比例 | 锚点抽象的核心价值验证 |
| 法规依据有效率 | `ruleReferences` 中经法务认可有效且适用的比例 | 防虚构机制的效果验证 |
| 修改建议可执行性 | 法务认为建议可直接执行/稍改可用的比例 | 主观评分，需明确定义评分标准 |
| 待人工判断比例 | `PENDING_LEGAL_DECISION` 占全部 Risk Case 的比例 | 过高则法务工作量不降反升 |
| 法务实际节省时间 | 与传统人工审核的耗时对比 | 产品成功的最终标准 |

### 12.2 评测集构造

| 样本类型 | 来源 | 用途 |
| --- | --- | --- |
| 正样本（确有风险） | 历史审核中法务确认过的风险物料 | 测召回率 |
| 负样本（无风险） | 历史审核中判为误判或无风险的物料 | 测误报率 |
| 边界样本 | 法务争议过、需专业判断的案例 | 测"待人工判断"分流的合理性 |
| 对抗样本 | 故意构造的极限情形（极小字号免责声明、图文不一致、口播与字幕矛盾） | 测鲁棒性 |

### 12.3 评测纪律

- **高风险漏检的测试优先级高于文案风格优化**（第 15 条明文）
- 评测集必须**冻结版本**并纳入版本管理，避免"用同一批样本反复调参"导致的过拟合
- 每次 prompt / 规则集 / 模型变更都必须跑回归，**高风险召回率下降则不予上线**
- 评测结果必须记录 `model_id` / `prompt_version` / `ruleset_version`，否则结果无法比较

## 13. 未实现能力的标注要求

`AGENTS.md` 第 15 条：**任何尚未实现或尚未验证的能力，都应明确标记为待办或实验能力，不得在产品界面中伪装成已经可靠可用。**

因此：

| 能力 | 当前状态 | 界面要求 |
| --- | --- | --- |
| 文字类风险定位 | 待 M0 验证（V1/V2） | 验证通过前不展示"已精确定位" |
| 画面类风险定位 | 仅九宫格大致区域 | **必须标注"大致区域"**，不得暗示像素级精度 |
| 视频关键帧语义理解 | 待验证（V4） | 未验证前标注为实验能力 |
| 相似物料检索（多模态） | 待验证（V7） | 未验证前不进入正式流程 |
| 文档原生解析 | 待确认（§3.3 待确认项） | 未确认前按"渲染+OCR"实现，界面不承诺文本级精度 |

**表述规范**：实验性能力必须在界面上有可见标识（如"实验"标签），且不得作为审核结论的唯一依据。
