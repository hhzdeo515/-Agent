# 技术选型调研：PDF / PPTX / DOCX 解析与 Java↔Python 集成

> 调研对象：企业内部「广宣法务审核 Agent」，后端 Java 17 + Spring Boot 3，Docker 内网部署（无外网出口）。
> 目标能力：解析 PDF / PPTX / DOCX，保留「页码 / 段落 / 句子」级锚点，使 AI 发现的风险能跳回原文位置。

### A.2 结论（A 节）

1. **PyMuPDF 是本项目唯一需要重点过法务的许可证风险项。** 它是 AGPL-3.0 与 Artifex 商业授权的双授权产品（[PyPI License 字段](https://pypi.org/project/PyMuPDF/)、[官方 License and Copyright](https://pymupdf.readthedocs.io/en/latest/about.html)）；Artifex 官方把「作为 server-based application/service 部署而不按 AGPL 公开自有应用源码」列为不可为，且措辞针对的是「**any users interacting with it**」而非仅「对外分发」（[artifex.com/licensing](https://artifex.com/licensing)）。**「企业内网自用」是否触发义务属法律解释问题，本文不结论**；另需注意 Artifex 页中「No report needed for internal usage」属于**商业订阅许可**说明，不构成 AGPL 豁免。
2. **坐标能力最完整、开箱即用的是 PyMuPDF 与 pdfplumber，但两者许可证性质相反。** PyMuPDF 的 `words` 直接给 word 级 bbox、`rawdict` 下到每字符 `bbox`+`origin`（[TextPage 文档](https://pymupdf.readthedocs.io/en/latest/textpage.html)）；pdfplumber 的 `chars` 每字符一个 dict 且显式列出 `x0/y0/x1/y1`（[README](https://github.com/jsvine/pdfplumber/blob/stable/README.md#objects)）。前者 AGPL-3.0/商业，后者 MIT。
3. **Java 主服务直接调用 PDF 坐标能力的现成方案是 Apache PDFBox（Apache-2.0）**，且这是本表中唯一「Java 原生 + 宽松许可证 + 官方提供逐字符坐标」的组合：`TextPosition` 给出旋转校正与文本方向校正两套坐标、每字符宽度数组，`PDFTextStripper.writeString(String, List<TextPosition>)` 是可覆写的逐词回调点；但必须显式 `setSortByPosition(true)` 才能按阅读顺序输出（[TextPosition javadoc](https://javadoc.io/static/org.apache.pdfbox/pdfbox/3.0.8/org/apache/pdfbox/text/TextPosition.html)、[PDFTextStripper 源码](https://svn.apache.org/repos/asf/pdfbox/trunk/pdfbox/src/main/java/org/apache/pdfbox/text/PDFTextStripper.java)）。
4. **pypdf 不适合作为「句子级锚点」主力**：它没有 char/word 级 bbox 高层 API，只能通过 `visitor_text` 拿变换矩阵自行换算，官方自己声明复杂文档中 visitor 坐标「may be difficult to determine」（[官方文档](https://pypdf.readthedocs.io/en/stable/user/extract-text.html)）。其合理定位是纯 Python 环境的轻量文本/元数据处理（BSD-3-Clause）。
5. **「PDF 无段落/句子语义」是格式层面的既有限制，不是库的能力缺陷**：pypdf 官方明确写「PDF files don't contain a semantic layer」（[官方文档](https://pypdf.readthedocs.io/en/stable/user/extract-text.html)）。因此「段落 / 句子」锚点只能由 bbox 几何规则或版面模型推断。
6. **扫描件（图片型 PDF）判定：官方只提供原材料，没有专门 API。** PyMuPDF 侧可组合「文本长度 = 0 / 极短」+「图片块或 `get_image_info()` 覆盖面积」；pdfplumber 侧可组合「`len(page.chars)`」+「`page.images` 面积占比」；pypdf 官方直接建议「文本极少或视觉为空 → 考虑 OCR」（[PyPI FAQ](https://pypi.org/project/PyMuPDF/)、[README](https://github.com/jsvine/pdfplumber/blob/stable/README.md#objects)、[pypdf 文档](https://pypdf.readthedocs.io/en/stable/user/extract-text.html)）。OCRmyPDF 的默认行为本身就是「检测到页面已有文字即退出」，并把该判断结果以返回码 6 暴露给调用方（[文档](https://ocrmypdf.readthedocs.io/en/latest/advanced.html)）。**具体阈值数值无官方来源，见「不确定项」。**

### B.2 结论（B 节）

1. **PPTX 的「页」锚点在格式层面天然成立**：PresentationML 以 slide part 为单位组织，`Slides` 支持按索引访问、`Slide.slide_id` 提供不随位置变化的稳定标识，因此「**页（slide 索引或 slide_id）+ 形状框**」两级锚点在 PPTX 上可实现（[python-pptx slides API](https://python-pptx.readthedocs.io/en/latest/api/slides.html)）。
2. **⚠️ 单位不一致是跨栈混用的硬约束**：python-pptx 的 `left/top/width/height` 官方原文为「Expressed in **English Metric Units (EMU)**」（[shapes API](https://python-pptx.readthedocs.io/en/latest/api/shapes.html)），而 **POI XSLF 的 `getAnchor()` 官方 javadoc 原文为「All coordinates are expressed in points (72 dpi)」**（[Shape javadoc](https://poi.apache.org/apidocs/dev/org/apache/poi/sl/usermodel/Shape.html)）。同一种 PPTX，两套库返回的坐标单位**不同**，任何把两者混用的实现都必须显式换算。POI 侧若需要 EMU 原值，官方路径是经 `XWPFRun.getEmbeddedPictures()` → `XWPFPicture.getCTPicture()` 取底层 DrawingML bean（`a:ext` 的 `cx`/`cy` 原始值即 EMU），但 `XWPFPicture.getWidth()` / `getDepth()` 返回的是 points。
3. **若考虑「Java 原生全包 PPTX / DOCX」，Apache POI 自己给出了两条成熟度保留意见**：(a) 官网 PowerPoint 组件页原文「**Please note that XSLF is still in early development and is a subject to incompatible changes in future.**」，且 HSLF 与 XSLF 之间「there is not a common interface」；(b) `XWPFDocument` 类注释自述「as it's not a mature and stable API yet」。（[POI PowerPoint 组件页](https://poi.apache.org/components/slideshow/index.html)、[XWPFDocument javadoc](https://poi.apache.org/apidocs/dev/org/apache/poi/xwpf/usermodel/XWPFDocument.html)）
4. **DOCX 的「固定页码」在格式层面不成立，这是文件格式性质而非解析库缺陷**：ISO/IEC 29500-1 把 `w:lastRenderedPageBreak` 定义为「上次由会分页的应用保存时」缓存的断页位置，用途是「供其他应用（如辅助软件）利用」（[Microsoft Learn](https://learn.microsoft.com/en-us/dotnet/api/documentformat.openxml.wordprocessing.lastrenderedpagebreak?view=openxml-3.0.1)）。**python-docx 官方文档对此给出了完全一致的表述**：「The position of these can change depending on the printer and page-size, as well as margins, etc. They also will change in response to edits, but not until Word loads and saves the document.」并明确「these are never inserted by python-docx because it has **no rendering function**」（[官方文档](https://python-docx.readthedocs.io/en/latest/api/text.html)）。**结论：DOCX 页码必须由渲染决定（例如转 PDF 后取页码），或降级为「段落索引」锚点。**
5. **DOCX 的稳定锚点应选「段落索引 + run」而非页码**：python-docx（MIT）的 `Document.paragraphs` / `Document.tables` 官方标注为「in document order」，`Paragraph.runs` + `Run.bold/italic/underline` 提供 run 级信息；POI XWPF（Apache-2.0）同样暴露段落与 run 级属性，并有 `getEmbeddedPictures()` 取图片（[Document objects](https://python-docx.readthedocs.io/en/latest/api/document.html)、[Text-related objects](https://python-docx.readthedocs.io/en/latest/api/text.html)、[XWPFRun 源码](https://svn.apache.org/repos/asf/poi/trunk/poi-ooxml/src/main/java/org/apache/poi/xwpf/usermodel/XWPFRun.java)）。
6. **两份 Python Office 库的维护节奏差异明显**：python-docx 1.2.0（2025-06-16 发布），python-pptx 1.0.2（2024-08-07 发布，近两年无新版）（[python-docx PyPI](https://pypi.org/project/python-docx/)、[python-pptx PyPI](https://pypi.org/project/python-pptx/)）。
7. **商业与转换类备选方案的官方限制已可量化**：Aspose.Words 评估版会加水印并把文档限制到「a few hundred paragraphs」，Aspose.Slides 评估版会加水印且**提取文本时限制为 1 张幻灯片**（[Words licensing](https://docs.aspose.com/words/java/licensing/)、[Slides licensing](https://docs.aspose.com/slides/java/licensing/)）；LibreOffice 的 headless 转换参数有官方文档，但**其 Docker 镜像体量与中文字体问题没有任何官方依据**（[官方帮助页](https://help.libreoffice.org/latest/en-US/text/shared/guide/start_parameters.html)）。
8. **「句子」级锚点在 PPTX/DOCX 上都没有现成规范**：OOXML 提供段落（`a:p` / `w:p`）与 run 结构，但「句子」边界需自行切分；python-docx 与 POI XWPF 均未提供 sentence 级 API。

### C.2 结论（C 节）

1. **Java 侧 HTTP 调用方式的选择在官方文档中是明确的**：Spring Framework 参考文档专章列出 `RestClient`（同步、fluent）、`WebClient`（非阻塞响应式）、`RestTemplate`（**官方已标注 deprecated in favor of RestClient**）与 HTTP Service Clients（[Spring Framework: Rest Clients](https://docs.spring.io/spring-framework/reference/integration/rest-clients.html)）；Python 侧 FastAPI 为 MIT、grpcio 为 Apache-2.0（[FastAPI](https://pypi.org/project/fastapi/)、[grpcio](https://pypi.org/pypi/grpcio/json)）。
2. **gRPC 在 Python 侧有官方文档与语言页，但 grpc.io 上查不到任何「GA / 支持级别」声明**，能引用的成熟度证据只有 PyPI 分类器 `Development Status :: 5 - Production/Stable`（[grpc.io/docs/languages/python](https://grpc.io/docs/languages/python/)、[PyPI JSON](https://pypi.org/pypi/grpcio/json)）。**这一点与「Python 侧成熟度」的常见说法需要区分：官网没有背书措辞。**
3. **Java gRPC 工具链有两个重要事实**：(a) `org.xolstice.maven.plugins:protobuf-maven-plugin` **GitHub 仓库已归档**，Maven Central 自 2018-10 起无新版本，且 Spring Boot 官方 gRPC 章节管理的是 `io.github.ascopes:protobuf-maven-plugin`（[归档仓库](https://github.com/xolstice/protobuf-maven-plugin)、[Spring Boot gRPC 章节](https://docs.spring.io/spring-boot/reference/io/grpc.html)）；(b) **`spring-grpc` 项目真实存在且活跃**（Apache-2.0，最新正式版 v1.1.1，且 Spring Boot 4.1.1 已内置 gRPC 章节与 starter）（[spring-grpc](https://github.com/spring-projects/spring-grpc)）。
4. **消息队列侧的许可证与支持级别差异显著，必须分别核实**：RabbitMQ 核心 **MPL-2.0**（[LICENSE](https://github.com/rabbitmq/rabbitmq-server/blob/main/LICENSE)）、Kafka **Apache-2.0**（[LICENSE](https://github.com/apache/kafka/blob/trunk/LICENSE)）、Redis 自 8 起为 **RSALv2 / SSPLv1 / AGPLv3 三选一**，7.2 及更早仍为 BSDv3（[LICENSE.txt](https://github.com/redis/redis/blob/unstable/LICENSE.txt)）；Celery 官方把 **Kafka 与 Google Pub/Sub、Zookeeper 一起标为 Experimental**，RabbitMQ 与 Redis 为 Stable（[Celery brokers 文档](https://docs.celeryq.dev/en/stable/getting-started/backends-and-brokers/index.html)）。
5. **进度上报的协议层有权威规范可引用**：SSE 由 WHATWG HTML 规范定义（`EventSource`，[规范](https://html.spec.whatwg.org/multipage/server-sent-events.html)），WebSocket 由 RFC 6455 定义（[RFC](https://www.rfc-editor.org/info/rfc6455/)）。**「任务表状态机 + 轮询」也有权威参考**：Spring Batch 官方 domain 章给出了 `JobRepository` + `BatchStatus(STARTED/FAILED/COMPLETED)` + 具名元数据表 + `JobOperator`（start/stop/restart/abandon）的完整模型，可直接作为任务状态机设计的引用依据（[Spring Batch: Domain Language](https://docs.spring.io/spring-batch/reference/domain.html)）。
6. **「Java 原生替代 Python」在三项上的核实结果**：(a) **Tess4J 真实存在**（`nguyenq/tess4j`，Apache-2.0，5.20.0，JNA 包装而非 JNI），但**是否需要自带本机 Tesseract/tessdata 未取得官方原文**（[仓库](https://github.com/nguyenq/tess4j)、[Maven metadata](https://repo1.maven.org/maven2/net/sourceforge/tess4j/tess4j/maven-metadata.xml)）；(b) **ONNX Runtime Java 真实存在且官方文档明确支持**（Java 8+，Maven Central，1.30.0），但官方**没有 OCR / ASR 示例**，且其**许可证本次未证实**（[官方文档](https://onnxruntime.ai/docs/get-started/with-java.html)、[Maven metadata](https://repo1.maven.org/maven2/com/microsoft/onnxruntime/onnxruntime/maven-metadata.xml)）；(c) **Whisper 的 Java 绑定 `whisper-jni` 确实存在**（Apache-2.0，JNI 包装 whisper.cpp），但最近 push 为 2025-04-26，**是否可用未验证 → 不确定**（[仓库](https://github.com/GiviMAD/whisper-jni)）。
