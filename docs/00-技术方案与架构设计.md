## 1. 关键结论（TL;DR）

**关于模型选型**

1. **千问一家即可覆盖全链路，无需再引入第二家供应商。** 已核实百炼同时提供：多模态视觉理解（含原生视频输入）、**专用 OCR 模型（具备文本定位能力）**、**语音识别（句级/字级时间戳）**、文本向量、多模态向量、文本重排序、多模态重排序。这一点很关键——早前评估的 DeepSeek 只有"图像理解 + 文本推理"两段，OCR、ASR、Embedding、Rerank 四层全部缺失，必须自建或另接供应商。
2. **"只在千问里做、没有专门 OCR/ASR 模型"这个前提需要修正**：百炼有 `qwen-vl-ocr` 与 `qwen3.5-ocr` 两个 OCR 专用模型，以及 `qwen3-asr-flash-filetrans` 等 ASR 专用模型。因此不需要用通用多模态模型硬扛 OCR，可以直接用专用模型，精度与成本都更优。
3. **视频链路不存在"30 秒限制"这类硬伤**：非实时语音识别支持 **单文件 ≤2GB、≤12 小时**，且**句级与字级时间戳（毫秒）原生返回**，不需要 VAD 切句绕路。

**关于架构**

4. **本方案的核心抽象是「证据锚点 Evidence Anchor」**。解析阶段为每个物料版本产出一批带稳定 ID 的锚点（OCR 文字行 / ASR 句子 / 关键帧 / 文档段落），模型输出风险时**只引用锚点 ID**，不输出坐标。定位 = ID 查表，可 100% 校验。
5. **OCR 的"文本定位"能力与锚点抽象是互补而非替代**。OCR 模型直接给出文字坐标是最可靠的坐标来源，锚点层负责把它固化为稳定 ID 并做校验；两者结合才能既准又可审计。
6. **结构化输出要分层处理，不能指望一个开关**。已核实的硬约束：`qwen3.5-ocr`、`qwen-vl-ocr` **均不支持结构化输出（JSON 模式）**，而 `qwen3-vl-8b-thinking` 支持。因此**只要用到 OCR 模型，就必须在服务端做 JSON 解析与 Schema 校验兜底**，不能依赖 `response_format`。
7. **很多关键模型不支持上下文缓存**（`qwen3-vl-8b-thinking`、`qwen3.5-ocr`、`qwen-vl-ocr` 均标注"上下文缓存：不支持"）。这意味着不能照搬"靠缓存命中省 50 倍成本"的策略，**成本优化必须改走 Batch 批量推理**（`qwen-vl-ocr` 支持，Batch File 单价约为实时的一半）。
8. **成本优化主路径 = Batch 批量推理 + 专用小模型分工**，而不是缓存。批量文件输入单价约为实时调用的一半，且广宣批次审核天然适合离线批处理。

**关于产品边界**

9. **四模块职责必须写成可检查的表 + 代码守卫**（见 §5），而不是靠文档约定。`AGENTS.md` 反复强调"不得为了页面丰富而在多个模块重复实现相同核心流程"。
10. **权限"三处一致"靠数据库触发器兜底**。MySQL 8 无行级权限，用**状态跃迁触发器 + 签名表只允许 INSERT** 让 DB 层真实生效。
11. **版本三件套（pipeline_version / prompt_version / ruleset_version）必须落库**，否则模型升级后无法解释、无法复现历史结论，违反审计要求。
12. **法规依据防虚构是机制而非呼吁**：`rule_references` 在契约中定义为**知识库 rule_id 数组**，模型无法凭空生成合法 ID；想引用但检索不到的内容只能进 `unsupported_claims` 并转待人工判断。
13. **AI 环节失败一律降级为「待人工判断」，绝不降级为「通过」**。这是安全方向的强制选择。

`qwen-vl-ocr` 快照版本：
- **`qwen-vl-ocr-2025-11-20`**：基于 **Qwen-VL3 架构**全面升级，**文档解析、文字定位能力全面升级，端到端时延与幻觉大幅降低**。
- `qwen-vl-ocr-2025-04-13`：内置六种识别任务——通用识别、文档解析、表格解析、信息抽取、多语言识别、公式识别。

> **架构含义（两条重要取舍）**
> 1. **OCR 模型不支持结构化输出**，所以 OCR 结果必须走"模型出 JSON 文本 → 服务端解析校验"，且**解析失败要能优雅降级**（不能因为 OCR 返回格式抖动就让整份物料解析失败）。
> 2. **`qwen-vl-ocr` 支持 Batch 且单价减半**，而 `qwen3.5-ocr` 版本更新、定位更强但不支持 Batch。**建议：默认用 `qwen-vl-ocr` 走 Batch 批处理（成本优先），对解析质量不达标的物料再用 `qwen3.5-ocr` 重跑（质量兜底）。** 这一"双模型 + 质量兜底"策略比单纯选一个更稳。

### 2.2 语音识别（解决视频口播链路）

非实时语音识别能力（官方描述）：支持多语言识别、歌唱识别、噪声拒识、**说话人分离**、敏感词过滤、**句子/词语级时间戳**。

| 项 | 值 |
| --- | --- |
| **文件限制（异步）** | **单文件 ≤2GB、时长 ≤12 小时** |
| 文件限制（同步） | ≤10MB、≤5 分钟 |
| 采样率/格式 | 支持任意采样率，兼容 aac、wav、mp3 等主流音视频格式 |
| 增强能力 | 上下文增强、自定义热词、说话人分离、情感识别、敏感词过滤 |

**模型选型**

| 模型 | 调用方式 | 时间戳 | 说话人分离 | 备注 |
| --- | --- | --- | --- | --- |
| `qwen-audio-3.0-asr-flash-filetrans` | 异步 | ✅ 固定开启 | ✅ | ≤12h/2GB |
| `fun-asr`（含 `fun-asr-mtl`） | 异步 | ✅ 固定开启 | ✅ | ≤12h/2GB |
| **`qwen3-asr-flash-filetrans`** | 异步 | ✅ 固定开启，`enable_words` 控制级别 | — | ≤12h/2GB；**推荐主力** |
| `paraformer-v2` / `paraformer-8k-v2` | 异步 | ✅ 固定开启 | ✅ | ≤12h/2GB |
| `qwen3-asr-flash` | 同步/流式 | ⚠️ 见下方陷阱 | — | ≤10MB/5min |
| `qwen-audio-3.0-asr-flash` / `fun-asr-flash-2026-06-15` | 同步 | ✅ | — | ≤10MB/5min |

**时间戳结构（本项目定位能力的基础）**

```json
{
  "transcripts": [{
    "channel_id": 0,
    "text": "……",
    "sentences": [{
      "begin_time": 100,          // 毫秒，句级起点
      "end_time": 3820,           // 毫秒，句级终点
      "text": "你好，我们今天讨论项目进度。",
      "sentence_id": 1,
      "speaker_id": 0,            // 开启说话人分离时返回
      "emotion": "neutral",       // Qwen3-ASR 系列固定开启
      "language": "zh",
      "words": [                  // 字级时间戳
        { "begin_time": 100, "end_time": 596, "text": "你好", "punctuation": "" }
      ]
    }]
  }]
}
```

- 时间戳单位统一为**毫秒**。
- **句级**：`sentences[].begin_time` / `end_time`。
- **字级**：`sentences[].words[].begin_time` / `end_time` / `text`。
- `qwen3-asr-flash-filetrans` 通过 `enable_words` 控制：`false`（默认）返回句级，`true` 返回字级。**字级时间戳仅支持中文、英语、日语、韩语、德语、法语、西班牙语、意大利语、葡萄牙语、俄语**，其他语种不保证准确性。
- 说话人分离：`diarization_enabled=true`，建议音频 ≤2 小时，**仅支持单声道**。

**⚠️ 四个必须写进代码与测试的陷阱**

1. **`qwen3-asr-flash` 走 OpenAI 兼容接口时输出形态为 `chat.completion`，不返回时间戳字段。** 本项目必须定位到时间点，因此**必须使用 `qwen3-asr-flash-filetrans` 异步任务接口**，不能用兼容接口图省事。
2. **同名不同义字段**：任务级 `end_time` 是**任务完成时间（字符串日期，如 `"2024-09-12 15:11:40.903"`）**；音频内时间戳是**毫秒整数**。文档明确警告勿混淆。**这两者在解析代码里必须用不同类型承载（如 `Instant` vs `long`），从类型层面杜绝混用。**
3. **识别结果 URL 仅 24 小时有效**（`transcription_url` 指向公网 JSON）。**必须提交后及时下载落盘到 MinIO**，否则结果丢失且需重跑计费。
4. **异步结果字段路径因模型而异**：`qwen-audio-3.0-asr-flash-filetrans` / `fun-asr` / `paraformer` 为 `output.results[].transcription_url`（数组，含 `subtask_status`）；`qwen3-asr-flash-filetrans` 为 `output.result.transcription_url`（**单对象，无 `results[]`**）。usage 字段分别为 `duration` 与 `seconds`。**代码不可写死单一路径**，需按模型分派。

**生产环境要求**

- **回调安全（必须做）**：异步任务建议用 EventBridge 回调替代轮询（轮询查询接口默认 20 QPS、最高 100 QPS，高并发易限流）。但**HTTP/HTTPS 投递方式必须校验请求头 `X-Eventbridge-Signature*`**——官方明确警示：不校验则**任意外部 IP 都可伪造 `AsyncTaskFinish` 事件注入虚假识别结果**。这对法务审核系统是不可接受的注入风险。建议同时设置 ≥5 秒接收超时。
- **回调幂等**：同一事件可能重复投递，需以 `data.id` 或 `data.task_id` 去重。
- **回调延迟**：任务结束到投递通常约 1–90 秒。
- **文件托管**：生产建议上传 OSS 并以 URL 调用；**本地文件上传调用上限 100 QPS 且不支持扩容**。
- **降噪**：噪声较大的音频建议先用 FFmpeg 预处理再提交。

### 2.3 检索层（Embedding + Rerank）

**文本向量**

| 模型 | 向量维度 | 批次大小 | 单批次最大 Token | 单价（每百万输入） |
| --- | --- | --- | --- | --- |
| `qwen3.7-text-embedding` | 2560 / 2048 / 1536 / **1024（默认）** / 768 / 512 / 256 | 20 | 128,000 | $0.07（新加坡） |
| **`text-embedding-v4`** | 2048 / 1536 / **1024（默认）** / 768 / 512 / 256 / 128 / 64 | 10 | 8,192 | $0.072（北京） |
| `text-embedding-v3` | **1024（默认）** / 768 / 512 | 10 | 8,192 | — |

- `text-embedding-v4` 属 **Qwen3-Embedding** 系列，支持 100+ 语种。
- **单条文本不得超过 8,192 token（v4）**，批次 ≤10 条。**这意味着长法条必须切块，切块策略要对齐这个上限。**
- **CMTEB 实测（中文检索）**：v4 @1024 维 = 70.14，@2048 维 = 71.99。**1024 维是性能与成本的最佳平衡点**，建议默认 1024。
- 高级能力（仅 DashScope SDK/API 支持，**OpenAI 兼容接口不支持**）：
  - `text_type`：区分 `query` / `document`。**短查询匹配长文档时必须设置**，否则检索质量明显下降。
  - `instruct`：英文任务指令优化向量（`qwen3.7-text-embedding` 指令遵循比 v4 提升 16.4%）。使用时必须同时设 `text_type=query`。
  - `output_type`：`dense` / `sparse` / `dense&sparse`。**稀疏向量做关键词精确匹配**（法条名称、条款号），**稠密向量做语义匹配**。新版 sparse 采用类 SPLADE 策略，提升 8.4%。
- **Batch 接口**可显著降低成本（大规模非实时文本处理）。

> **架构含义**：法务知识库检索**应使用 `dense&sparse` 混合检索**。原因很实在：法务检索有两种截然不同的意图——"《广告法》第九条第几款"是**精确关键词**需求（稀疏向量强），"绝对化用语的合规边界"是**语义**需求（稠密向量强）。只做稠密检索会漏掉条款号精确匹配。

**多模态向量**

| 模型 | 维度 | 文本限制 | 图片限制 | 视频限制 | 单价 |
| --- | --- | --- | --- | --- | --- |
| `tongyi-embedding-vision-plus` | 1152 | 1,024 token | ≤3MB，最多 8 张 | ≤10MB | 图/视频 $0.09，文本 $0.09 |
| `tongyi-embedding-vision-flash` | 768 | — | — | — | 图/视频 $0.03，文本 $0.09 |
| `qwen3-vl-embedding`（北京） | 2560 默认 / 2048 / 1536 / 1024 / 768 / 512 / 256 | 32,000 token | **最多 1 张且 ≤5MB** | ≤50MB | 图/视频 $0.258，文本 $0.1 |

- `qwen3-vl-embedding` 同时支持**独立向量**与**融合向量**（`enable_fusion=true`）。
- 多模态向量仅支持 DashScope SDK/API，**不支持 OpenAI 兼容接口**（`qwen3-vl-embedding` 的融合向量甚至不支持 Java SDK，需走 HTTP）。

> **架构含义（本项目一个高价值能力）**：**多模态向量可用于"相似物料检索"**——例如拿一张新海报去检索历史上的相似海报及其审核结论。这对 `AGENTS.md` 第 10 条要求的"历史审核案例"检索能力，是纯文本检索做不到的，应作为知识库的一个独立能力规划。

**重排序（Rerank）**

| 模型 | 最大文档数 | 单条最大 Token | 单次请求最大 Token | 适用 |
| --- | --- | --- | --- | --- |
| `qwen3-rerank` | 500 | 4,000 | 120,000 | 语义文本搜索、RAG（100+ 语言） |
| **`qwen3-vl-rerank`** | 文本 100 / **图片 40** / **视频 4** | 8,000 | 120,000 | **多模态搜索结果重排序** |
| `gte-rerank-v2` | 500 | 4,000 | 30,000 | ⚠️ **2026-05-30 下线，勿用** |

- `qwen3-rerank` 支持 `instruct` 英文指令切换策略：**问答检索**（默认，找答案）vs **语义相似度**（FAQ 场景）。
- 官方建议的典型 RAG 流程：**Embedding 检索 50–100 候选 → Rerank 筛 Top 5–10 → 送入 LLM**。
- 端点：OpenAI 兼容 `/compatible-api/v1/reranks`；DashScope `/api/v1/services/rerank/text-rerank/text-rerank`。多模态 rerank **不支持 OpenAI 兼容接口**。
- ⚠️ 注意 `gte-rerank-v2` 已下线，**若沿用旧代码示例会直接失败**。

### 2.4 成本与限流的关键约束

| 约束 | 事实 | 架构应对 |
| --- | --- | --- |
| **上下文缓存覆盖不全** | `qwen3-vl-8b-thinking`、`qwen3.5-ocr`、`qwen-vl-ocr` 均**不支持** | 不能依赖缓存省成本，**改用 Batch** |
| **Batch 折扣** | `qwen-vl-ocr` Batch File 输入 $0.022 vs 实时 $0.043，输出 $0.036 vs $0.072 | 批量初审走 Batch，**成本约减半** |
| **地域性能差异巨大** | `qwen3-vl-8b-thinking` 北京 RPM 600 / 新加坡 RPM 60 | **锁定华北2（北京）地域** |
| **OCR 吞吐极高** | `qwen-vl-ocr` / `qwen3.5-ocr` 北京 RPM 6,000、TPM 30,000,000 | OCR 不是瓶颈，可放心批处理 |
| **Embedding 批次小** | 批次 ≤10 条，单条 ≤8,192 token（v4） | 知识库入库需分批任务化，不能一次灌入 |
| **轮询易限流** | 异步 ASR 查询接口 20 QPS（最高 100） | 用 EventBridge 回调（**必须验签**） |
| **结果 URL 时效** | `transcription_url` 24 小时有效 | 及时落盘 MinIO，并做"未落盘"告警 |

### 2.5 与 DeepSeek 的对比（选型依据留档）

早前已核实 DeepSeek 能力，作为"为什么单靠它不够"的依据留档：

| 能力 | DeepSeek | 千问（百炼） |
| --- | --- | --- |
| 图像理解 | ✅ 仅 `deepseek-flash`（`deepseek-v4-pro` 不支持图像） | ✅ 全系 Qwen-VL |
| 原生视频输入 | ❌ | ✅ |
| **文件原生输入（PDF/Office）** | ❌ Files API 仅收图片（JPEG/PNG/GIF/WebP） | ✅ |
| **OCR（文本定位）** | ❌ 无专用模型、不返回坐标 | ✅ `qwen-vl-ocr` / `qwen3.5-ocr` |
| **ASR** | ❌ 完全缺失 | ✅ 句级/字级时间戳，≤12h |
| **Embedding** | ❌ 缺失（RAG 检索层无法落地） | ✅ 文本 + 多模态 |
| **Rerank** | ❌ 缺失 | ✅ 文本 + 多模态 |
| 私有化 | ❌ | ✅ 一体机方案 |
| 成本 | flash 缓存命中价极低（$0.02–0.04/百万量级） | Batch 半价；缓存覆盖不全 |

> **结论**：DeepSeek 在"读图 + 文本推理"两段有价格优势，但**缺的四层（OCR/ASR/Embedding/Rerank）恰好是本项目定位能力的全部地基**，必须自建或另接供应商。**单一千问供应商是更简洁且能力完整的选择。** 架构上仍保留 Provider 抽象（§7.1），使未来替换或补充供应商不需要改动业务代码。

### 2.6 待实测验证的关键假设（不可跳过）

以下能力来自文档描述，**必须在 M0 阶段用真实物料做小样本实测**，不能直接进入设计假设：

| # | 待验证 | 为什么关键 | 验证方法 |
| --- | --- | --- | --- |

| V3 | **`qwen3-vl` 视觉 2D 定位的实际输出形态与稳定性** | 决定画面类风险能否自动定位 | 用海报/视频帧测试 grounding 输出 |

| V7 | **`qwen-vl-rerank` 对"相似海报"检索的实际效果** | 决定历史案例检索是否可用多模态 | 用历史审核过的海报构造召回集，测 Top-5 命中率 |

> **纪律要求**：V1–V5 未验证前，**不得开始反馈区风险定位界面的开发**——因为锚点契约会变，界面必然返工。

### 2.7 能力声明的时效性（运维要求）

本文 §2 的模型清单与能力矩阵是 **2026-09 的核实快照**。供应商迭代很快（千问在数月内已从 GLM/Qwen3 演进到 Qwen3.5-OCR、qwen3.7-text-embedding 等新版本），因此：

1. **每季度复核一次** §2.1–§2.3 的模型清单与能力矩阵，核对是否有新模型、新能力（尤其"结构化输出/Batch/上下文缓存"三项支持情况的变化）或下线公告。
2. **下线公告必须触发排查**。已有先例：`gte-rerank-v2` 于 2026-05-30 下线，若代码沿用它会在某天突然全部失败。所有 `model_id` 都应记录在配置中，便于一次性检索替换。
3. **模型替换必须走回归评测**：高风险召回率不得下降，否则不予切换（见 `03` §12.3）。
4. **锁定快照版本号**用于生产，避免 `-latest` 类动态别名导致行为漂移。`qwen-vl-ocr` 等价于快照 `qwen-vl-ocr-2025-11-20`，生产建议直接固定快照名。

## 3. 核心抽象：证据锚点（Evidence Anchor）

这是整个技术方案的地基，也是本方案与"把整份材料丢给大模型、让它直接返回风险"的朴素做法之间最大的区别。

### 3.1 要解决的问题

模型能说出"这里宣称行业第一"，但**不能可靠地给出像素坐标**。两条朴素路径都有硬伤：

- **让模型直接输出 bbox**：坐标与图片缩放比例强耦合，重采样即全错；且无法校验，错了也看不出来。
- **拿模型输出的风险原文去 OCR 结果里做字符串匹配**：模型可能改写原文（正常化、补标点、纠错）导致匹配失败；同一句在多处出现时定位歧义；匹配失败只能静默降级，风险就此"丢失位置"。

### 3.2 方案

**解析阶段为每个物料版本生成一批不可变、带稳定 ID 的锚点；模型只被允许引用锚点 ID。**

```
解析产物（持久化、不可变）
  ├─ anchor_id      稳定标识，可校验、可查表
  ├─ anchor_type    TEXT_LINE | SPEECH_SENTENCE | SUBTITLE_LINE
  │                 | KEY_FRAME | DOC_PARAGRAPH | DOC_SENTENCE
  ├─ locator        类型相关位置信息（见下表）
  ├─ text           锚点文本
  └─ source_engine + engine_version   OCR/ASR 引擎与版本，可追溯
```

| anchor_type | locator 内容 | 用途 | 来源 |
| --- | --- | --- | --- |
| `TEXT_LINE` | `bbox` + `polygon`(可选) + `image_width/height` + **`scale_ratio`** | 图片文字框选 | OCR 文本定位 |
| `SPEECH_SENTENCE` | `begin_ms` + `end_ms` + `speaker_id`(可选) | 视频口播定位 | ASR `sentences[]` |
| `SUBTITLE_LINE` | `begin_ms` + `end_ms` + `bbox` | 视频硬字幕定位 | 抽帧 + OCR |
| `KEY_FRAME` | `ts_ms` + `scene_id` + `object_key` | 视频画面风险 | 场景检测抽帧 |
| `DOC_PARAGRAPH` | `page_no` + `para_index` + `char_range` | 文档段落定位 | 文档解析 |
| `DOC_SENTENCE` | `page_no` + `para_index` + `sentence_index` + `char_range` | 文档句子级（最细） | 文档解析 |

> ⚠️ **定位粒度必须按格式如实承诺**：**DOCX 无法提供真实页码**——Word 的分页在渲染期决定，文件本身不存页码（依据 ISO/IEC 29500-1 对 `w:lastRenderedPageBreak` 的定义，以及 python-docx 官方说明该标记 never inserted）。因此 **DOCX 只承诺"段落/run 级"，`page_no` 字段必须允许为空**，界面文案统一为"定位到段落"而非"定位到页面"。若需求或原型写了"DOCX 跳到第 N 页"，**需先改需求**。详见 `06` §3。

### 3.3 四条硬约束

1. **坐标基准必须与送模型的图片完全一致。** OCR 与送 VLM 的必须是**同一张、同尺寸**图片。若 OCR 在原图、VLM 看缩放图，坐标必然错位。**落地要求：流水线先确定"送模型尺寸"，再在其上做 OCR，并把 `scale_ratio` 落库**，前端渲染时按同一比例还原。
2. **锚点在版本内不可变。** 版本变更生成新锚点集，**旧锚点必须保留**，否则历史 Risk Case 的位置引用会指向错误内容。
3. **模型只输出 `evidence_anchor_ids: [string]`。** 服务端逐个校验 ID 必须存在于该版本的锚点集内。**校验失败 = 该风险定位无效 → 强制转待人工判断并记录原因，不得静默丢弃、不得猜测坐标。**
4. **画面类风险（无对应文字）**：模型输出 `region_hint`（枚举 `TOP_LEFT`…`BOTTOM_RIGHT`、`FULL_FRAME`）+ `visual_description`，映射到粗粒度区域。**界面必须如实标注为"大致区域"，不承诺像素级精度。**

### 3.4 为什么这个抽象值得

- **定位从"猜"变成"查表"**，可 100% 校验，错了能发现——这对法务系统的审计要求是决定性的。
- **一套抽象覆盖四类物料**（图片/视频/文档/纯文本），前端只需一个"按锚点渲染高亮"的组件族。
- **天然支撑 Version Diff**：两版锚点集按 `text` 与 `locator` 对齐即可产出差异。
- **可审计**：Risk Case 存的是锚点 ID，任何时候都能回溯到"当时看到的那张图那行字"。
- **锚点覆盖率可作质量指标**：无锚点的风险占比过高，说明解析质量不足（如小字漏识），应触发告警而非静默通过。

### 4.1 选型

| 部署 | Docker Compose（内网） | 需内网出口或代理访问百炼 |

### 4.2 一个必须提前决策的架构分叉：解析放 Java 还是 Python

千问提供的是**云端 API**，这意味着"解析"不再必然需要本地引擎。两种路线：

| 路线 | 做法 | 优点 | 代价 |
| --- | --- | --- | --- |
| **A. 纯 API 路线（推荐起步）** | Java 直接调百炼：OCR 模型出文字+坐标、ASR 出时间戳、视觉模型做画面理解。本地只需 ffmpeg 抽帧 | **不需 Python 服务、不需 GPU、交付最快**；OCR/ASR 精度由阿里维护 | 物料原件必须出内网到百炼；持续 API 费用 |
| **B. 本地解析路线** | 本地部署 PaddleOCR / FunASR 出坐标与时间戳，仅推理走 API | 原件不出内网 | 需 Python 服务 + GPU/CPU 算力 + 运维；精度需自己调 |
| **C. 混合** | OCR/ASR 走 API（元件出网），仅把"已提取文本+帧"送推理 | 平衡 | 仍需出网，只是出网内容更少 |

> **建议：A 起步，保留切 B/C 的能力。** 理由：项目当前最大的风险是**交付周期**，不是数据外流（企业内网到阿里云的调用在多数企业是可接受的，且百炼是企业级服务）。**但必须在 M0 阶段由法务/安全部门书面确认物料可否上传到百炼**——这是阻塞项（§9 A3）。
>
> **架构上必须让路线可切换**：定义 `ParsePort` 接口（OCR/ASR/文档解析三组方法），API 路线与本地路线是两套实现。**禁止业务代码直接调用百炼端点**，否则将来切换要全量改动。

## 5. 四模块职责矩阵与边界守卫

`AGENTS.md` 反复强调"不得为了页面丰富而在多个模块重复实现相同的核心流程"。因此把边界写成**可检查、可测**的表。

### 5.1 职责与禁止项

| 模块 | 核心职责 | **明确禁止**（代码层守卫） |
| --- | --- | --- |
| **AI 法务助手** | 单条咨询、临时单图/单文案分析、页面内 Copilot、解释风险、生成沟通话术 | 禁止创建正式 Case；禁止批次审核；禁止产出批次通过率；禁止写 Risk Case 状态；禁止终审/签名/关闭。**守卫：该模块 API 无任何写 `risk_case.status` 的权限（方法级 + DB 层双重）** |
| **接收区** | 建 Case、批量上传、解析、审核要求、启动 AI 初审 | 禁止展示最终风险结论；禁止生成正式报告；禁止处理整改版本；禁止审批。**守卫：接收区 API 不返回 risk_case 明细，只返回解析状态与物料清单** |
| **反馈区** | 第一次全量初审、三分类、Risk Case 定位与人工判断、Markdown 初审报告 | 禁止管理 V1/V2/V3；禁止 Version Diff；禁止最终审批/签名/关闭。**守卫：状态机不允许 Feedback 阶段跃迁到 `Closed`；反馈区 API 不暴露 version 创建接口** |
| **终审区** | 已确认 Risk Case 的整改、版本链、Diff、AI 复审、法务终审、签名、关闭 | 禁止重新全量初审。**守卫：复审请求强制携带 `review_scope`，服务端拒绝 `scope=FULL`** |

### 5.2 「转为正式审核任务」的正确实现

AI 法务助手 → 接收区是**唯一**允许的跨模块流转，且必须是"预填充 + 用户确认"，不能直接创建：

```
助手分析结果 ──► [转为正式审核任务] ──► 接收区新建页（预填审核要求 + 带入临时上传文件）
                                          └─► 用户确认 ──► 才真正创建 Case
```

**禁止**助手一键直接落库成正式 Case。理由：正式审核任务的创建必须由人明确确认，否则会污染正式审核台账与通过率统计口径。

### 5.3 边界冲突处理原则

若后续需求要求两个模块承担同一核心职责（例如"在接收区也显示风险结论"），**不得直接照做**，应指出重复点并按「助手管问题、接收管任务、反馈管初审、终审管风险闭环」提出归属建议。

## 6. 端到端主链路

严格对应 `AGENTS.md` 第 14 条的优先顺序。

```
[接收区] ①建 Case ─► ②批量上传 Material ─► ③异步解析
                                              ├ OCR(文字+坐标) ─► TEXT_LINE 锚点
                                              ├ ASR(句/字时间戳) ─► SPEECH_SENTENCE 锚点
                                              ├ 抽帧+场景检测 ─► KEY_FRAME 锚点
                                              ├ 硬字幕 OCR ─► SUBTITLE_LINE 锚点
                                              └ 文档解析 ─► DOC_* 锚点
                            │
                            ├─ 解析失败 ─► 阻止进入初审，明确告知重传/补充什么（不计入分母）
                            ▼
[接收区] ④设置审核要求（模板需人工确认后生效）─► ⑤点击「开始 AI 初审」
                            ▼
[反馈区] ⑥AI 全量初审：候选风险识别(宽召回) ─► 混合检索(dense+sparse) ─► Rerank
                        ─► 风险判断 ─► 结构化输出 ─► 锚点ID校验
                            ▼
        ⑦生成 Risk Case（每个独立问题一条）+ 物料三分类 + Markdown 初审报告
                            ▼
[反馈区] ⑧法务逐条操作：确认风险 / 标记误判(留理由) / 要求补充材料 / 转入整改
                            ▼
[终审区] ⑨上传新 Version(V2) ─► ⑩Version Diff ─► ⑪AI 复审三问 ─► ⑫法务终审 + 签名 + 关闭
                            ▼
        ⑬物料所有阻断性风险关闭 ─► 标记最终批准版本（绑定精确 version_id + 哈希）
```

**反向可追溯验收**：从最终批准版本能反查全部 Risk Case 与 Review Record；从任一 Risk Case 能找到最初物料、各次修改版本、最终批准信息。详见 `05`。

## 7. AI 能力编排策略

### 7.1 Provider 抽象（强制要求）

**定义 `AiProvider` 与 `ParsePort` 两组接口，业务代码不得直接调用百炼端点。**

```java
// 文本推理（可替换供应商）
interface TextInferencePort {
    StructuredRiskDraft judge(RiskJudgeRequest req);   // 风险判断
    String generateReport(ReportRequest req);          // 报告/话术生成
}

// 多模态理解（图/视频帧）
interface VisionPort {
    VisualUnderstanding understand(VisionRequest req);  // 语义理解 + 视觉定位
}

// 解析（路线 A 走百炼，路线 B 走本地，可切换）
interface ParsePort {
    OcrResult      ocr(OcrRequest req);          // 文字 + 坐标 + 置信度
    AsrResult      asr(AsrRequest req);          // 句/字级时间戳
    DocumentResult parseDocument(DocRequest req);
}

// 检索（法务知识库）
interface RetrievalPort {
    List<Hit> embedSearch(String query, int topK);   // dense + sparse 混合
    List<Hit> rerank(String query, List<Hit> cands); // qwen3-rerank
    List<Hit> multimodalSearch(MediaRef ref, int topK); // qwen3-vl-embedding / rerank
}
```

所有调用记录 `model_id` 落库。**禁止在业务代码里硬编码模型名**，否则后续换型号需全量回归。

### 7.2 模型分工矩阵

| 阶段 | 模型 | 理由 |
| --- | --- | --- |
| 图片文字提取（含坐标） | **`qwen-vl-ocr`（Batch，成本优先）** + `qwen3.5-ocr`（质量兜底） | 专用 OCR 模型，具备文本定位 |
| 图片/关键帧语义理解 | `qwen3-vl-8b-thinking`（北京） | 视觉 2D/3D 定位、空间感知；RPM 600 |
| 视频口播转写 | **`qwen3-asr-flash-filetrans`** | 句级/字级时间戳，≤12h/2GB |
| 视频硬字幕 | 抽帧 + `qwen-vl-ocr` | 复用 OCR 能力 |
| 文档解析 | `qwen-vl-ocr` / `qwen3.5-ocr`（扫描件）+ 文本层提取 | 混排需双路 |
| 候选风险识别（宽召回） | 文本主力模型（型号按 V6 锁定），低成本档 | 允许含噪声 |
| 风险判断（收紧） | 文本主力模型，高能力档 | 需引入"低置信度+高影响→人工"规则 |
| 初审报告 / 沟通话术 | 文本主力模型，高能力档 | 长文生成质量 |
| 知识库向量化 | `text-embedding-v4` @1024 维，`output_type=dense&sparse` | CMTEB 70.14，混合检索 |
| 检索重排 | `qwen3-rerank`（+ `qwen3-vl-rerank` 做图文案例） | 50–100 候选 → Top 5–10 |
| AI 法务助手 | 含图/视频 → `qwen3-vl`；纯文本 → 文本主力模型 | 按输入是否含媒体分流 |

### 7.3 审核流水线（五阶段）

对应 `AGENTS.md` 第 11 条「内容解析 → 候选风险识别 → 规则与证据检索 → 风险判断 → 结构化输出」。

| 阶段 | 输入 | 输出 | 说明 |
| --- | --- | --- | --- |
| 1 内容解析 | 原件 | 锚点集 + 解析文本 + 派生图 | OCR/ASR/文档解析 + 视觉语义 |
| 2 候选风险识别 | 解析文本 + 锚点清单 + 审核要求 | 候选风险列表 | **宽召回，宁多勿漏** |
| 3 规则与证据检索 | 候选风险 | 命中的 rule_id + 证据 + Approved Claims | dense+sparse 检索 → rerank |
| 4 风险判断 | 候选 + 依据 + 产品参数 | 风险等级 / 置信度 / 推荐状态 / 理由 | 引入人工判断触发规则 |
| 5 结构化输出 | 判断结果 | 经校验的 Risk Case 草稿 | 服务端 Schema 校验 + 锚点校验 |

**为什么拆 5 阶段而不是一次问完**：
- 阶段 2 与阶段 4 目标相反（宽召回 vs 低误报），合成一次会互相污染；
- 阶段 3 的检索必须**独立可审计**（用了哪些法条、哪个版本），合进生成过程就无法回答"依据从哪来"；
- 阶段 4 才引入"低置信度 + 高影响 → 优先人工"（`AGENTS.md` 第 11 条），需要独立打分。

**阶段 2 必须宽召回**：`AGENTS.md` 第 15 条明确"涉及高风险漏检的测试应优先于文案风格优化"。宁可多出待人工判断，不可漏。

### 7.4 三条解析管线

**图片**
```
原件 ─► ① 格式识别（按内容而非扩展名）
      ─► ② 尺寸规范化，记录 scale_ratio
      ─► ③ 在【规范化后图片】上跑 OCR ─► 文字 + bbox + 置信度 + line_id
      ─► ④ 同一张规范化图片送视觉模型做语义理解（人物/场景/道具/呈现方式）
      ─► ⑤ 合并锚点集
```
**③ 与 ④ 必须基于同一张图**，否则坐标错位（§3.3 约束 1）。送视觉模型的 prompt 中**携带 OCR 行清单（含 line_id）**，使模型能直接引用行号——这比让它描述文字再回头匹配可靠得多。

**视频**
```
视频 ─► ① ffmpeg 抽音轨 ─► ASR(句/字级时间戳) ─► SPEECH_SENTENCE 锚点
     ─► ② 场景检测 + 关键帧抽取 ────────────────► KEY_FRAME 锚点
     ─► ③ 硬字幕区域 OCR（带时间戳）──────────► SUBTITLE_LINE 锚点
     ─► ④ 关键帧送视觉模型做画面语义 ───────────► 画面风险候选
     ─► ⑤ 三轨对齐到统一时间轴（ms）──────────► 可定位到 [begin_ms, end_ms]
```
**"口播与字幕不一致"本身就是风险信号**，因此三轨必须是独立锚点类型、可被同一条 Risk Case 同时引用——这也是把它们分开建模而非合并成一段文本的原因。

**文档**
```
PDF/PPTX/DOCX ─► ① 判定是否含文本层
                 ├─ 含文本层 ─► 抽取文字 + 页码/段落/句子锚点
                 └─ 扫描件   ─► 页面渲染为图 ─► OCR（行 + bbox）─► 锚点
              ─► ② 图片/图表区域单独送视觉模型做语义理解
              ─► ③ 合并锚点集（DOC_PARAGRAPH / DOC_SENTENCE）
```
**混排场景**（PPT 一页多图 + 文字）必须同时走文本层与图片理解，否则会漏掉"图片里的宣传语"——这是广宣物料最常见的形态之一。

### 7.5 成本控制

| 手段 | 机制 | 预期效果 |
| --- | --- | --- |
| **Batch 批量推理** | OCR 走 Batch File 接口 | 输入 $0.043→$0.022，输出 $0.072→$0.036，**约减半** |
| **专用小模型分工** | OCR/ASR 用专用模型，不用旗舰多模态硬扛 | OCR 输出 $0.072–0.275/百万量级，远低于旗舰 |
| **分辨率策略** | OCR 保持高分辨率（小字漏识 = 高风险漏检） | 不省这个钱，见 ADR D-11 |
| **检索层收口** | 先检索 50–100 候选 → rerank Top 5–10 再送 LLM | 显著压缩送入 LLM 的 token |
| **地域锁定** | 华北2（北京） | RPM 600 vs 新加坡 60，吞吐差 10 倍 |

**成本必须可观测**：记录每次调用的模型、阶段、输入/输出 token、Batch 与否，并按 Case 归集。**注意不能依赖"缓存命中率"做监控**——关键模型不支持上下文缓存。

**"经济队列"设计（可选，需用户决策 A4）**：批量初审默认走 Batch 异步，意味着**提交后不立即出结果**。因此：
- 必须提供 `标准队列`（实时调用，全价，快）/ `经济队列`（Batch，半价，慢）两个选项；
- 界面必须**明确告知预计出结果时间**，不能让用户干等；
- 默认建议标准队列，经济队列由用户主动选择。

### 7.6 幂等与去重（防止重复 Risk Case）

需求明确要求"避免同一文件或同一任务因重复提交而创建重复 Risk Case"。三层防护：

1. **文件层**：SHA-256 哈希唯一索引。同一文件重复上传 → 复用已有 Material/Version，不新建。
2. **任务层**：幂等键 `case_id + material_id + version_id + pipeline_version + prompt_version + ruleset_version + model_id`。同键的初审请求只执行一次，重复提交返回已有结果。
3. **风险层**：`risk_dedup_key = version_id + risk_type + 主锚点ID + 归一化风险原文哈希`。同键风险合并（保留最高置信度与全部锚点），不重复建单。

**⚠️ 版本三件套（`pipeline_version` / `prompt_version` / `ruleset_version`）必须落库。** 它同时解决三件事：幂等键稳定性、审计可复现性（`AGENTS.md` 第 12 条）、以及模型升级后"为什么同一份材料这次判得不一样"的可解释性。缺了它，历史结论无法解释。

### 7.7 失败处理

| 失败 | 处理 |
| --- | --- |
| 解析失败 / 文件损坏 | **阻止进入正式初审**，明确告知重传或补充什么（`AGENTS.md` 第 4 条）；**不计入通过率分母，单独列出** |
| ASR 结果 URL 过期未落盘（24h） | 判定为解析失败，需重跑；**必须提前告警**，不能到期才发现 |
| OCR/ASR 返回 JSON 格式抖动（不支持结构化输出） | 服务端容错解析 + 有限重试；仍失败 → 转待人工判断并标注"解析结果未通过校验"，**绝不静默丢弃** |
| Schema 校验失败 | 视为一次无效调用并重试；连续失败降级为「待人工判断」 |
| 锚点 ID 不存在 | 该风险定位标为无效，转待人工判断，记录原因 |
| 429 / 限流 | 指数退避 + 抖动；队列层全局令牌桶，避免打满账号限额 |
| 回调伪造风险 | **必须校验 `X-Eventbridge-Signature*`**，并按 `task_id` 幂等去重 |

**统一原则**：任何 AI 环节失败都**降级为「待人工判断」，绝不降级为「通过」**。这是安全方向的强制选择——`AGENTS.md` 第 11 条明确"不能为了完成流程编造确定答案"。

## 8. 架构决策记录（ADR）

| # | 决策 | 备选 | 选择理由 | 代价 |
| --- | --- | --- | --- | --- |
| D-01 | 模型只引用**证据锚点 ID**，不输出坐标 | 模型直出 bbox / 事后字符串匹配 | 可校验、可审计、跨物料统一；避免模糊匹配静默失败 | 需先建解析锚点层，前期工作量增加 |
| D-02 | **单一千问供应商**，不引入第二家 | 双供应商 / DeepSeek+千问 | 千问一家覆盖解析+检索+推理全链路；DeepSeek 缺 OCR/ASR/Embedding/Rerank 四层地基 | 单点依赖；但 Provider 抽象保留切换能力 |
| D-03 | **解析走云端 API（路线 A）起步** | 本地 OCR/ASR | 交付最快，不需 Python 服务与 GPU，精度由阿里维护 | 物料原件出内网，**需安全部门书面确认（A3）** |
| D-04 | OCR 用**双模型策略**：`qwen-vl-ocr`(Batch) 默认 + `qwen3.5-ocr` 质量兜底 | 只用其一 | 前者支持 Batch 单价减半，后者定位能力更新；兼顾成本与质量 | 需实现"质量判定 + 重跑"逻辑 |
| D-05 | 结构化输出**不依赖 `response_format`**，一律服务端 Schema 校验 | 全靠 JSON 模式 | OCR 模型明确不支持结构化输出；服务端校验是唯一可靠路径 | 需实现完整校验层与容错解析 |
| D-06 | 检索用 **dense+sparse 混合** + rerank | 纯稠密向量 | 法务检索兼具"条款号精确匹配"与"语义理解"两种意图，纯稠密会漏条款号 | 需向量库支持稀疏向量，存储上升 |
| D-07 | **锁定华北2（北京）地域** | 新加坡/其他 | RPM 600 vs 60，TPM 1M vs 100K，吞吐差 10 倍 | 数据存储地域受限，需确认合规 |
| D-08 | AI 失败一律降级为**待人工判断** | 降级为通过 / 静默跳过 | 安全方向正确；呼应"不得编造确定答案" | 待人工比例上升，法务工作量增加 |
| D-09 | 权限三处一致靠**DB 触发器兜底** | 只做前端隐藏 + 后端校验 | MySQL 无行级权限，触发器是唯一能让"数据库权限"真实生效的手段 | 迁移与调试复杂度上升 |
| D-10 | 版本三件套**落库** | 只存模型名 | 审计可复现、幂等键稳定、模型升级可解释 | 每次流水线调整需版本号管理纪律 |
| D-11 | 图片**不做省钱压缩**，反而保高分辨率 | 压缩省流量 | 小字漏识（免责声明）是最高等级的漏检风险 | 存储与带宽略增 |
| D-12 | ASR **必须用 Filetrans 异步接口** | 用 OpenAI 兼容接口 | 兼容接口**不返回时间戳**，无法定位，功能直接不成立 | 需实现异步任务 + 回调/轮询 |
| D-13 | 终审区复审**强制携带 review_scope** | 无约束 | 防止终审区退化为第二次全量初审（`AGENTS.md` 第 7 条） | 需在服务端做 scope 校验 |
| D-14 | 保留 `ParsePort` 抽象，支持切本地解析 | 直接调 API | 若安全部门否决出网，需能快速切路线 B | 多一层接口与两套实现 |

## 10. 风险登记册

| 风险 | 等级 | 影响 | 缓解 |
| --- | --- | --- | --- |
| 安全部门否决物料出网 | **高** | 需切路线 B，工期显著增加 | A1 前置确认；保留 `ParsePort` 抽象（D-14） |
| 内网无百炼出口 | **高** | 项目无法交付 | A3 前置确认 |
| OCR 小字漏识导致免责声明漏检 | **高** | 高风险漏检，直接违反审核目标 | 保持高分辨率；OCR 置信度低的行降低 AI 置信度；免责声明区域定向检测；锚点覆盖率纳入质量指标 |
| OCR 文本定位格式/精度不足（V1/V2） | **高** | 图片风险框选能力不成立 | **M0 实测前置**；不达标则叠加本地 OCR 交叉校验；画面类风险降级为"大致区域"+ 人工框选 |
| ASR 结果 24h 未落盘 | 中 | 需重跑并重复计费 | 落盘任务 + 到期告警 |
| 回调事件被伪造注入 | 中 | 虚假识别结果进入审核链路 | **强制校验 `X-Eventbridge-Signature*`** + task_id 幂等 |
| 不支持结构化输出导致解析抖动 | 中 | 解析失败率上升 | 服务端容错解析 + 重试 + 降级为待人工 |
| 关键模型不支持上下文缓存 | 中 | 无法用缓存压成本 | 改走 Batch（D-04）；成本监控按 token 而非缓存命中率 |
| 同名 `end_time` 字段误用 | 中 | 时间定位错乱，且难以发现 | 类型层面隔离（`Instant` vs `long`）+ 单元测试覆盖 |
| 待人工判断比例过高 | 中 | 法务工作量不降反升 | 纳入效果指标（`AGENTS.md` 第 15 条）；宽召回后必须评估人工负担 |
| 地域选错导致限流 | 中 | 吞吐差 10 倍 | 锁定北京（D-07） |
| 模型升级导致历史结论不可解释 | 中 | 审计缺陷 | D-10 版本三件套落库 |
| Batch 时延不可控 | 低 | 用户等待超预期 | A4 决策；界面如实展示预计时间 |
| **基础组件许可证问题（Redis 8 的 SSPL/AGPL）** | 中 | 合规风险，可能被迫返工替换 | 锁定 **Redis 7.2.x（BSD-3）**；CI 校验镜像 tag（`06` §2.1） |
| 云 API 要求文件公网可达 | 中 | 无法用 VPC 内网规避"物料出网" | 短期签名 URL + 任务结束即删对象；A1/L2 前置确认 |
| DOCX 无法定位到页码 | 低 | 产品承诺与实现不符 | 界面与需求统一改为"定位到段落"（`06` §3） |

## 11. 验收主线（详见 `05`）

主链路必须一次性走通，且每一步留痕：

```
建 Case → 上传(图片/视频/PPT/PDF/Word/纯文本各≥1) → 解析(含位置映射)
→ AI 初审 → 生成 Risk Case（单文件多风险 ≥3 条）→ 法务确认/误判/补料
→ 进入整改 → 上传 V2 → Version Diff → AI 复审(三问) → 法务终审
→ 签名 → 关闭风险 → 标记最终批准版本
```

**必须同时验证的反向追溯**：
- 从最终批准版本 → 反查全部 Risk Case 与 Review Record
- 从任一 Risk Case → 找到最初物料、各次修改版本、最终批准信息
- **从批准记录 → 还原"批准时看到的准确版本"（哈希一致），而非一个可能被覆盖的地址**

**必须通过的异常路径**：单文件多风险、多文件同类风险、缺少证明材料、AI 误判、解析失败、重复提交不重复建单、版本无变化、原风险已解决但出现新增风险、并发修改、无权限审批被拒（**且必须接口层与 DB 层同时拒绝**）。
