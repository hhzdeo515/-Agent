## 1. 实施总原则

### 1.1 唯一优先级判据

依据 `AGENTS.md` 第 14 条：

> **端到端主链路优先于一切增强能力。**

主链路的完整定义（`00` §6、§11）：

```
[接收区] 建 Case → 批量上传 Material → 异步解析（含锚点）
        → 设置审核要求（模板须人工确认后生效）→ 开始 AI 初审
[反馈区] AI 全量初审 → 生成 Risk Case（每个独立问题一条）+ 三分类 + 初审报告
        → 法务逐条：确认风险 / 标记误判 / 要求补充材料 / 转入整改
[终审区] 上传 V2 → Version Diff → AI 复审三问 → 法务终审 → 签名
        → 关闭风险 → 标记最终批准版本
```

**在主链路一次性走通（即第 4 章 E2E 剧本全部通过）之前，下列内容一律不排期**：

| 冻结项 | 冻结依据 |
| --- | --- |
| 统计看板、报表中心、多维分析 | 第 14 条明确"统计看板可在主链路稳定后迭代" |
| 体验优化类需求（动效、批量快捷操作、自定义主题、消息中心美化） | 同上 |
| 知识库高级检索能力（多模态相似物料检索、跨项目案例推荐） | 第 14 条"知识库增强可后置"；且 `qwen3-vl-rerank` 效果本身待 V7 验证 |
| AI 法务助手的高级能力（多轮上下文、话术模板库、历史案例推荐排序） | 助手是最轻量的模块，价值密度低于主链路 |
| 移动端适配、国际化 | 需求未提及 |

### 1.2 三条不可违反的实施纪律

| # | 纪律 | 依据 | 违反后果 |
| --- | --- | --- | --- |
| **R1** | **V1–V5 未验证前，不得开始反馈区风险定位界面开发** | `00` §2.6 明文纪律 | 锚点 `locator` 契约会变，界面必然返工（高成本返工，非小改） |
| **R2** | **物料原件可否上传百炼（A1）未确认前，不得开始解析链路的生产级开发** | `00` §4.2、§9 A1、§10 | 若安全部门否决，路线 A → B 是全链路切换；`ParsePort` 抽象（D-14）只能降低、不能消除成本 |
| **R3** | **内网到百炼的出口（A3）未打通前，不得开始 M1 的联调** | `00` §9 A3、§10 | 无出口则所有模型相关任务全部阻塞，联调无法进行 |

## 2. 里程碑计划

### 2.1 M0：关键假设实测验证（必须先做，不可跳过）

#### 2.1.1 为什么 M0 不可跳过

`00` §2.6 列出的 V1–V8 全部来自**官方文档描述**，而非本项目实测。其中 V1–V5 直接决定两件事：

1. **锚点契约的字段结构**（`evidence_anchor.locator` 的 JSON 形状，见 `01` §6）；
2. **风险定位能力的上限**（图片能不能框到"免责声明"级别的小字；视频能不能定位到句；画面类风险能不能自动定位）。

**`00` §2.6 纪律要求原文**：V1–V5 未验证前，**不得开始反馈区风险定位界面的开发**——因为锚点契约会变，界面必然返工。

**M0 不是"技术预研"，是"契约冻结前的取证"。** 它的产出不是 demo，而是**冻结后的契约 + 样本库 + 决策记录**。

#### 2.1.2 M0 的组织方式

| 项 | 安排 |
| --- | --- |
| 时间盒 | **建议 2 周**（10 个工作日），**需按实际人力调整**；不建议超过 3 周，否则说明 A1/A3 前置结论未落地 |
| 人力 | AI 工程 1 人（主力）+ 后端 1 人（验证脚本与落库）+ 测试 1 人（样本标注与比对）+ 法务 0.3 人（样本标注与"可接受"判定） |
| 环境 | 百炼华北2 地域账号可用、内网出口已打通（**否则 M0 无法开始，回到 R3**） |
| 产出物 | ①《M0 实测报告》（含 V1–V8 每条的证据截图/原始 JSON）②`anchor_locator_contract.md`（冻结版契约）③M0 样本库与标注集 ④`model_id` 锁定清单 ⑤决策记录（每条 V 的"通过/切换方案"结论）⑥**薄验证原型**（仅用于验证，不进生产） |
| 不做 | 不产出生产代码；不做界面；不做性能优化 |

> **重要**：M0 的验证代码**必须**通过 `ParsePort` / `AiProvider` 抽象（`00` §7.1、D-14）编写。理由很实际——这份代码是将来路线切换的探针，如果直接调百炼端点，验证结论只能作废重写。

#### 2.1.3 V1–V8 逐条验证方案

> **关于通过标准的说明**：`00`/`01`/`02` 与 `AGENTS.md` 均未给出 V1–V8 的量化通过阈值。下表"通过标准"列中：
> - 凡带 **`待确认（需求未给定）`** 的数值，**必须由项目组在 M0 启动会上指定责任人并填入**（建议责任人：测试负责人 + 法务）；

##### V1｜OCR 的"文本定位"返回格式

| 项 | 内容 |
| --- | --- |
| **验证目标** | 确定 `qwen-vl-ocr` / `qwen3.5-ocr` 返回的文字位置字段的**准确形状**：是矩形 `bbox` 还是四边形 `polygon`？坐标是**归一化 0–1** 还是**像素**？坐标系原点在哪？是否返回行级置信度？一份结果能否区分"行/段/块"层级？ |
| **为什么关键** | 这一条**唯一决定** `01` §6 中 `TEXT_LINE.locator` 的字段结构。契约定错 → 全部锚点数据、全部风险定位引用、前端渲染组件族**全部返工**。 |
| **样本** | 3 类共 6 张：①标准印刷海报（横版，文字规整）②含倾斜/弧形文字的促销物料 ③竖版长图（高度 > 4000px，用于验证坐标基准与缩放的耦合）。每张均在**规范化尺寸**下处理（`00` §3.3 约束 1）。 |
| **方法** | 1. 对 6 张图各调用一次 `qwen-vl-ocr` 与 `qwen3.5-ocr`（**同一张、同尺寸**图，两张模型输入必须完全一致）；<br>2. **原文保存返回 JSON**（不加工、不解析），落 `parse_artifact.payload` + `raw_object_key`；<br>3. 逐字段对照官方文档，确认：坐标类型（整数像素 / 浮点归一化）、原点位置（左上 / 左下）、是否 0-based、是否有 `polygon`、是否有行号、是否有 `confidence`；<br>4. 用返回坐标在原图上**画出矩形**，人工视觉确认是否套住文字；<br>5. 用同一张图在**两个不同规范化尺寸**下各调一次，通过坐标比值反推坐标基准与 `scale_ratio` 的关系。 |
| **看什么输出** | 字段名清单、坐标数值量级（若是 0–1 之间浮点 ⇒ 归一化；若明显大于 1 且接近图宽 ⇒ 像素）、层级结构（`lines[]` / `blocks[]` / `words[]`）、`confidence` 是否存在。 |
| **通过标准** | ① 字段名与坐标语义**完全确定**，足以写出 `TEXT_LINE.locator` 的字段级 Schema；② 坐标套框人工确认**正确率 `待确认（需求未给定）`**（建议责任人：测试负责人，M0 启动会填入；本文件建议先按"抽查 60 行，错框 ≤ 3 行"评审）；③ 不同规范化尺寸下坐标可**确定性换算**（同一行文字两次坐标经 `scale_ratio` 换算后偏差 `待确认（需求未给定）`）。 |
| **不通过时的备选方案** | **备选 1（首选）**：改用本地 OCR（PaddleOCR / RapidOCR）出坐标——`docs/research/` 下已有中文 OCR 引擎调研的事实核实材料可直接复用；走 `00` D-14 的 `ParsePort` 路线 B，**只把图标出网、坐标本地出**。<br>**备选 2**：OCR 只出文字不出坐标，所有文字类风险**降级为 `region_hint` + 人工框选**，界面明确标注"大致区域"（`00` §3.3 约束 4 已允许这种降级）。<br>**备选 3**：双引擎交叉校验（云 + 本地），取交集提高可信度，成本上升。<br>**升级路径**：若 V1 与 V2 同时不通过 ⇒ 触发**项目级评审**，评估是否将 A1（物料出网）结论改为"仅文本出网"的路线 C。 |

##### V2｜OCR 坐标精度能否框准"免责声明"级别的极小字号

| 项 | 内容 |
| --- | --- |
| **验证目标** | 在真实广宣物料的极限尺寸下，OCR 能否**稳定识别并框准**小字免责声明。 |
| **为什么关键** | **漏框 = 高风险漏检**，这是项目最高等级的风险（`00` §10 风险登记册第一高危项："OCR 小字漏识导致免责声明漏检"）。免责声明恰恰是广宣审核中最常见的风险来源（`DISCLAIMER_MISSING`）。 |
| **样本** | 构造**极限尺寸文本测试集**，至少 12 张：①字号极小（相对图高占比 `待确认（需求未给定）`，建议先按"字高 ≤ 图高 1%"构造）②低对比度（浅灰字 / 深色底浅字）③被半透明蒙层或渐变遮挡 ④位于画面边缘（贴边、被裁切）⑤倾斜排版 ⑥艺术字体 ⑦中英混排小字 ⑧小字与背景花纹重叠。**必须包含至少 3 张来自真实历史广宣物料的免责声明截图**（脱敏后使用）。 |
| **方法** | 1. 每张图**先人工标注**"免责声明区域的真实文字与位置"作为 ground truth；<br>2. 调用两个 OCR 模型（`qwen-vl-ocr` 走 Batch、`qwen3.5-ocr` 走实时），各记录：是否识别出该行、识别文本与 ground truth 的字符级差异、框的 IoU；<br>3. **特别记录"完全漏识"的样本清单**——这是最高优先级缺陷；<br>4. 对漏识样本做**分辨率梯度实验**（`00` D-11：图片不做省钱压缩，反而保高分辨率）：在 2–3 档分辨率下重复，确认漏识是否由分辨率导致、提高到哪一档可解决；<br>5. 记录低置信度行（`evidence_anchor.confidence`）与"实际是否识别正确"的相关性，用于决定 `PENDING_LEGAL_DECISION` 的置信度触发阈值。 |
| **看什么输出** | 每张图的：识别行数、漏识行数、文本准确率、框 IoU、`confidence` 值；分辨率梯度下的识别率变化曲线。 |
| **通过标准** | ① **免责声明类小字漏识数 = 0**（在选定的分辨率策略下）——这是硬指标，不允许用平均值掩盖；<br>② 识别准确率（字符级）≥ `待确认（需求未给定）`（建议责任人：法务 + 测试，M0 启动会填入）；<br>③ 框 IoU ≥ `待确认（需求未给定）`（建议先按 IoU ≥ 0.7 评审）；<br>④ **确认一个"分辨率下限"**并写入 D-11 的实现细则：低于该值不得送 OCR。 |
| **不通过时的备选方案** | **备选 1（首选）**：**免责声明区域定向检测**——先用视觉模型定位"小字/免责声明区域"（`region_hint` 或视觉 2D 定位），对该区域**单独裁剪放大后再 OCR**，两段结果合并。<br>**备选 2**：本地 OCR 交叉校验（小字场景本地引擎常优于通用多模态）；<br>**备选 3**：界面提供**人工框选入口**，法务可手动补一个锚点，该锚点标记 `source_engine='MANUAL'`；<br>**兜底**：`00` §3.4 明确"锚点覆盖率可作质量指标"——**把"低置信度/无锚点风险占比"做成上线看板项与告警项**，而不是静默通过。 |

##### V3｜`qwen3-vl` 视觉 2D 定位的实际输出形态与稳定性

| **不通过时的备选方案** | **备选 1（首选）**：画面类风险统一走 `region_hint` 粗粒度区域（`00` §3.3 约束 4 已设计好）+ `visual_description` 文字描述，**界面如实标注"大致区域"，不承诺像素级精度**。<br>**备选 2**：把"视觉元素"尽量文本化——要求视觉模型先输出"画面中有哪些元素及其相对位置描述"，再由人工确认，把定位责任交回人；<br>**备选 3**：本地目标检测模型（若安全部门允许本地算力，见 A2）。 |

##### V5｜OCR/ASR 结果 JSON 的稳定性

| 项 | 内容 |
| --- | --- |
| **验证目标** | 量化"同一输入重复调用"时的**格式抖动率**：是否严格 JSON、字段是否漂移、字段类型是否变化、是否夹带 Markdown 代码块或自然语言前后缀。 |
| **为什么关键** | `qwen3.5-ocr` 与 `qwen-vl-ocr` **均不支持结构化输出（JSON 模式）**（`00` §2.1 表、D-05）。这意味着**服务端容错解析是唯一可靠路径**，不能依赖 `response_format`。抖动率直接决定"解析失败 → 转待人工判断"的比例，进而决定法务的实际工作量。 |
| **样本** | 选 3 张代表性图片 + 2 段音频（覆盖复杂排版、表格、多语言）。 |
| **方法** | 1. **同一输入重复调用 20 次**（图片两个 OCR 模型各 20 次；ASR 用 2 段音频各 20 次，注意 ASR 走异步、成本与耗时需预算）；<br>2. 每次记录：<br>　a. 是否为合法 JSON（`json.loads` 是否成功）；<br>　b. 是否被 ```json 代码块或自然语言包裹；<br>　c. 顶层字段名集合是否与首次一致（字段漂移）；<br>　d. 关键字段类型是否变化（如 `confidence` 从 number 变 string）；<br>　e. 数值型字段的格式（坐标是 int 还是 float、时间戳是否带单位后缀）；<br>3. 统计：**格式合法率、字段集合一致率、类型一致率**；<br>4. 用统计结果设计容错解析层（剥离代码块、字段别名映射、类型宽松转换）并**回放 20 份样本验证容错层有效**。 |
| **看什么输出** | 20 次原始返回的并排对比；抖动分类计数（非法 JSON / 包裹 / 字段缺失 / 字段新增 / 类型变化）。 |
| **通过标准** | ① 拿到**可量化的抖动率**（三类：格式、字段、类型）；<br>② 服务端容错解析层能把抖动样本**全部解析为合法结构**，或明确降级为"待人工判断并标注'解析结果未通过校验'"（`00` §7.7 要求：**绝不静默丢弃**）；<br>③ 抖动率若 > `待确认（需求未给定）`（建议责任人：AI 工程，M0 启动会填入），必须有明确的降级策略而非重试到底。 |
| **不通过时的备选方案** | **备选 1**：服务端容错解析 + **有限次重试**（重试次数 `待确认（需求未给定）`），连续失败降级为 `PENDING_LEGAL_DECISION`（`00` §7.7）；<br>**备选 2**：换用支持结构化输出的模型做**格式修复**（把抖动文本喂给支持 JSON 模式的模型做规范化）——注意这会增加一次调用成本；<br>**备选 3**：对 OCR 结果只取"文本 + 坐标"最小必要字段，放弃非必需字段，减少漂移面；<br>**兜底**：无论抖动率如何，**Schema 校验层必须存在**（D-05 已定），且失败必须可见（计入质量指标，不得静默）。 |

#### 2.3.3 法规入库治理流程（必须可审计）

```
① 采集：法务/合规提供法规原文与来源 URL
        ├─ 记录 title / region / publish_date / effective_date / expire_date
        └─ 生成 kb_item (governance_status='DRAFT')
                 ▼
② 结构化：人工或半自动切分为条款级条目 → kb_item_version（含 content_hash）
        ├─ 入库前校验 token_count ≤ 8192（ck_chunk_tokens）
        └─ 关联 kb_chunk 并向量化（分批，批次 ≤10）
                 ▼
③ 审批：法务复核 → governance_status='PENDING_APPROVAL'
        └─ 批准后 approved_by / approved_at 落库 → 'PUBLISHED'
                 ▼
④ 关联规则：建立 risk_rule_kb_ref（规则 ←→ 知识依据）
                 ▼
⑤ 失效治理：法规修订时新建 kb_item_version（不覆盖旧版），
            旧版 effective_to 置为修订日，governance_status 视情况 'RETIRED'
                 ▼
⑥ 检索边界：检索默认只返回 PUBLISHED 且在生效期内；
            历史条目必须显式查询并标注
```

**四条硬约束**：

1. **`review_record` 与 `kb_item` 之间没有自动写路径。** 法务确认、误判标记是沉淀数据，**不得在未经治理的情况下直接写回高可信法律法规库**（`01` §5 治理约束 2）。
2. **`kb_item_version` 不可覆盖**——法规修订必须新建版本，与 `material_version` 同精神。
3. **不预置法规内容**——`R__seed_*` 只建结构与角色权限，法规必须走 ①–④ 流程（`01` §10 第 4 条）。
4. **A7（知识库初始数据来源）必须先有结论**，否则 M2 无法开工（见 §8 A7）。

### 3.1 使用说明

- **层级**定义：**单元** = 单一类/函数的确定性测试；**集成** = 跨层（API + DB + 队列/对象存储）；**E2E** = 从界面或完整 API 编排走通业务链路。

- **与 `02` §10 的关系**：T1–T14 是**安全与状态机**专项用例，已在 `02` §10 完整定义，**本文不重复展开**，仅在 §3.14 做映射与执行要求。

- **不可省略的原则**：任何一条 AI 失败路径的期望结果**必须是"待人工判断"**，不得是"通过"（D-08）。

### 4.7 反向追溯验收（一）：从最终批准版本反查全部风险与审核记录

**目标**：证明"对外批准的文件能反向追溯到批准时使用的准确版本"（`AGENTS.md` 第 9 条）。

**操作**：拿到 `material_approval.id`（§4.6 第 12.2 步产生），执行：

```
① 取批准记录
   SELECT id, material_id, version_id, file_sha256, status, approved_by, approved_at, signature_id
     FROM material_approval WHERE id = :approvalId;

② 校验哈希一致性（关键：批准的是"哪一份文件"）
   SELECT file_sha256, version_no, version_label, file_object_key
     FROM material_version WHERE id = :versionId;
   → 断言 material_version.file_sha256 == material_approval.file_sha256

③ 反查该物料的全部 Risk Case
   SELECT id, risk_no, risk_type, risk_level, status, first_version_id, current_version_id, closed_at
     FROM risk_case WHERE material_id = :materialId ORDER BY id;

④ 反查每条风险的全部审核记录（完整审计链）
   SELECT id, actor_type, actor_id, ai_model_id, action, result, opinion,
          from_status, to_status, material_version_id, created_at
     FROM review_record WHERE risk_case_id = :riskCaseId ORDER BY created_at;

⑤ 反查 Case 级记录（含初审、复审、批准、撤销）
   SELECT * FROM review_record WHERE case_id = :caseId ORDER BY created_at;

⑥ 反查所有版本的完整链路
   SELECT id, version_no, version_label, file_sha256, uploader_id, upload_reason,
          parent_version_id, created_at
     FROM material_version WHERE material_id = :materialId ORDER BY version_no;
```

**期望结果（逐条断言）**：

| # | 断言 |
| --- | --- |
| A1 | `material_approval.version_id` 指向的版本 `file_sha256` 与批准记录中的哈希**完全一致** |
| A2 | 能列出该物料的**全部** Risk Case，包括已关闭的、被判误判的、以及 V2 阶段新增的 |
| A3 | 每条 Risk Case 都能列出**从 AI 初审到关闭**的完整 `review_record` 链，且 `from_status`/`to_status` 前后衔接（不出现断链） |
| A4 | AI 记录（`actor_type='AI'`）与人工记录（`actor_type='HUMAN'`）**可区分**，且 AI 记录中**不存在** `action` 为 `SIGN`/`CLOSE`/`APPROVE_MATERIAL` 的行 |
| A5 | `material_version` 的版本链完整（V1 ← V2 ← V3），**无版本被覆盖或删除** |
| A6 | 被撤销的批准记录（`status='REVOKED'`）**仍然存在**，且 `revoke_reason` 可读 |
| A7 | 全部查询结果中**不包含物料原文全文**（原文只能通过锚点 ID 回溯，`01` §4.11） |

### 4.8 反向追溯验收（二）：从任一 Risk Case 找到最初物料、各次修改版本、最终批准信息

**操作**：取 §4.5 第 8.5 步产生的**新增风险**的 `risk_case.id`（这是最难的场景：它诞生于 V2，最终批准的是 V3），执行：

```
① 风险基本信息 + 首次发现版本
   SELECT r.id, r.risk_no, r.risk_type, r.risk_level, r.status,
          r.first_version_id, r.current_version_id, r.created_at, r.closed_at,
          mv.version_no AS first_version_no, mv.file_sha256 AS first_hash
     FROM risk_case r
     JOIN material_version mv ON mv.id = r.first_version_id
    WHERE r.id = :riskCaseId;
   → 断言 first_version_id 的 version_no = 2（首次发现于 V2）

② 所属物料与 Case
   SELECT m.id, m.name, m.material_type, c.case_no, c.name
     FROM risk_case r JOIN material m ON m.id = r.material_id
     JOIN audit_case c ON c.id = r.case_id WHERE r.id = :riskCaseId;

③ 风险定位（回到"当时看到的那一行字/那一帧"）
   SELECT a.anchor_type, a.text, a.locator, a.source_engine, a.confidence
     FROM risk_anchor_ref rr JOIN evidence_anchor a
       ON a.material_version_id = rr.material_version_id AND a.anchor_id = rr.anchor_id
    WHERE rr.risk_case_id = :riskCaseId;
   → 断言锚点属于 first_version（或 current_version），且 locator 可渲染

④ 该风险跨过的所有版本（各次修改版本）
   SELECT DISTINCT mv.id, mv.version_no, mv.version_label, mv.file_sha256,
          mv.uploader_id, mv.upload_reason, mv.created_at
     FROM review_record rr JOIN material_version mv ON mv.id = rr.material_version_id
    WHERE rr.risk_case_id = :riskCaseId ORDER BY mv.version_no;

⑤ 该风险的最终批准信息
   SELECT ma.id, ma.version_id, ma.file_sha256, ma.status, ma.approved_by, ma.approved_at,
          mv.version_no, mv.version_label
     FROM risk_case r JOIN material_approval ma ON ma.material_id = r.material_id
     JOIN material_version mv ON mv.id = ma.version_id
    WHERE r.id = :riskCaseId AND ma.status = 'APPROVED';
```

**期望结果（逐条断言）**：

| # | 断言 |
| --- | --- |
| B1 | `first_version_id` 指向 **V2**（首次发现该风险的版本），且**永不改变** |
| B2 | `current_version_id` 指向**最终处理的版本**（V3 或之后） |
| B3 | 能列出该风险跨越的**所有版本**（V2 → V3），每个版本有 `upload_reason`、`uploader_id`、`file_sha256` |
| B4 | 能查到该风险的**最终批准信息**（批准的版本号 + 哈希 + 批准人 + 批准时间） |
| B5 | 从该风险能定位回**最初的物料与 Case**（含 `case_no`、物料名、类型） |
| B6 | 风险定位锚点能还原"当时看到的那一行字/那一帧"（`anchor_type`、`text`、`locator` 齐备） |

| 3 | 再次执行 §4.7 第 ② 步的哈希校验 | **数据库中的 `material_version.file_sha256` 与 `material_approval.file_sha256` 仍然一致**（哈希是快照，不随对象变化）；同时**对象存储侧校验能发现实际内容与记录哈希不符** → 触发安全告警 |
| 4 | 尝试让"新版本"覆盖旧版本 | **被拒绝**：`material_version` 只允许 INSERT；V2 是新行，V1 的行与 `file_object_key` **不被修改**（`file_object_key` 含 sha256，天然不可变，`01` §4.3） |
| 5 | 检查批准记录关联的是 `version_id` 而非"当前版本" | `material_approval` 表**没有**"取 material 的 current_version_id"这种隐式逻辑；批准必须显式绑定 `version_id`（`01` §4.8 设计说明） |

## 5. AI 效果评估指标

### 5.1 总原则

依据 `AGENTS.md` 第 15 条：

> **AI 效果评估不能只看整体准确率**，还应分别关注高风险召回率、误报率、风险定位准确率、法规依据有效率、修改建议可执行性、待人工判断比例和法务实际节省时间。**涉及高风险漏检的测试应优先于文案风格优化。**

由此确立三条纪律：

| # | 纪律 | 说明 |
| --- | --- | --- |
| **E1** | **禁止用"整体准确率"作为主指标** | 整体准确率会被大量"显而易见的低风险样本"拉高，掩盖高风险漏检。**高风险召回率是唯一的一级指标** |
| **E2** | **高风险漏检优先级高于文案风格优化** | 用例排序、人力分配、发版门禁都按此排序；文风类问题的修复永远排在漏检类问题之后 |
| **E3** | **任何指标的改善不得以"增大待人工判断比例"为代价而不被察觉** | 宽召回必然推高待人工比例（`00` §10 风险登记册已列此项），必须同时监控 §5.7 |

### 5.2 七项指标定义

> **关于目标值**：`00`/`01`/`02` 与 `AGENTS.md` **均未给出任何目标数值**。下表"目标值建议"列中：
> - 标 `待确认（需求未给定）` 的，**必须由法务与项目组在 M1 验收前共同定稿**，并写入《AI 效果基线》；
> - 标 `建议值（需评审确认）` 的，为本文件提出的工程建议，仅在评审通过后成为基线；
> - **未定稿前，M1 的 §5 相关验收项不得判定通过**（只能判定"定义完整、采集可用"）。

#### 5.2.1 高风险召回率（一级指标）

| 项 | 内容 |
| --- | --- |
| **定义** | 在所有"真实存在的高风险问题"中，AI 成功将其识别为 Risk Case 的比例 |
| **计算方式** | `高风险召回率 = 被 AI 识别出的高风险问题数 ÷ 评测集中真实高风险问题总数`（分母来自人工标注 ground truth，分子要求 AI 产出的 Risk Case 在人工复核中被判定为"确实存在"） |
| **两个口径（必须分别计算）** | ① **严格召回**：AI 判定为 `risk_level='HIGH'` 且人工复核确为高风险 → 用于评估"高风险识别的准确度"；② **宽松召回（安全口径）**：AI 只要产出了任何等级的 Risk Case 且人工复核确为高风险 → 用于评估"是否漏掉"。**两个口径都要报，宽松召回更贴近"漏检"的定义** |
| **数据来源** | 评测集 + `risk_case` + 人工复核 |
| **目标值建议** | **`待确认（需求未给定）`**。建议：**宽松召回率 → 100%（不接受任何已知高风险样本漏检）**；严格召回率 `待确认（需求未给定）`（建议责任人：法务负责人，M1 验收前定稿） |
| **特别要求** | 召回率**必须按风险类型分别报告**（`ABSOLUTE_CLAIM`/`SAFETY_PROMISE`/`EVIDENCE_MISSING`/`DISCLAIMER_MISSING`/`COMPETITOR_COMPARISON`/`PRICE_CLAIM`/`MISLEADING`/`OTHER`），不得只报加权平均——**某一类型被系统性漏检会被平均值掩盖** |

#### 5.2.2 误报率

| 项 | 内容 |
| --- | --- |
| **定义** | AI 产出的 Risk Case 中，经法务判定为"不存在该风险"的比例 |
| **计算方式** | `误报率 = 被标记为 REJECTED_FALSE_POSITIVE 的 Risk Case 数 ÷ AI 产出的 Risk Case 总数` |
| **数据来源** | `risk_case.status='REJECTED_FALSE_POSITIVE'` + `review_record.action='LEGAL_FALSE_POSITIVE'`（这是**唯一的可信数据源**——误判必须由法务留理由标记，`AGENTS.md` 第 5 条） |
| **两个口径** | ① 整体误报率（全等级）；② **高风险误报率**（仅 `risk_level='HIGH'`）——后者对法务信任度影响最大 |
| **目标值建议** | `待确认（需求未给定）`。建议：高风险误报率应显著低于整体误报率；整体误报率上限 `待确认（需求未给定）`（建议责任人：法务负责人） |
| **与召回率的权衡** | **宽召回策略（`00` §7.3 阶段 2）必然推高误报率，这是有意为之的取舍**。因此误报率**不得单独看**，必须与 §5.7 待人工判断比例一起看：若误报率上升但待人工比例可控，属正常；若两者同时恶化，说明宽召回的"闸门"开得过大 |
| **重要提醒** | **误报率不能通过"少报"来优化**。降低误报的正确手段是优化阶段 4 的判断质量，不是让阶段 2 少召回 |

#### 5.2.3 风险定位准确率

| 项 | 内容 |
| --- | --- |
| **定义** | AI 给出的风险位置（锚点）在人工抽检中被判定为"指向正确内容"的比例 |
| **计算方式** | `风险定位准确率 = 人工判定定位正确的 Risk Case 数 ÷ 抽检样本中带有有效锚点的 Risk Case 数` |
| **"定位正确"的判定标准** | 高亮区域**包含**风险原文/风险画面，且**未覆盖无关内容到误导程度**（宽度容差 `待确认（需求未给定）`，建议责任人：法务 + 测试，在 M0 期间用真实样本标定） |
| **配套指标（必须同时监控）** | ① **锚点覆盖率** = 有有效锚点的 Risk Case 数 ÷ Risk Case 总数。`00` §3.4 明确"锚点覆盖率可作质量指标"，**无锚点风险占比过高说明解析质量不足，应触发告警而非静默通过**；② **无效定位率** = 锚点校验失败被强制转 `PENDING_LEGAL_DECISION` 的比例（对应 `00` §7.7 失败处理） |
| **按物料类型分别报告** | 图片（`TEXT_LINE` 框选）、视频（时间点）、文档（页/段/句）、纯文本（字符区间）、画面类（`region_hint` 大致区域）的准确率**必须分别报告**——画面类风险按设计就只承诺"大致区域"，与文字类不可混算 |
| **目标值建议** | `待确认（需求未给定）`。建议：文字类定位准确率与锚点覆盖率均需达到较高水平（建议先按"文字类 ≥ 95%、锚点覆盖率 ≥ 98%"评审，`建议值（需评审确认）`）；画面类单独设定 |
| **抽检样本量** | `待确认（需求未给定）`。建议：每个风险类型 × 每种物料类型各 ≥ `10` 条（`建议值（需评审确认）`），总量不足以支撑结论时不得出具评测报告 |

#### 5.2.4 法规依据有效率

| 项 | 内容 |
| --- | --- |
| **定义** | `risk_case.rule_refs` 中引用的知识库条目，在实际核对中"真实存在、现行有效、且与风险类型相匹配"的比例 |
| **计算方式** | `法规依据有效率 = 三项校验全部通过的 rule_ref 数 ÷ 需要法规依据的 Risk Case 的 rule_ref 总数` |
| **三项校验** | ① **存在性**：`rule_ref` 能解析为真实的 `kb_item_version_id`（防虚构，`00` §1 第 12 条：模型无法凭空生成合法 ID）；② **时效性**：对应 `kb_item` 为 `PUBLISHED` 且在当前生效期内（`effective_date`/`expire_date`）；③ **匹配性**：该依据的适用条件（`region`/`applicable_business`/`applicable_product`）与本次物料相符，且经法务判定"依据恰当" |
| **分母口径** | **只统计"应当有法规依据的风险"**。若初审阶段（M1）知识库尚未就绪，`rule_refs` 为空是**预期状态**，此时**不出具该指标**（而不是记为 0 分）——记为 0 分会产生误导性的"依据质量差"结论，掩盖真实原因是"知识库未入库" |
| **目标值建议** | `待确认（需求未给定）`。建议：**存在性与时效性校验必须 100% 通过**（这是机制保证的，不达标即为缺陷）；匹配性 `待确认（需求未给定）`（建议责任人：法务负责人） |
| **配套指标** | `unsupported_claims` 非空率——模型"想引用但检索不到依据"的比例。**这个数字直接指向知识库的缺口**，是 M2 的排期依据 |

#### 5.2.5 修改建议可执行性

| 项 | 内容 |
| --- | --- |
| **定义** | `suggestion`（修改建议）与 `recommended_copy`（推荐表达）在法务/设计/品牌看来"可以直接执行"的程度 |
| **计算方式（两级）** | ① **主观评分**：法务对每条建议按 1–5 分打分，`可执行性 = 评分 ≥ 4 的条数 ÷ 被评分的总条数`；② **客观代理指标**：`推荐表达采纳率 = 整改版本中实际采用了 recommended_copy（或高度近似）的 Risk Case 数 ÷ 提供了 recommended_copy 的 Risk Case 数` |
| **数据来源** | ① 评分需在反馈区/终审区增加一个轻量评分控件（M3 交付物 D5）；② 采纳率可从 Version Diff 自动推断 |
| **目标值建议** | `待确认（需求未给定）`。建议：`建议值（需评审确认）`——评分 ≥ 4 的比例先按 ≥ 70% 评审 |
| **优先级** | **本项属于"文案质量"类指标，优先级低于 §5.2.1 高风险召回率**（`AGENTS.md` 第 15 条明文）。当人力有限时，**先保证不漏检，再优化建议文案** |
| **常见失败模式** | 建议太空泛（"建议修改表述"）、建议不可执行（"请提供数据来源"但没有说明找谁要）、推荐表达过于保守（把正常宣传词也改成无信息量的表述） |

#### 5.2.6 待人工判断比例

| 项 | 内容 |
| --- | --- |
| **定义** | AI 无法独立给出结论、需要法务介入的 Risk Case 比例 |
| **计算方式** | ① `待人工判断比例 = 进入过 PENDING_LEGAL_DECISION 的 Risk Case 数 ÷ AI 产出的 Risk Case 总数`（含最终被确认为真风险的与判为误判的）；② **物料级口径**：`v_material_initial_review.initial_review_class='PENDING_HUMAN'` 的物料数 ÷ `reviewed_material_count` |
| **为什么必须监控** | `00` §10 风险登记册列明："**待人工判断比例过高 → 法务工作量不降反升**"。这是宽召回策略的**直接代价**，也是产品价值能否成立的**最关键的反向指标**——如果 AI 把 80% 的内容都推给法务，产品就没有节省任何时间 |
| **数据来源** | `risk_case.status` 流转历史（`review_record`）+ `v_material_initial_review` 视图 |
| **目标值建议** | `待确认（需求未给定）`。**这是最需要法务参与设定的指标**，因为它直接决定法务的实际工作量。建议责任人：法务负责人，M1 试用期（`待确认（需求未给定）`）后基于真实数据定稿 |
| **降级事件必须单独统计** | 由 AI 失败降级（超时/校验失败/限流/`unsupported_claims`）导致的 `PENDING_LEGAL_DECISION` 必须与"真实需要人工判断"**分开统计**。前者是**系统缺陷指标**，后者是**业务特征指标**，混在一起会掩盖系统问题（`00` §7.7 的各类失败都走这个降级路径） |
| **配套指标** | **法务单条风险平均处理时长**——若待人工比例不变但处理时长下降，说明界面效率提升；两者一起看才能判断产品价值 |

#### 5.2.7 法务实际节省时间

| 项 | 内容 |
| --- | --- |
| **定义** | 使用系统后，法务完成一次同等规模审核所节省的净时间 |
| **计算方式（净节省，必须扣除人工处理成本）** | `净节省时间 = T_传统 − (T_AI等待 + T_法务处理)`<br>其中：`T_传统` = 人工从头阅读全部物料并撰写意见的耗时；`T_AI等待` = 物料提交到初审结果可用的等待时间（含解析 + 初审 + Batch 排队）；`T_法务处理` = 法务在系统中处理 Risk Case 的实际耗时 |
| **`T_传统` 基线来源** | **`待确认（需求未给定）`**——需求未给出基线。必须先测量：建议在 M1 试用前，请法务对 §4.2 的验收物料包做一次**计时的人工审核**（作为基线），并记录物料数量、总时长、发现的真实风险数 |
| **`T_法务处理` 的测量** | 需在系统中埋点：从打开 Risk Case 到完成操作（确认/误判/补料/转整改）的时长（M3 交付物 D5）；**注意减去"挂着页面走开"的异常值**（统计口径 `待确认（需求未给定）`） |
| **目标值建议** | `待确认（需求未给定）`。建议：`建议值（需评审确认）`——净节省时间应为正，且随批次规模增大而提升（规模效应） |
| **反面情形（必须如实报告）** | 若净节省时间为负（例如：AI 等待 + 处理逐条 Risk Case 的时间超过人工通读），**必须如实报告并触发方案评审**，不得通过调整统计口径来掩盖。`AGENTS.md` 第 16 条明确："产品成功的标准不是 AI 生成了多少内容，而是法务是否能够更快发现真正重要的问题、更少重复阅读材料" |
| **分物料类型报告** | 图片/视频/文档/文本的节省时间差异很大（视频抽帧 + ASR + 关键帧理解耗时最长），必须分别报告 |

### 5.4 评测集构造方法

#### 5.4.1 三类样本的来源

| 样本类型 | 定义 | 来源 | 数量建议 |
| --- | --- | --- | --- |
| **正样本**（真实存在风险） | 已知含风险的历史广宣物料 | ① 企业历史被驳回/被要求修改的物料（法务台账）② 监管处罚案例中的公开广告（脱敏后）③ 由法务**定向构造**的样本（按 `risk_type` 每个类型 ≥ `待确认（需求未给定）`，建议 ≥15 条） | `待确认（需求未给定）`（建议 ≥100 条，覆盖 8 种 `risk_type`） |
| **负样本**（确实无风险） | 审核通过且事后无争议的物料 | 企业历史已批准的合规物料 | `待确认（需求未给定）`（建议 ≥100 条，用于测误报率） |
| **边界样本**（最难的一类，价值最高） | 处于"可判可不判"灰区、依赖具体事实或法律解释的物料 | ① 历史上法务内部有分歧的案例 ② 需要外部证据才能判断的宣称（如"行业领先"有第三方报告 vs 无报告）③ 表述合法但可能误导消费者的情形 ④ **跨规则交叉**的情形（一句话同时触及绝对化与证据缺失） | `待确认（需求未给定）`（建议 ≥50 条，**边界样本的评测结果比正负样本更能反映真实能力**） |

#### 5.4.2 样本必须携带的元数据

每个样本必须有配套的标注记录（建议以 `eval_sample.yaml` + 文件目录管理）：

```yaml

material_type: IMAGE                     # 与 material.material_type 枚举一致
file: samples/img/EV-IMG-0007.png
file_sha256: <64位哈希>                  # 与 material_version.file_sha256 同口径

ground_truth:
  - risk_type: ABSOLUTE_CLAIM            # 与 risk_case.risk_type 枚举逐字一致
    risk_level: HIGH                     # 与 CHECK 约束逐字一致
    risk_text: "行业第一"
    location: { kind: TEXT_LINE, bbox_hint: [x, y, w, h] }   # 位置真值（粗标注即可）
    kb_ref_expected: [kb_item_version_id]  # 期望命中的依据（用于测法规依据有效率）
    rationale: "《广告法》绝对化用语…"     # 人工理由
  - risk_type: SAFETY_PROMISE
    risk_level: HIGH
    ...
no_risk: false                           # 负样本为 true
boundary: false                          # 是否边界样本
annotator: <法务代号>
annotated_at: <日期>
reviewed_by: <复核法务代号>               # 必须双人复核
```

#### 5.4.3 评测集构造的四条硬要求

| # | 要求 | 理由 |
| --- | --- | --- |
| 1 | **全部脱敏** | `AGENTS.md` 第 12 条：物料可能含未发布产品、商业秘密、个人信息 |
| 2 | **双人标注 + 分歧留档** | 单人标注的"真值"不可信；分歧案例单独标记为 `boundary`，**分歧本身就是最有价值的评测样本** |
| 3 | **评测集与训练/提示词优化数据分离** | 评测集一旦被用于调 prompt，就不再是独立评测集；必须**留出一份"封存集"**（`待确认（需求未给定）`，建议 ≥20%），只在发版门禁时使用 |
| 4 | **版本化** | 评测集每次变更必须有版本号；跨版本比较指标时必须声明评测集版本，否则数字不可比 |

#### 5.4.4 评测执行规范

| 项 | 要求 |
| --- | --- |
| 固定变量 | 每次评测必须固定并记录：`pipeline_version`、`prompt_version`、`ruleset_version`、`model_id`、评测集版本（`00` D-10 的版本三件套） |
| 触发时机 | ① 首次上线前；② 任何 `prompt_version` 变更；③ 任何 `ruleset_version` 变更；④ 任何 `model_id` 变更；⑤ 知识库大规模入库后；⑥ 每次发版门禁 |
| 结果落库 | 评测结果必须存档（含评测集版本 + 三件套 + 七项指标数值），否则"为什么这次判得不一样"无法回答 |
| 报告要求 | **必须按 `risk_type` 与 `material_type` 交叉报告**，不得只给总数 |
| 门禁规则 | **高风险召回率（宽松口径）下降即阻断发版**，无论其他指标是否提升 |
