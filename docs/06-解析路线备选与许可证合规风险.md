## 1. 选型结论（路线 B）

| 能力 | 方案 | 版本 | 许可证 | CPU/GPU |
| --- | --- | --- | --- | --- |
| 中文 OCR（含坐标） | PaddleOCR + PP-OCRv6_medium | 3.7.0 | 代码与 v5/v6 权重模型卡均为 Apache-2.0；**⚠️ 3.x 可选依赖含 AGPL-3.0 库，必须裁剪** | **CPU 够用**：官方端到端 **1.40 s/图**（Xeon 8350C + OpenVINO）；tiny 0.20 s/图 |
| 海报/文档版面分析 | PP-StructureV3 | 随 PaddleOCR 3.7.0 | Apache-2.0 | CPU（官方 FAQ 明确支持）；20 类版面标签 + 表格单元格坐标；轻量模式 3.74 s/图 |
| 中文 ASR（含时间戳） | FunASR + Paraformer-zh（**须显式配 FSMN-VAD + ct-punc**） | funasr 1.4.16 | 工具链 MIT；权重标 Apache-2.0；**⚠️ 仓库另有《模型协议 v1.1》要求署名，双文本并存** | **CPU 够用**：官方 ONNX int8 基准 237MB、CER 1.95%、单并发 **RTF 0.028（≈35× 实时）**；老 CPU 无 avx512_vnni 亦 ≈13× 实时 |
| 镜头切分 | PySceneDetect + ffmpeg | 0.7.1 | BSD-3-Clause | CPU；默认 `ContentDetector(threshold=27, min_scene_len=15)`；**快剪广告改用 `AdaptiveDetector(adaptive_threshold=3.0)`** |
| PDF / PPTX / DOCX | **Java 原生**：Apache PDFBox + Apache POI（Python 侧 pdfplumber 做交叉校验） | PDFBox 3.0.8、POI 5.5.1、pdfplumber 0.11.10 | Apache-2.0 / MIT | CPU |
| 集成方式 | FastAPI 解析微服务 + Redis 队列异步 + HTTP 结果/进度查询 | FastAPI 0.141.1 | MIT | — |

**关键判断：简单文档解析不需要 Python。** PDFBox + POI 均为 Apache-2.0 且是 Java 原生，已能覆盖 PDF 文字+坐标、PPTX 形状+段落+坐标、DOCX 段落+run。Python 微服务**只承载 Java 做不了的部分**：PP-StructureV3 复杂版面、扫描件 OCR、ASR、视频抽帧。这能显著缩小路线 B 的部署面。

## 2. 许可证与合规风险（**与选哪条路线无关，必须现在处理**）

### 2.1 ⚠️ Redis 版本许可（直接影响本项目技术栈）

> **Redis 8 起为 RSALv2 / SSPLv1 / AGPLv3 三重许可；Redis 7.2 及更早为 BSD-3-Clause。**

`00` 文档的技术栈把 Redis 列为队列与缓存组件。若部署 Redis 8，将引入 **AGPLv3 或 SSPLv1** 的合规问题（SSPL 对"作为服务提供"有强约束，AGPL 有网络分发触发条款）。

**决策建议（三选一，需法务确认）**：

| 选项 | 说明 | 建议 |
| --- | --- | --- |
| **锁定 Redis 7.2.x（BSD-3）** | 最省事，功能对本项目完全够用（队列/进度/锁/幂等键/令牌桶） | ✅ **推荐** |
| 改用 **Valkey**（Redis 7.2 的 BSD 分支） | 长期维护活跃，许可干净 | 可选，需评估团队熟悉度 |
| 使用 Redis 8 并接受许可 | 需法务书面认可 | ❌ 不建议，收益不足以承担合规成本 |

> **这条要写进 `deploy/docker-compose.yml` 的镜像 tag 并从 CI 加校验**，避免有人顺手 `redis:latest` 把许可问题引进来。

### 2.2 ⚠️ PyMuPDF 的 AGPL 定性（若走路线 B 才相关）

PyMuPDF 是 **AGPL-3.0 / 商业双授权**。Artifex（权利方）的公开表述禁止"作为 server-based application 部署而不按 AGPL 公开自有源码"，且约束对象是"any users interacting with it"。

**内网自用是否触发 AGPL 义务属法律解释，本文不下结论**，列为法务拍板项。

**规避方式**：路线 B 的选型已**不使用 PyMuPDF**——PDF 用 Apache-2.0 的 PDFBox，版面用 PaddleOCR 的 PP-StructureV3。

### 2.3 ⚠️ PaddleOCR 3.x 依赖树中混入 AGPL 组件

PaddleOCR 3.x 的**可选依赖**包含 PyMuPDF / pdf2docx（AGPL-3.0）。虽然不是默认核心依赖，但一旦被间接装进镜像就会引入许可风险。

**对策（必须做）**：
1. 安装时显式裁剪可选依赖，锁定 `requirements` 清单；
2. **CI 增加许可证白名单扫描**（对镜像内所有 Python 包做 SPDX 校验），出现 AGPL/SSPL 即构建失败；
3. 在交付手册中记录裁剪方式，避免后续有人"补装个 pdf2docx 方便调试"。

### 2.4 FunASR 权重许可存在双文本

工具链为 MIT，Paraformer 权重在 ModelScope/HuggingFace 标注 Apache-2.0，但**仓库另有一份《模型协议 v1.1》要求署名**。

**处理**：两者并存意味着许可口径不唯一。**建议向模型方书面确认，并同时在产品"关于"页做署名**（成本极低，可一次性消除风险）。

### 2.5 云 API 的三条架构约束（**对主方案路线 A 至关重要**）

调研结论（针对腾讯云 / 百度 / 阿里云的独立 OCR、ASR 公网 API）：

| # | 约束 | 对本项目的影响 |
| --- | --- | --- |
| 1 | 三家公网 API **均要求输入公网可达**（腾讯 ASR `Url` 要求"公网环境浏览器可下载"；百度转写要求"云端可外网访问的 url 链接"） | **视频/图片必须先上传到公网可达存储**，不能直接内网传文件 |
| 2 | 三家 AI 能力文档中**均未查到 VPC 内网接入或专线直连的说明** | 无法通过"内网打通"来避免文件出网 |
| 3 | 三家**均未查到"输入内容不用于模型训练"的书面条款** | 数据用途缺乏书面保证 |

有完整公开私有化路径的**只有百度**（OCR 离线 SDK 公开价 299 元/设备起）。

**对本项目的具体含义（必须让决策者看到）**：

- 走路线 A 时，**物料原件会离开内网**。百炼的 ASR 异步接口同样要求 `file_url` 为可访问 URL（官方 FAQ 推荐用阿里云 OSS 并生成公网访问 URL）。
- 可行的收敛做法：**上传到阿里云 OSS（北京地域）+ 短期签名 URL**，并在任务结束后删除对象。文件在阿里云生态内，公网暴露窗口最小化，但**"物料出内网"这一事实无法消除**。
- 因此 **A1（安全部门书面确认）是硬前置**，不是形式流程。若 A1 不通过 → 走路线 B，且需接受解析精度与运维成本的权衡。
- ⚠️ 上述第 2、3 条是针对三家云独立 OCR/ASR 产品的调研结论。**百炼作为企业级大模型平台，其数据条款与 VPC 接入能力需单独向阿里云商务确认**（本文不替它做结论）。这应作为 A1 的一部分一并问清。

## 3. 锚点粒度必须按格式如实承诺（**对主方案同样适用**）

调研发现一个格式固有限制，**与用哪个解析引擎无关**：

> **DOCX 拿不到真实页码。** 依据：ISO/IEC 29500-1 对 `w:lastRenderedPageBreak` 的定义，以及 python-docx 官方文档明确说明该标记"never inserted by python-docx because it has no rendering function"。Word 的分页是渲染期决定的，文件里不存页码。

因此 `00` 文档 §3.2 的锚点设计需要按下表**如实分层承诺**，不能对用户许诺做不到的粒度：

| 物料格式 | 可承诺的定位粒度 | 不可承诺 |
| --- | --- | --- |
| 图片/海报 | 归一化 bbox（文字行级，可精确框选） | — |
| 视频 | 起止毫秒（句级/字级）+ 关键帧 | — |
| PDF | 页码 + 段落 + 句子 + 坐标框 | — |
| PPTX | slide 序号 + 形状 ID + 形状坐标 | — |
| **DOCX** | **段落索引 + run 索引** | ❌ **页码、页内坐标** |
| 纯文本 | 字符区间 | — |

**行动项**：
1. ⚠️ 若需求（或界面文案）写了"DOCX 风险可跳转到第 N 页"，**必须先改需求或改文案**。这是格式限制，不是实现难度问题。
2. `DOC_PARAGRAPH` 锚点的 `locator` 中 `page_no` 字段**对 DOCX 必须允许为空**，界面对 DOCX 隐藏"页码"维度。
3. 界面文案统一表述为"定位到段落"，而非"定位到页面"。

> **这正是 `AGENTS.md` 第 15 条的要求**：尚未实现或无法实现的能力，不得在界面上伪装成可用。

## 4. 工程陷阱清单（**对两条路线都适用**）

### 4.1 "装了就有"是错的：三个默认关闭的开关

| 组件 | 需要的能力 | 默认值 | 后果 |
| --- | --- | --- | --- |
| PaddleOCR | 词/单字级坐标 | `return_word_box=False` | 只拿到行级坐标，无法框到单个字 |
| FunASR | 时间戳 | `pred_timestamp` / `output_timestamp` 默认 **False** | **拿不到时间戳，视频定位直接失效** |
| FunASR | 标点恢复 / 说话人 | `ct-punc`、`cam++` **都不默认启用**，且 `cam++` 必须配 VAD | 无标点导致句子切分不可用 |

**FunASR 的官方选型指南原文**："Switch to Paraformer when your workload is Mandarin-only and you want **character-level timestamps**" —— 字级时间戳是官方明示能力，但**必须显式开启**。

> 这与主方案里发现的同类问题完全一致（`qwen3-asr-flash` 走 OpenAI 兼容接口不返回时间戳）。**"时间戳能力"在两条路线上都需要显式确认，不能假设。**

### 4.2 跨语言坐标单位不一致

- **Apache POI XSLF（PPTX）的 `getAnchor()` 单位是 points（72 dpi）**
- **python-pptx 的单位是 EMU**
- **PaddleOCR 的 `rec_polys` / `rec_boxes` 是像素，且基于送检图片尺寸**

混用必须显式换算。建议：**内部统一以"送检图片的像素坐标 + `scale_ratio`"为唯一坐标基准**（与 `00` §3.3 约束 1 一致），任何引擎的单位在入库前换算到该基准。

### 4.3 依赖成熟度风险

- POI 官方自述 **XSLF（PPTX）"still in early development… subject to incompatible changes"**，**XWPF（DOCX）"not a mature and stable API yet"** → **必须锁版本**并预留回退方案。
- **gRPC 不作为起点**：`net.devh:grpc-spring-boot-starter` 停更于 2024-04，`org.xolstice:protobuf-maven-plugin` 仓库已 archived；gRPC 官网对 Python 侧无 GA 背书。→ 与 `00` 文档 §4.2 结论一致：**HTTP + 队列起步**。

### 4.4 内网镜像可达性（路线 B 的落地风险）

> **Docker Hub 上没有 PaddleOCR 官方镜像**（官方在百度云 CCR：`ccr-2vdh3abv-pub.cnc.bj.baidubce.com/...`）；**FunASR 官方镜像在阿里云 registry**（`registry.cn-hangzhou.aliyuncs.com/funasr_repo/funasr`）。

这两个 registry **在企业内网很可能不可达**。必须在可联网环境 `docker pull` 后 `docker save` / `docker load` 离线导入，并写进交付手册。

**建议尽早验证这两个域名的内网可达性**——这属于"早发现一天省一周"的检查项。

### 4.5 进度必须一开始就定义成"可计量单位"

`AGENTS.md` 第 14 条要求"向用户展示真实进度"。但"真实进度"必须有可计量分母：

| 物料类型 | 进度分母 |
| --- | --- |
| 视频 | 已处理毫秒 / 总毫秒 |
| PDF / PPTX | 已处理页数 / 总页数 |
| 图片 | 单图（0% 或 100%，配合 OCR 内部分阶段） |
| 批量 Case | 已完成物料数 / 总物料数 |

**若不从一开始这样定义，后续想换成真实进度会导致前端语义返工**（进度条从"假动画"改成"真百分比"时，用户对"卡在 87%"的容忍度完全不同）。

### 4.6 Whisper 系在广告视频场景的反面证据（解释"为什么不选"）

广告视频大量存在"纯 BGM 无人声"段落，而 Whisper 系对此有已知问题：

- ICASSP 2025 论文《Investigation of Whisper ASR Hallucinations Induced by Non-Speech Audio》(arXiv:2501.11378) 证实**非语音音频会诱发高频幻觉**，语音叠加亦会诱发。
- openai/whisper 官方 Discussion #2645 标题即"中文输入为静音或只有背景噪声时，模型经常输出固定的无关文本"。
- `word_timestamps` 在 openai/whisper 的 CLI 帮助中**自标 "(experimental)"**。

FunASR 的 **VAD + Paraformer 架构让无语音段不进入识别器**，机制上规避了这个问题。

⚠️ **但必须诚实说明**：**没有任何来源给出"中文广告口播 + BGM"场景的量化 CER**。这是最大的验证空白，**必须用企业自有素材实测**（见 `05` 文档 M0 的 V4）。

### 4.7 "PaddleOCR 中文最好"是社区共识，不是官方基准

RapidOCR / CnOCR / EasyOCR / Tesseract **四者官方均无中文准确率数据**（Tesseract 官方 Benchmarks 只测速度，其 `chi_sim` 语言数据最近提交为 2024-03-07）。因此选型时**不能用横向排名做验收依据**，必须用企业自有海报样本集实测。这也是 `05` 文档要求 M0 用真实物料验证的原因。

## 5. 两条路线的对比与切换

| 维度 | **路线 A：千问云 API（主方案）** | **路线 B：本地解析（备选）** |
| --- | --- | --- |
| 物料出内网 | ⚠️ **必须**（需公网可达 URL） | ✅ 否 |
| 部署复杂度 | 低（Java + Redis + MinIO） | 高（+ Python 服务 + 镜像离线导入） |
| 算力 | 无需 GPU | **CPU 即可**（OCR 1.40 s/图，ASR ≈35× 实时） |
| 精度维护 | 阿里维护，随模型升级 | 自行调优 |
| 成本结构 | 按量付费（可走 Batch 减半） | 一次性算力 + 运维人力 |
| 交付速度 | 快 | 慢 |
| 许可证风险 | 无（云服务） | PaddleOCR/FunASR 依赖树需审计 |
| 与需求冲突点 | **A1**（数据出网） | 无 |

### 5.1 切换的技术前提（必须现在就做）

`00` 文档 ADR D-14 已要求保留 `ParsePort` 抽象。具体落地：

```java
public interface ParsePort {
    OcrResult      ocr(OcrRequest req);        // 文字 + 坐标 + 置信度
    AsrResult      asr(AsrRequest req);        // 句级/字级时间戳
    DocumentResult parseDocument(DocRequest req);
    // 注意：接口签名不得出现任何供应商专有类型
}

// 路线 A 实现
class DashscopeParseAdapter implements ParsePort { ... }
// 路线 B 实现
class LocalParseAdapter implements ParsePort { ... }   // 调 gw-parse
```

**强制约束**：
- `ParsePort` 的方法签名**不得出现任何供应商专有类型**（如 DashScope 的 `TranscriptionResult`），否则切换时要改业务代码；
- 两条路线产出的**锚点结构必须完全一致**（同一个 `evidence_anchor` 表结构），这样 `01`/`03` 的下游逻辑无需区分路线；
- 写一个**契约测试**，同一份测试物料分别喂给两个实现，断言产出的锚点集合结构等价（允许内容与精度不同，但字段结构必须一致）。
