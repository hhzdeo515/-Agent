## 1. 接口设计约定

### 1.1 基础约定

| 项 | 约定 |
| --- | --- |
| 协议 | HTTPS，内网经 Nginx 反代（拓扑见 00 §4.3） |
| Base Path | `/api`。**不引入 `/api/v1` 前缀**（内部系统、前后端同仓发布；是否需要版本前缀见 §8 T-21） |
| 请求体 | `application/json; charset=utf-8`；文件分片为 `application/octet-stream` |
| 响应体 | `application/json; charset=utf-8`；报告导出为文件流 |
| JSON 命名 | 统一 **camelCase**（建议；见 §8 T-03）。数据库 `snake_case` → DTO camelCase 的映射由后端显式完成，**不得依赖全局命名策略静默转换**，否则 01 的视图列名（如 `initial_pass_rate_by_material`）与前端字段名会失去可追溯的对照关系 |
| 时间字段 | 一律 **ISO-8601 带时区偏移**字符串，例如 `2026-09-12T10:00:00+08:00`。**毫秒偏移量字段一律以 `_ms` 结尾且为整数**（`begin_ms` / `end_ms` / `ts_ms` / `durationMs`）。这是一条硬规则，用于防住 00 §2.2 陷阱 2（ASR 任务级 `end_time` 是完成时间字符串、音频内 `end_time` 是毫秒整数，同名不同义）。**服务端不得把两者序列化成同名字段**（见 §8 T-22） |
| 字符编码 | UTF-8；`char_range` 的计数单位见 §3.4 与 §8 T-08 |
| 幂等 | 所有**非幂等写接口**必须支持 `Idempotency-Key` 请求头，见 §1.4 |
| traceId | 见 §1.5 |

### 1.2 RESTful 风格约定

1. **资源用复数名词**：`/cases`、`/materials`、`/risks`、`/versions`、`/signatures`、`/approvals`。
2. **领域命令用子资源 + POST**：`/confirm`、`/false-positive`、`/request-evidence`、`/to-remediation`、`/rereviews`、`/close`、`/approvals`。理由：这些动作不是 CRUD，映射不到 PUT/PATCH 语义；但**禁止**把多个动作塞进一个端点用 `action` 参数分派（如 `POST /api/risk/do?type=close`），否则权限注解与审计粒度都会失效。
3. **HTTP 方法语义**：
   - `GET` 安全且幂等；
   - `PUT` 全量替换、幂等（用于上传分片、审核要求覆盖保存）；
   - `PATCH` 部分更新（仅用于 Case 基础信息编辑）；
   - `POST` 非幂等，**必须携带 `Idempotency-Key`**（上传会话创建、启动初审、复审、签名、关闭、批准、驳回、撤销）；
   - `DELETE` **仅允许用于未产生业务留痕的会话类资源**（如未完成的上传会话）。**禁止提供任何删除 Case / Material / Version / Risk Case / Review Record / 签名的接口**——01 §7.1 的触发器已从数据库层拒绝，"接口层也不提供"是第二道防线。
4. **状态码语义**（必须同时正确，不得一律返回 HTTP 200 + 业务码）：

| HTTP | 用途 | 依据 |
| --- | --- | --- |
| 200 / 201 / 204 | 成功 / 创建成功 / 无内容 | — |
| 400 | 参数校验失败；**`reviewScope=FULL` 拒绝** | 02 §8 明确要求返回 400 |
| 401 | 未认证或令牌失效 | — |
| 403 | 无权限点、跨项目访问、非项目成员 | 02 §4.3、01 §3 |
| 404 | 资源不存在（或按 §8 T-28 的决策统一处理跨项目） | — |
| 409 | 乐观锁冲突、重复提交、并发任务运行中 | 02 §7 明确要求返回 409 |
| 413 | 分片/文件超出大小上限 | — |
| 422 | **状态机拒绝与业务规则拒绝**（`ILLEGAL_TRANSITION` 等） | 02 §3.3 |
| 429 | 限流 | 00 §7.7 |
| 500 / 503 | 系统内部错误 / 外部依赖不可用 | 00 §7.7 |

### 1.3 统一响应包装

采用 `Result<T>`（命名与 02 §5.2 的 `Result.ok()` 保持一致）：

```jsonc
// 成功
{ "code": 0, "message": "OK", "data": { /* T */ }, "traceId": "b7f1c2...", "timestamp": "2026-09-12T10:00:00+08:00" }

// 失败
{ "code": 43001, "message": "OPEN → CLOSED 不是合法跃迁", "data": null,
  "traceId": "b7f1c2...", "timestamp": "2026-09-12T10:00:00+08:00",
  "details": [ { "field": "status", "reason": "当前状态：OPEN", "rejectedValue": "CLOSED" } ] }
```

- `code = 0` 表示成功；非 0 为错误码（见 §1.6）。
- `message` 是**面向用户的、可直接展示的中文**。前端**不得**用 `code` 拼装用户文案，也不得把 `message` 再包一层技术前缀。
- `details` 仅用于参数校验与字段级冲突，供表单标红。
- **分页响应**固定为 `PageResult<T>`：

```jsonc
{ "records": [ /* T[] */ ], "total": 137, "pageNum": 1, "pageSize": 20 }
```

### 1.4 分页、排序、筛选约定

| 项 | 约定 |
| --- | --- |
| 分页参数 | `pageNum`（**从 1 开始**）、`pageSize`（默认 20，上限 200）。`pageSize` 超限返回 40001，**不得静默截断** |
| 排序 | `sort`（字段名，白名单枚举）+ `order`（`asc` / `desc`）。**排序字段必须走白名单**，禁止把前端字符串直接拼进 SQL |
| 筛选 | 平铺 query 参数（`status`、`riskLevel`、`riskType`、`materialId`、`keyword`）。多值用重复参数（`riskLevel=HIGH&riskLevel=MEDIUM`） |
| 大列表 | 反馈区/终审区风险列表必须分页；**禁止一次性返回整批风险**。看板聚合走专用聚合端点（§2.3 C-01） |
| 导出 | 走独立文件流端点（§2.3 C-11），不复用列表端点 |
| 前端状态 | 列表页的筛选/分页状态**必须同步到路由 query**，保证可复制分享与刷新还原（§7.3） |

### 1.5 traceId 透传

1. `gw-api` 入口过滤器（最外层，先于鉴权）读取请求头 `X-Trace-Id`；**存在则沿用，不存在则生成**。生成后写入日志 MDC 与 `UserContext`。
2. 响应头**一律回写** `X-Trace-Id`。
3. `audit_log.trace_id`（01 §4.11）写入同值，使"用户截图里的 traceId"能直接定位审计记录。
4. 前端：多步流程（如"签名 → 关闭"两步调用、上传会话的三个调用）可复用同一个 `X-Trace-Id`，便于把一次用户操作串成一条链路。**是否要求前端主动生成并透传，见 §8 T-22 同一决策组**。
5. ⚠️ `audit_log` 与日志**严禁写入物料原文**（01 §4.11）。记录锚点 ID、字段级摘要与哈希即可。

### 1.6 错误码分段

**分段规则**：`4xxxx` 业务错误，`5xxxx` 系统与依赖错误；成功为 `0`。

| 码段 | 分类 | 典型 HTTP | 说明 |
| --- | --- | --- | --- |
| `40001–40099` | 通用请求与参数校验 | 400 | `40001` 参数校验失败、`40002` 缺少确认标记（`confirm=true`）、`40003` 必填理由缺失 |
| `40101–40199` | 认证 | 401 | `40101` 凭证错误、`40102` 账号停用、`40103` 令牌失效/过期 |
| `40301–40399` | 鉴权与数据权限 | 403 | `40301` 缺少权限点、`40302` 跨项目访问被拒、`40303` 非项目成员 |
| `40401–40499` | 资源不存在 | 404 | `40401` Case、`40402` 上传会话、`40403` Risk Case |
| `40901–40999` | 并发与重复提交 | 409 | `40901` 乐观锁冲突（`lock_version`）、`40902` 同类任务运行中、`40903` 重复提交 |
| `42901–42999` | 限流 | 429 | `42901` 助手限流、`42902` 上传限流 |
| `43001–43999` | **状态机与业务流程** | 422 / 400 | `43001` `ILLEGAL_TRANSITION`、`43101` `REVIEW_SCOPE_REQUIRED`、`43102` `REVIEW_SCOPE_FULL_REJECTED`、`43201` `BLOCKING_RISK_OPEN`、`43301` `AI_CANNOT_CLOSE_RISK`、`43302` `SIGNATURE_REQUIRED`、`43303` `SIGNER_NOT_PRIVILEGED` |
| `44001–44999` | 解析与 AI 环节 | 422 / 503 | `44001` 助手临时文件过期、`44002` 解析失败、`44003` 锚点校验失败（已降级为待人工判断） |
| `45001–45999` | 文件与存储 | 400 / 413 / 422 | `45001` 对象不存在、`45002` 类型不支持、`45003` 超出大小上限、`45004` 文件哈希不一致 |
| `50001–50999` | 系统内部 | 500 | `50001` 未预期异常 |
| `51001–51999` | 外部依赖 | 503 | `51001` 模型服务不可用、`51002` 对象存储不可用、`51003` 缓存不可用 |

**`43001` / `43301` / `43302` 三个枚举名直接来自 02 §5.2 的示例代码**，本文只为其分配数值。**数值分配为建议值，必须在 `gw-common` 的 `ErrorCode` 中冻结，并与 02 回填对齐（见 §8 T-01）。**

**通用重试策略**：`5xxxx` 与 `429xx` 允许按 00 §7.7 做指数退避重试；`4xxxx` **不得自动重试**（业务拒绝重试没有意义，重试还会污染审计）。

### 1.7 幂等键请求头约定

| 项 | 约定 |
| --- | --- |
| 请求头 | `Idempotency-Key: <UUID>`，由客户端生成（同一用户操作重试必须复用同一个值） |
| 适用端点 | 全部 `POST`（上传会话创建、启动初审、解析重试、人工判断四个动作、复审、签名、关闭、批准、撤销、驳回） |
| 服务端行为 | 以 `(userId, method, path, Idempotency-Key)` 为键登记；**首次请求执行并缓存结果，重复请求返回首次结果（HTTP 200 + 相同 body）**，不返回 409 |
| 与业务幂等键的关系 | 客户端**只传随机 key**，**不得自行拼装业务幂等键**。业务幂等键由服务端按 00 §7.6 派生：任务层 = `case_id + material_id + version_id + pipeline_version + prompt_version + ruleset_version + model_id`；解析层 = `parse_job.idempotency_key`；异步层 = `async_task.idempotency_key` |
| 三层防重的落点 | 文件层 `uk_version_sha`（01 §4.3）、任务层 `uk_parse_idem` / `uk_async_idem`、风险层 `uk_risk_dedup`（01 §4.6）。**前端不参与任何一层去重判断** |
| TTL | Redis 中登记键与结果的 TTL **待确认**（见 §8 T-25） |

**前端约定**：同一"用户意图"内（如一次点击触发的多步调用）复用同一个 `Idempotency-Key`；用户主动再次点击（新意图）必须生成新 key。实现见 §7.3。

### 1.8 认证方式：推荐 JWT

**推荐 JWT（Bearer Token）+ 服务端权限点校验**，理由：

1. `gw-api` 按 00 §4.3 可多实例部署，JWT 无状态，避免为一个内部系统引入会话粘滞或集中 session 存储的复杂度。
2. claim 中携带 `userId` / `jti` / `tokenVersion` 便于审计归因（`audit_log.actor_id`、`review_record.actor_id`）。
3. **但权限点绝不从 JWT claim 取信**：02 §5.1 明确"前端权限列表必须由后端下发，不得在前端硬编码角色到权限的映射"。同理，后端鉴权也必须实时查（DB + Redis 缓存），否则管理员调整权限后旧 token 仍带着旧权限。**JWT 只承载身份，不承载授权。**

落地要点：

| 项 | 约定 |
| --- | --- |
| 传递方式 | `Authorization: Bearer <accessToken>` |
| 前端存储 | `accessToken` 仅存内存（Pinia，不落 localStorage）；`refreshToken` 放 `HttpOnly` Cookie（**Cookie 属性与 CSRF 策略见 §8 T-02**） |
| 权限下发 | `GET /api/me/permissions`（02 §5.1 已规定该端点），返回 `sys_permission.code` 字符串数组，**逐字与 02 §4.2 一致** |
| 失效与撤销 | Redis 维护 `jti` 黑名单 + 用户级 `tokenVersion`；用户停用（`sys_user.status='DISABLED'`）、角色变更、权限变更时递增 `tokenVersion`，旧令牌立即失效 |
| 401 处理 | 前端清空用户态 → 跳登录并带 `redirect` |
| SSO | 是否对接企业统一身份（AD / 企业微信 / 钉钉）**待确认**（§8 T-02） |
| 实现库 | 具体 JWT 库**待确认**（§8 T-02），不得在本文凭空指定依赖坐标 |

### 1.9 数据权限：项目隔离必须由拦截器统一注入

01 §3 已定：**所有业务查询必须携带 `project_id` 过滤，由 `gw-app` 层的数据权限拦截器统一注入，不允许在 Controller 里手工拼接。**

本文落实为四层，缺一不可：

```
① 认证过滤器        JwtAuthFilter → UserContext{userId, projectIds, permissions}（ThreadLocal）
② 持久层注入        ProjectScopeInterceptor（gw-infra）
                    对标注 @ProjectScoped 的 Mapper 方法，自动在 SQL 追加 project_id IN (:userProjectIds)
③ 资源归属校验      DataScopeGuard（gw-app）
                    对"按主键取单条"的请求，先查资源的 project_id，再判定是否 ∈ 可见集，防止 ID 猜测（IDOR）
④ 审计留痕          跨项目访问被拒时写 audit_log（action=ACCESS_DENIED），便于安全排查
```

**明确禁止**：

- ❌ Controller 或 Service 中手写 `if (!projectIds.contains(x.getProjectId()))` 作为**唯一**防线（可以保留为业务前置校验，但拦截器必须独立生效）。
- ❌ 从请求参数接受 `projectId` 并直接用于查询过滤。`projectId` 只在**创建**资源时接受（`POST /api/intake/cases`），读取时一律由 `UserContext` 决定。
- ❌ 任何跨项目检索历史物料/风险的接口（AGENTS.md 第 12 条明令禁止）。

**可见项目范围**：由 `biz_project_member`（01 §3）决定。`LEGAL` 角色是否可见其非成员的项目的风险，02 未规定 → **待确认**（§8 T-04）；**在确认前默认"仅可见自己是成员的项目"**，不得放开。

**自动化断言**（CI 必过）：

1. 扫描全部 Mapper XML / 注解 SQL，断言业务表的查询语句均含 `project_id`，例外必须登记在白名单并写明理由；
2. 断言每个 Controller 方法都有 `@PreAuthorize`（或显式加入匿名白名单），缺一即失败——这是 02 §5 的"接口层"不被漏写的最低保障；
3. 契约测试：跨项目访问用例返回 40302 且写 `audit_log`。

## 2. 接口清单

### 2.0 分组与路径前缀

按 00 §5.1 的模块边界分组，**每个端点归属唯一模块**，通过**路径前缀 + Controller 分包**双重固定，使边界可被 Spring Security 配置与 ArchUnit 测试机械校验：

| 模块 | 路径前缀 | Controller 包 | 权限来源 |
| --- | --- | --- | --- |
| 公共（认证 / 字典 / 文件） | `/api/auth/**`、`/api/me/**`、`/api/dict/**`、`/api/files/**` | `controller.common` | 认证 |
| AI 法务助手 | `/api/assistant/**` | `controller.assistant` | 02 §4.2 |
| 接收区 | `/api/intake/**` | `controller.intake` | 02 §4.2 |
| 反馈区 | `/api/feedback/**` | `controller.feedback` | 02 §4.2 |
| 终审区 | `/api/final-review/**` | `controller.finalreview` | 02 §4.2 |

> **与 02 §5.2 示例路径的对应**：02 §5.2 用 `POST /api/risks/{riskId}/close` 作为"接口层 + 领域层双层校验"的代码示例。本文将其规范化为 `POST /api/final-review/risks/{riskId}/close`（终审区所属）。**若评审要求保留 02 的无前缀写法，则四模块统一去掉前缀（见 §8 T-21）。** 领域守卫（`RiskCase.close()`）与 DB 触发器不受路径影响，这是关键——**路径只是边界的第一道可见标记，真正的安全边界仍在领域层与数据库层**（02 §5）。

### 2.1 公共接口

| 编号 | 方法 | 路径 | 权限点 | 请求要点 | 响应要点 | 关键错误码 |
| --- | --- | --- | --- | --- | --- | --- |
| P-01 | POST | `/api/auth/login` | 匿名 | `username`、`password` | `accessToken`、`expiresIn`、`user{userId,displayName,roles[]}`、`projects[]` | 40101 / 40102 |
| P-02 | POST | `/api/auth/refresh` | 匿名（凭 `HttpOnly` Cookie） | — | 新 `accessToken` | 40103 |
| P-03 | POST | `/api/auth/logout` | 认证 | — | 无内容；`jti` 入黑名单 | 401 |

### 3.3 图片：坐标还原与 Canvas / SVG 覆盖层

#### 3.3.1 `scale_ratio` 如何把锚点坐标还原到原图显示尺寸

坐标系共三层（00 §3.3 约束 1）：

```
① 送模型规范化图片坐标系   ← locator.bbox 就在这里，基准是 image_width × image_height
        │  ÷ scale_ratio（scale_ratio = 送模型图 / 原图，见 01 §6 注释）
        ▼
② 原图像素坐标系           ← file_object_key 指向的原件，尺寸为 W0 × H0
        │  × displayRatio（displayRatio = 显示宽度 / 原图宽度）
        ▼
③ 页面显示坐标系（CSS px） ← 覆盖层与图片显示区域严格同尺寸
```

**关键推论（必须写进组件注释）**：

- `W0 = locator.image_width / locator.scale_ratio`。也就是说**原图尺寸可以从 locator 反推**，01 无需新增字段来记录原图宽高。
- 校验：前端 `<img>` 加载完成后的 `naturalWidth` / `naturalHeight` 是真实的原图尺寸。若

  ```
  |naturalWidth - locator.image_width / locator.scale_ratio| > max(2, 0.005 × naturalWidth)
  ```

  则说明**前端加载的图片与后端锚点记录的不是同一张**（例如文件被换过），此时**必须不渲染任何高亮框**，改为展示"物料版本与定位基准不一致，请核对版本"的告警（对应 00 §3.3 约束 1 与 ADR D-11 的严肃性）。

- 合式：

  ```
  displayX = bbox.x / scale_ratio × (displayW / W0)
  等价于  displayX = bbox.x × (displayW / image_width)
  ```

  **两种写法数学等价，但组件里只能选一种。** 混用（例如横向用 `image_width` 基准、纵向用 `W0` 基准）会产生被拉伸错位的高亮框，且这类 bug 在小图上肉眼难以发现。

- 若 `locator.polygon` 非空（倾斜文字），**优先用 `polygon`**，它的坐标与 `bbox` 同坐标系，同样先还原再映射。

- **`scale_ratio` 的存储精度直接影响还原精度**（01 只在 JSON 里示例 `0.58`，未定义精度）→ 见 §8 T-09；本文建议**至少保留 6 位有效小数**，并在 §3.3.2 的容差中吸收舍入误差。

参考实现：

```ts
// gw-web/src/composables/useAnchorTransform.ts
export interface BBox { x: number; y: number; w: number; h: number }

export class AnchorTransformError extends Error {
  constructor(public readonly code: 'MISSING_SCALE_RATIO' | 'BASE_MISMATCH') { super(code) }
}

/** ①→② 送模型图坐标 → 原图像素坐标 */
export function locatorToOriginal(bbox: BBox, scaleRatio: number): BBox {
  if (!Number.isFinite(scaleRatio) || scaleRatio <= 0) throw new AnchorTransformError('MISSING_SCALE_RATIO')
  return { x: bbox.x / scaleRatio, y: bbox.y / scaleRatio, w: bbox.w / scaleRatio, h: bbox.h / scaleRatio }
}

/** ②→③ 原图像素坐标 → 显示坐标 */
export function originalToDisplay(b: BBox, naturalW: number, displayW: number): BBox {
  const k = displayW / naturalW
  return { x: b.x * k, y: b.y * k, w: b.w * k, h: b.h * k }
}

/** ①→③ 一步到位；组件内部统一使用本函数，禁止各处自行换算 */
export function locatorToDisplay(bbox: BBox, scaleRatio: number, naturalW: number, displayW: number): BBox {
  return originalToDisplay(locatorToOriginal(bbox, scaleRatio), naturalW, displayW)
}

/** 基准一致性校验：不通过时调用方必须放弃渲染高亮 */
export function assertBaseMatches(
  locator: { image_width: number; scale_ratio: number },
  naturalW: number,
): boolean {
  const expected = locator.image_width / locator.scale_ratio
  return Math.abs(naturalW - expected) <= Math.max(2, 0.005 * naturalW)
}
```

| 方案 | 优点 | 代价 | 适用 |
| --- | --- | --- | --- |
| **SVG 覆盖层（推荐）** | 坐标即原图像素、无需处理 `devicePixelRatio`；`<rect>`/`<polygon>` 可直接绑定点击；样式由 CSS 控制；可访问性可加 `<title>` | 锚点数量极大（数千）时 DOM 节点偏多 | **默认方案** |
| Canvas 覆盖层 | 大量锚点时性能更好；可做像素级合成 | 必须手动乘 `devicePixelRatio`；命中测试（hit test）需自己实现；样式需命令式重绘 | 单版本锚点数超过阈值时切换（阈值见 §8 T-33） |

**推荐结构（关键技巧：`viewBox` 用原图像素尺寸，缩放平移交给外层 CSS transform）**：

```vue
<!-- components/anchor/ImageAnchorOverlay.vue -->
<template>
  <div ref="viewportEl" class="anchor-viewport" @wheel.prevent="zoomAt" @pointerdown="startPan">
    <div class="anchor-stage" :style="{ transform: `translate(${tx}px, ${ty}px) scale(${scale})` }">
      <img ref="imgEl" :src="imageSrc" draggable="false" @load="onImageLoad" />

      <!-- viewBox 直接用原图像素尺寸：<rect> 的 x/y/w/h 就是"已还原到原图"的坐标 -->
      <svg class="anchor-overlay"
           :viewBox="`0 0 ${naturalW} ${naturalH}`"
           preserveAspectRatio="none">
        <template v-for="a in rendered" :key="a.anchorId">
          <rect v-if="!a.polygon"
                :x="a.originalBox.x" :y="a.originalBox.y"
                :width="a.originalBox.w" :height="a.originalBox.h"
                :class="['anchor-box', `is-${a.refRole.toLowerCase()}`, { 'is-active': a.anchorId === activeAnchorId }]"
                @click="$emit('anchorClick', a.anchorId)" />
          <polygon v-else :points="a.polygonPoints"
                   :class="['anchor-box', `is-${a.refRole.toLowerCase()}`, { 'is-active': a.anchorId === activeAnchorId }]"
                   @click="$emit('anchorClick', a.anchorId)" />
          <title>{{ a.text }}</title>
        </template>
      </svg>
    </div>
  </div>
</template>
```

**为什么把 `transform` 放在 SVG 外面**：SVG 内部坐标恒为原图像素，缩放平移时**不需要重算任何 `<rect>`**，只需要改一个 CSS transform。若把缩放做进 `viewBox`，每次滚轮都要重建整个锚点列表，性能和代码复杂度都会变差。

**缩放**（以指针为锚点，保证指针下的原图点不动）：

```ts
function zoomAt(ev: WheelEvent) {
  const next = clamp(scale * (ev.deltaY < 0 ? 1.1 : 1 / 1.1), MIN_SCALE, MAX_SCALE)
  const rect = viewportEl.value!.getBoundingClientRect()
  const px = ev.clientX - rect.left
  const py = ev.clientY - rect.top
  tx.value = px - (px - tx.value) * (next / scale.value)
  ty.value = py - (py - ty.value) * (next / scale.value)
  scale.value = next
}
```

**平移**：`pointerdown` 记录起点 → `pointermove` 累加 `tx/ty` → `pointerup` 结束；同时提供"适应窗口"按钮把 `scale` 置为 `min(viewportW / naturalW, viewportH / naturalH)` 并居中。

**"跳到下一个风险"**：

```ts
function focusAnchor(anchorId: string) {
  const box = originalBoxOf(anchorId)                  // 已还原到原图坐标
  const cx = box.x + box.w / 2
  const cy = box.y + box.h / 2
  const vw = viewportEl.value!.clientWidth
  const vh = viewportEl.value!.clientHeight
  // 1) 目标过小则先提升到可读档位（建议三档：适应窗口 / 1.0 / 2.0）
  if (box.w * scale.value < MIN_READABLE_PX) scale.value = nextReadableScale(box, vw, vh)
  // 2) 目标居中：显示坐标 = 原图坐标 × scale + translate ⇒ translate = 视口中心 − 目标中心 × scale
  tx.value = vw / 2 - cx * scale.value
  ty.value = vh / 2 - cy * scale.value
  activeAnchorId.value = anchorId                        // 触发 is-active 高亮
}
```

- 上一/下一个风险的**顺序来自 C-12 的 `navOrder`**，前端只按数组顺序遍历，不自行排序。
- 键盘快捷键建议 `N` / `P`；**必须与输入框焦点互斥**（监听时判断 `document.activeElement` 是否为输入类元素）。
- 到达首/尾时按钮禁用并提示"已是最后一个风险"，不得循环跳回造成用户迷失。

**性能**：`rendered` 为计算属性，仅渲染当前视口内的锚点 + 当前风险的全部锚点；锚点数超过阈值时切换 Canvas 或降低渲染密度（阈值见 §8 T-33）。

**高亮样式语义**：`PRIMARY` 锚点用实线高亮；`SUPPORTING` 锚点用虚线次级高亮（`risk_anchor_ref.ref_role`，01 §4.6）。

### 3.4 视频：时间轴组件

#### 3.4.1 两条轨 + 区间渲染

视频风险的两类可定位锚点必须**分轨渲染**（00 §7.4：口播与字幕不一致本身就是风险信号，因此二者是独立锚点类型）：

| 轨 | 锚点类型 | 关键字段 | 位置 |
| --- | --- | --- | --- |
| 口播轨 | `SPEECH_SENTENCE` | `begin_ms` / `end_ms` / `speaker_id?` / `emotion?` | 上轨 |
| 字幕轨 | `SUBTITLE_LINE` | `begin_ms` / `end_ms` / `frame_ts_ms` / `bbox` | 下轨 |
| 关键帧轨（可选） | `KEY_FRAME` | `ts_ms` / `scene_id` / `visual_description` | 下轨下方的标记线 |

区间渲染公式：

```ts
const trackWidthPx = durationMs * pxPerMs                       // pxPerMs 为缩放状态
const leftPx  = (a.locator.begin_ms / durationMs) * trackWidthPx
const widthPx = ((a.locator.end_ms - a.locator.begin_ms) / durationMs) * trackWidthPx
```

- `durationMs` 来源：`AnchorBundle.video.durationMs`。**01 未定义视频时长的落库字段**，见 §8 T-11。
- 兜底：若后端未返回 `durationMs`，前端可退化为 `max(end_ms, ts_ms)` 作为时间轴长度，并**在 UI 上标注"时长未知，时间轴按最大时间点估算"**，不得让用户以为这是精确总长。

#### 3.4.2 缩放、平移与虚拟化

- 缩放：`pxPerMs` 由滑杆或"适应窗口 / 30s / 10s / 3s 一屏"预设控制；`pxPerMs = viewportW / windowMs`。
- 平移：外层横向滚动容器（`overflow-x: auto`）或自定义 `translateX`；`scrollLeft` 变化时重算可视区间。
- **虚拟化**：仅渲染 `[scrollLeft / pxPerMs, (scrollLeft + viewportW) / pxPerMs]` 区间内的锚点区间并预留 ±10% 缓冲；长时间视频（≤12 小时，00 §2.2）锚点数可达上万，**必须虚拟化，不得全量渲染**。
- 每条轨固定高度（建议 28–32px），轨内区间用圆角条；同一锚点被多个风险引用时叠加角标计数（点击展开风险列表）。

#### 3.4.3 播放头与 seek

```ts
// 播放头：rAF 驱动比 timeupdate 平滑；组件卸载时必须 cancelAnimationFrame
function loop() {
  if (videoEl.value && !videoEl.value.paused) {

```

- **点击风险默认只 seek、不自动播放**；另提供"播放该片段"按钮，从 `begin_ms` 播到 `end_ms` 后暂停。结束判定需加一帧容差（**具体容差待确认**，见 §8 T-11）。
- 播放头拖动时**必须暂停播放**（否则会出现拖动与播放竞争导致的抖动），松手后恢复到拖动前的播放状态。
- 时间轴与 `<video>` 双向联动：时间轴点击空白区域同样 seek。

#### 3.4.4 口播与字幕不一致的呈现

同一 Risk Case 同时引用 `SPEECH_SENTENCE` 与 `SUBTITLE_LINE`（`risk_anchor_ref` 两行）时：

1. 两轨对应区间**同时高亮**（同一强调色）；
2. 两区间之间画一条竖直连接线（SVG `<line>`）表达"这是同一个风险的两条证据"；
3. 详情面板并列展示两段原文，并在标题旁加"口播与字幕不一致"标记（当两段文本归一化后不相等时）；
4. **不得**把两段文本拼接成一段展示，否则会掩盖不一致这个风险本身。

#### 3.4.5 字幕 bbox 在视频画面上叠加

`SUBTITLE_LINE.locator` 的 `bbox` 基准是**抽帧图片**（`frame_width` × `frame_height`），不是视频元素尺寸。视频元素通常存在 letterbox（黑边），**必须计算实际渲染矩形**，否则框会偏移：

```ts
function subtitleOverlayRect(videoEl: HTMLVideoElement,
                             frameWidth: number, frameHeight: number, scaleRatio: number) {
  const anchorAR = frameWidth / frameHeight                 // 抽帧图宽高比
  const elAR = videoEl.clientWidth / videoEl.clientHeight   // 元素宽高比（含黑边）
  let renderW: number, renderH: number, offsetX = 0, offsetY = 0
  if (elAR > anchorAR) {                                    // 元素更宽 → 左右黑边
    renderH = videoEl.clientHeight; renderW = renderH * anchorAR
    offsetX = (videoEl.clientWidth - renderW) / 2
  } else {                                                  // 元素更高 → 上下黑边
    renderW = videoEl.clientWidth; renderH = renderW / anchorAR
    offsetY = (videoEl.clientHeight - renderH) / 2
  }
  // bbox 在"送模型帧"坐标系 → ÷ scaleRatio 回到真实帧像素 → × (renderW / frameWidth) 映射到渲染矩形
  const k = renderW / frameWidth
  return { k, offsetX, offsetY, scaleRatio }
}
```

- 与图片同理：**只选一种换算路径并写进组件**，不得一处用 `frame_width` 基准、另一处用真实帧宽基准。
- 字幕轨的区间高亮与画面上的 bbox 高亮**必须同时随播放头变化**：播放头处于 `[begin_ms, end_ms]` 时显示该字幕的 bbox，离开区间即隐藏。

### 3.5 文档：按页 / 段落 / 句子高亮

#### 3.5.1 两条渲染路径

| 文档形态 | 锚点来源 | 前端渲染 | 定位字段 |
| --- | --- | --- | --- |
| **含文本层**（常见 PDF / DOCX / PPTX） | `DOC_PARAGRAPH` / `DOC_SENTENCE` | **文本视图**：后端返回 `document.pages[].pageText` 与段落/句子 `charRange`，前端按段落渲染并高亮切片区段 | `page_no` + `para_index` + `sentence_index?` + `char_range` |
| **扫描件** | `TEXT_LINE`（OCR 文本定位，00 §7.4 文档管线） | **页图 + bbox 覆盖层**：用 `document.pages[].renderedPageRef` 取该页渲染图，叠加与图片完全相同的 SVG 方案 | `page_no` + `bbox`（坐标还原同 §3.3） |

**前端必须按 `anchorType` 分支渲染，不得假设某类文档一定产出某类锚点。** 混排文档（PPT 一页多图 + 文字，00 §7.4）会同时出现 `DOC_*` 与 `TEXT_LINE` 锚点。

#### 3.5.2 `char_range` 高亮与它的单位陷阱

```ts
function renderPage(page: PageDto, highlights: CharRange[]) {
  // 切片必须使用同一份 pageText：不得用前端从别处取的文本，否则下标立刻错位
  const text = page.pageText
  const sorted = [...highlights].sort((a, b) => a[0] - b[0])
  let cursor = 0
  const segments: Array<{ text: string; hl: boolean }> = []
  for (const [s, e] of sorted) {
    if (s > cursor) segments.push({ text: text.slice(cursor, s), hl: false })
    segments.push({ text: text.slice(s, e), hl: true })
    cursor = e
  }
  segments.push({ text: text.slice(cursor), hl: false })
  return segments
}
```

> ⚠️ **`char_range` 的计数单位在 01 中未定义**（00/01 只示例 `[180, 246]`）。Java 侧 `String.substring` 与前端 JS `String.prototype.slice` 都以 **UTF-16 code unit** 计数；若后端按 **Unicode 码点** 或**字形簇**计数，则含 emoji、生僻字（代理对）或组合字符的段落会整体错位——而且错位只在这些字符之后出现，测试用例很容易漏掉。**此项必须在联调前确认（§8 T-08）**，本文建议统一为 UTF-16 code unit 并写进接口文档。

**跳转与滚动**：`goToPage(page_no)` 切页后对该高亮片段调用 `scrollIntoView({ block: 'center', behavior: 'smooth' })`；页内只渲染当前页 ±1 页（虚拟滚动），避免数百页文档一次渲染。

**是否需要在原版式（PDF 原样排版）上高亮**：需要引入 00 未提及的 PDF 渲染依赖，**待确认**（§8 T-29）。本文默认走文本视图 + 扫描件页图两条路径，可在不引入新依赖的前提下 100% 命中并满足"法务进入风险详情后能直接跳转，不需要从头重新阅读整份材料"（AGENTS.md 第 5 条）。

**PPT 的 `para_index` 语义**（文本框顺序还是页内段落顺序）**待确认**（§8 T-08 同组）；实现前必须用一份真实 PPT 验证。

### 3.6 画面类风险：仅有 `region_hint` 时的展示

`region_hint` 是 00 §3.3 约束 4 定义的**九宫格枚举 + `FULL_FRAME`**，用于"画面类风险（无对应文字）"。

```ts
type RegionHint =
  | 'TOP_LEFT' | 'TOP_CENTER' | 'TOP_RIGHT'
  | 'MIDDLE_LEFT' | 'MIDDLE_CENTER' | 'MIDDLE_RIGHT'   // 中间三格的枚举字符串待确认（§8 T-09）
  | 'BOTTOM_LEFT' | 'BOTTOM_CENTER' | 'BOTTOM_RIGHT'
  | 'FULL_FRAME'

export function regionHintToRatio(hint: RegionHint) {
  if (hint === 'FULL_FRAME') return { left: 0, top: 0, width: 1, height: 1 }
  const row = hint.startsWith('TOP') ? 0 : hint.startsWith('MIDDLE') ? 1 : 2
  const col = hint.endsWith('LEFT') ? 0 : hint.endsWith('CENTER') ? 1 : 2
  return { left: col / 3, top: row / 3, width: 1 / 3, height: 1 / 3 }
}
```

**展示规范（强制）**：

| 项 | 要求 |
| --- | --- |
| 视觉 | **虚线描边 + 8% 不透明度填充 + 右上角角标「大致区域」**；`FULL_FRAME` 时使用整图外框虚线，不填充 |
| 文案 | 必须与 `visual_description` 并列展示（例如"画面中央为车辆正面特写，右上角有促销角标"）；任何位置描述后面追加"（大致区域）" |
| **必须标注** | 界面、报告、导出文件、tooltip 四处**都必须出现"大致区域"字样**，明确这是九宫格级别的粗定位，**不得暗示像素级精度** |
| 禁止 | 实线精确框；在格内再画子框；展示"定位精度 xx%"之类指标；在导出报告中把该格渲染成实心精确框；用 `region_hint` 反推具体坐标 |
| 与文字锚点并存 | 若同一风险既有 `TEXT_LINE` 锚点又有 `region_hint`，**以锚点为主**，`region_hint` 作为辅助提示，且仍需标注"大致区域" |
| 无任何定位信息 | `locationValid=false` 且 `region_hint` 为空时，展示"定位信息不可用"占位 + `locationInvalidReason` + `locationDesc`，**不得猜测位置**（00 §3.3 约束 3） |

**关于"人工框选"**：00 §10 风险登记册把"画面类风险降级为'大致区域' + 人工框选"列为 OCR 精度不足时的缓解手段。但**01 未定义人工框选结果的落库方式**（`evidence_anchor.source_engine` 的人工取值、人工 `anchor_id` 的分配规则、是否允许人工新增锚点均未规定）→ 见 §8 T-10。**在确认前，前端不提供写回框选坐标的功能**，只提供"复制位置描述"与"在大致区域内人工核对"的辅助。

### 4.2 路由守卫与模块准入

```ts
// gw-web/src/router/guard.ts
router.beforeEach(async (to) => {
  // ① 认证
  if (!useUserStore().isLoggedIn) return { name: 'login', query: { redirect: to.fullPath } }

  // ② 权限点（02 §5.1 的实现，权限列表由后端下发，前端不硬编码角色→权限映射）
  const required = to.meta?.perm as string | undefined

  const caseId = to.params.caseId as string | undefined

    const rule = MODULE_ENTRY_RULES[to.meta!.module as ModuleKey]

      return { name: rule.fallback(ctx) }
    }
  }
  return true
```

| 接收区 | `DRAFT`、`PARSING`、`READY_FOR_REVIEW`、`AI_REVIEWING` | 已出结果时提示"本任务已进入反馈区，请前往反馈区查看初审结果" → 跳反馈区总览 |
| 反馈区 | `FEEDBACK_PENDING`、`REMEDIATION`、`FINAL_REVIEW`、`APPROVED` | `AI_REVIEWING` 时提示"AI 初审进行中，完成后可查看" → 跳接收区任务工作台 |
| 终审区 | `REMEDIATION`、`FINAL_REVIEW`、`APPROVED`、`REJECTED` | 未进入整改时提示"该任务尚无已确认需整改的风险" → 跳反馈区风险列表 |

> ⚠️ 这只是**体验层**（02 §5 已明确"前端不是安全边界"）。真正的准入由后端状态守卫与 `risk_status_transition` 白名单保证。

### 4.3 各模块页面信息架构与关键交互

#### 4.3.1 AI 法务助手（`/assistant` + 全局抽屉）

**定位**：轻量、即时。**不出现任何 Case / Material / Version 的结构化表单与列表**（那是接收区的职责）。

信息架构（单列，从上到下）：

1. **输入区**：文本框（一句话宣传语 / 一段文案）+ 临时上传（单图 / 单短视频 / 小文件）+ **当前页面上下文条**（如"来自：风险 RK-2026-0001-03"）。
2. **回答区**：结论概览 → 风险点列表（每条：风险类型 / 风险等级 / 置信度 / 原因 / 依据引用 / 修改建议 / 推荐表达 / 所需证明材料 / **不确定性说明**）→ 依据来源（可折叠，展示知识库条目、生效期、是否历史规则）。
3. **动作条**：`解释这条风险`、`生成沟通话术`、`转为正式审核任务`。
4. **免责声明常驻**：AI 结论不构成法律意见，正式物料必须经法务批准。

关键交互：

- **携带页面上下文**：在风险详情页点击助手入口时，自动把 `pageContext{module,caseId,materialId,riskId,versionId}` 带入 A-02，助手回答时可直接引用该风险的原文与依据。
- **`转为正式审核任务`**：点击后**不直接创建 Case**，而是调用 A-07 拿到草稿，跳转 `/intake/cases/new?prefill=<token>`，由用户在接收区页面上**确认后才创建**（00 §5.2）。页面必须有明确文案："以下内容将带入接收区，创建后才会成为正式审核任务。"
- **批量能力不存在**：界面不提供"选中多条一起分析"、不提供"批量审核"按钮（AGENTS.md 第 3 条、02 §4.2 注）。

#### 4.3.2 接收区任务工作台（`/intake/cases/:caseId`）

**约束**（00 §5.1、AGENTS.md 第 4、13 条）：突出任务信息、上传进度、解析结果、审核要求；**不提前展示风险结论**。

信息架构：

- **顶部任务信息卡**：`caseNo`、名称、项目、提交人、负责人、截止时间、`status`（状态标签按 §6.1 编码）、物料计数。
- **Tab 1 物料与解析**：
  - 上传区（拖拽 + 选择；显示分片进度、暂停/继续/取消、失败分片重试、"该文件已存在，已复用版本"提示）；
  - 物料表：名称 / 类型 / 大小 / `parse_status` / 错误原因 / 上传人 / 上传时间；失败行提供"重新上传"与"重试解析"（`case.parse_retry`）；
  - 解析进度：按物料展示 `parse_job.progress` 与阶段（OCR / ASR / 帧 / 文档），**必须展示真实进度**，不得用假进度条动画（AGENTS.md 第 14 条）。
  - **本 Tab 禁止出现任何风险数量、风险等级、通过与否的信息**。
- **Tab 2 审核要求**：
  - 关注点多选（绝对化宣传 / 安全承诺 / 无依据数据 / 竞品表达 / 价格宣传 / 免责声明 / 可能误导的描述）+ 补充说明；
  - 模板选择：选择模板后**仅作为草稿内容**，页面必须提示"模板内容需确认后才生效"；未确认时 `requirementConfirmedAt` 为空、状态区显示"审核要求未确认"；
  - `确认审核要求` 按钮（`case.requirement_confirm`）→ 二次确认提示"确认后本次任务以当前要求为准"。
- **底部动作区**：`开始 AI 初审`（`case.start_initial_review`）。不满足前置条件时按钮禁用并**明确说明缺什么**（"仍有 2 个物料解析失败，请先重传" / "审核要求尚未确认"）。

#### 4.3.3 反馈区初审总览（`/feedback/cases/:caseId/overview`）

信息架构：

1. **三分类看板**（来自 C-01，口径由后端视图固化，01 §8）：
   - 物料级三张卡片：`初审通过`（INITIAL_PASS，蓝灰色 + **"不等于法务最终批准"**）、`待人工判断`（PENDING_HUMAN，橙）、`风险未通过`（RISK_FAIL，红）；
   - 卡片数字旁标注口径："单位：物料"；
   - **解析失败单独一块**，显示 `parseFailedCount` 并注明"不计入通过率分母"；
   - 通过率展示：`初审通过率 = 初审通过物料数 ÷ 参与初审物料数`，并在下方原样展示后端下发的 `rateBasisNote` 三句口径文案；
   - 风险项统计：`highRiskItems` / `mediumRiskItems` / `lowRiskItems`，**明确标注"单位：风险项，与物料口径不可互换"**。
2. **物料三分类表**：物料 / 类型 / 分类 / 风险数 / 高风险数 / 当前版本 / 操作（查看风险）。
3. **风险类型分布**：按 `risk_type` 的中文名字（绝对化宣传、产品性能缺乏证明、安全承诺、竞品比较依据不足、价格宣传、免责声明缺失、可能误导消费者的描述、其他）展示计数与占比。
4. **入口**：`查看全部风险`（带当前筛选跳 C-02）、`查看 AI 初审报告`。

#### 4.3.4 反馈区风险列表与详情（`/feedback/cases/:caseId/risks`）

- **左侧/顶部筛选栏**：物料、物料分类（三分类）、`riskLevel`、`riskType`、`status`、自由关键词（仅搜 `risk_text` 与 `location_desc`，**后端不建全文索引**，01 §9）、只看高风险、只看定位有效。
- **风险表**：风险编号 / 物料 / 风险原文（截断，hover 显示全文）/ 等级标签 / 状态标签 / **置信度数字** / 位置描述 / 更新时间 / 操作。等级、状态、置信度三列**必须使用三套视觉编码**（§6.1）。
- **行点击 → 风险详情抽屉**（右侧，宽 720–900px；深链走 `/feedback/risks/:riskId`）：
  - 顶部：`riskNo`、等级、状态、置信度、是否阻断性（`blocked`）；
  - **锚点定位查看器**（§5 的 `AnchorLocatorViewer`）：图片 / 视频 / 文档三种形态，含"跳到下一个风险"与"上一个"；
  - 风险原文与画面描述、`locationDesc`、`regionHint`（按 §3.6 标注"大致区域"）；
  - 风险原因、相关企业规则与法律依据（含生效期与"历史规则"标记）、证据来源、`unsupportedClaims`；
  - AI 修改建议、推荐表达、所需证明材料；
  - 模型与版本信息（`modelId` / `pipelineVersion` / `promptVersion` / `rulesetVersion`）折叠在"审计信息"内；
  - **底部操作条**：`确认风险`（`risk.confirm`）、`标记误判`（`risk.false_positive`，弹出必填理由）、`要求补充材料`（`risk.request_evidence`）、`转入整改`（`risk.to_remediation`）、`生成沟通话术`（调用 A-05）。
  - 操作按钮全部用 `v-perm` 控制；`risk.confirm` 等四个动作仅 `LEGAL` 可见（02 §4.3）。

#### 4.3.5 反馈区 AI 初审报告（`/feedback/cases/:caseId/report`）

- 左：Markdown 渲染预览（含报告头：生成时间、数据版本、生成者、三个版本号）；
- 右：目录 / 锚点导航（点击条目滚动到对应风险并高亮）；
- 顶部：`复制`、`导出`（`report.export`，导出留痕）；
- 报告内每条风险的"沟通话术"提供独立复制按钮（每条风险一段，见 §5 `CommunicationScriptPanel`）；
- **报告页固定顶部提示**："本报告为 AI 初审结果，其中 AI 结论不代表法务已批准。"
- 报告中的通过率必须与 C-01 完全一致（同一视图口径），**不得由前端计算**。

#### 4.3.6 终审区 Risk Case 列表（`/final-review/cases/:caseId/risks`）

- 筛选：`status`、`riskLevel`、物料、责任方（落点见 §8 T-06）、是否已复审、复审结论。
- 列表列：风险编号 / 物料 / 当前版本 / 首次发现版本 / 等级 / 状态 / 最近复审时间与 `reviewScope` / 更新时间 / 操作。
- 顶部聚合条：待整改数、待复审数、待法务终审数、已关闭数、**未关闭阻断性风险数**（该数字直接决定能否批准，必须常驻可见）。
- **本页不得出现"重新初审整批物料"的入口**（00 §5.1）。若用户需要看本批全貌，提供"查看 AI 初审报告"跳转到反馈区。

#### 4.3.7 终审区风险闭环详情（`/final-review/risks/:riskId`）

信息架构（自上而下）：

1. **风险头部**：`riskNo`、等级、状态、当前版本、首次发现版本（只读）、是否阻断性。
2. **版本时间线**（`VersionTimeline`）：V1 → V2 → V3，每节点显示版本号、上传人、上传时间、`uploadReason`、文件哈希（可复制）、`parse_status`；当前版本高亮；节点可点选作为 Diff 的任一侧。
3. **Version Diff 查看器**（`VersionDiffViewer`）：左选 base、右选 target；按物料类型切换差异呈现（文字差异 / 画面与版式差异 / 视频字幕与镜头差异 / 文档页面与段落差异）；点击差异项 → **在锚点定位查看器中跳转到对应位置**（`linkedRiskIds` 关联风险）。
4. **AI 复审结果**（`RereviewPanel`）：三问结论（原风险是否解决 / 是否仍有剩余风险 / 是否产生新增风险）+ 证据 + 置信度 + `reviewScope` + 模型与版本号；`newRisks` 非空时必须提示"将新建关联 Risk Case，不改变原风险含义"，并提供"新建关联风险"动作。
5. **法务终审区**：意见输入 + `采纳复审结论` / `不认可复审结论（退回整改）`。
6. **签名与关闭区**：签名上下文预览（`signaturePreviewHash` 由服务端给出）→ `法务签名`（`risk.sign`）→ `关闭风险`（`risk.close`，必填关闭原因）。两个动作各有独立二次确认（§6.3）。**界面文案必须写清"关闭后该风险视为已解决并留痕，历史记录不可删除"。**
7. **审计链**（`ReviewRecordTimeline`）：全部 `review_record`，区分 AI / 人工主体（`actor_type`），显示动作、原状态→新状态、意见、关联版本。

#### 4.3.8 终审区物料批准（`/final-review/materials/:materialId/approval`）

- 展示：物料信息、待批准版本（版本号 + 哈希 + 上传信息）、该物料全部 Risk Case 的闭环状态清单（阻断性 / 非阻断性分组）、未关闭阻断性风险清单。
- `标记为最终批准版本` 按钮：`material.approve`；**存在未关闭阻断性风险时按钮禁用**，并显示阻塞原因（后端 D-11 `blockingRiskOpen=true`）。
- 二次确认框（§6.3）必须展示：版本号、`fileSha256`、已关闭风险数、未关闭非阻断风险数。
- 已批准后：展示批准人、批准时间、签名哈希，并提供 `撤销批准`（`material.revoke_approval`，必填撤销原因）。

#### 4.3.9 追溯视图（`/final-review/cases/:caseId/traceability`）

- 三栏：物料与版本（含 `material_approval` 及其哈希校验结果）→ 该版本产生的 Risk Case → 该风险的 Review Record。
- 提供"反查"入口：从批准记录出发能一路点到当时的准确版本与哈希（AGENTS.md 第 9 条）；
- **只读**，不提供任何编辑动作。

```ts
interface AnchorLocatorViewerProps {
  bundle: AnchorBundle            // §3.2
  activeAnchorId?: string
  navOrder: number                // 来自 C-12，前端不得自行推导
  navTotal: number

// emits
// 'anchorClick' (anchorId: string)
// 'prev' | 'next'                 // 由父组件按 navOrder 取上/下一条
// 'baseMismatch'                  // 触发 §3.3.1 的基准不一致告警
```

**内部必须遵守的三条纪律**：

1. 坐标换算**只走 `useAnchorTransform`**，组件内不得出现第二份换算逻辑；
2. `locationValid=false` 时**不渲染任何高亮**，只渲染 `LocationValidityNotice`；
3. `region_hint` 分支只能由 `RegionHintBox` 渲染，确保"大致区域"角标不会在某个分支被漏掉。

### 6.3 高风险动作的二次确认规范

依据 02 §6（文案要求与影响范围）与 AGENTS.md 第 13 条。**统一由 `HighRiskActionConfirm` 组件实现**，禁止各页面自行写确认框。

**确认框结构（固定五段）**：

```
① 标题          「<动作名>」                例：标记为最终批准版本
② 影响范围区     以描述列表展示后端返回的影响字段（下表）
③ 不可逆说明     一句话说明该动作的后果与留痕性质
④ 原因输入       需要原因的动作：必填，最少 5 个字，展示字数计数
⑤ 操作区         主按钮文案 = 具体动作（绝不为"确定"）；危险色；取消按钮为次要样式
```

**四种高风险动作的具体模板**：

| 动作 | 标题 | 必须展示的影响范围字段（来源端点） | 原因输入 | 主按钮文案 |
| --- | --- | --- | --- | --- |
| **标记最终批准版本** | 标记为最终批准版本 | `versionLabel`、`fileSha256`、`closedRiskCount`、`openNonBlockingRiskCount`、`involvedMaterials[]`（D-11） | 选填意见 | `确认批准 <版本号> 为最终版本` |
| **关闭风险** | 关闭风险 | 原风险原文、新版本内容、AI 复审结论、签名人（D-08/D-10 + `signature-context`） | **必填**关闭原因 | `确认关闭该风险` |
| **驳回任务** | 驳回本批任务 | 将被退回的风险数、涉及的物料数（D-14） | **必填**驳回原因 | `确认驳回，退回整改` |
| **撤销批准** | 撤销批准 | 受影响的物料与版本、批准人与批准时间、已下线的对外版本提示（D-13） | **必填**撤销原因 | `确认撤销批准` |
| **标记误判** | 标记为误判 | 风险原文、将保留的留痕说明（C-07） | **必填**误判理由（DB 约束 `ck_rr_false_positive_opinion` 强制） | `确认标记误判（留痕）` |

**交互硬要求**：

1. **主按钮文案必须写明动作**，禁止"确定 / 提交 / OK"。
2. 危险动作必须使用危险色（`#C0392B`）；`标记误判` 用中性色（它不是破坏性动作，但需留痕）。
3. **不得提供"不再提示"选项**。二次确认是流程要求的一部分，不是可关闭的打扰。
4. 影响范围数据**由后端预取**（C-05 / D-08 / D-11 等 `impact` 端点），**前端不得自行计算风险数量**。
5. **二次确认只是体验措施，不是安全措施**：后端必须独立校验前置条件（02 §6 明确）。因此确认后若返回 43201 `BLOCKING_RISK_OPEN` 等拒绝码，前端必须刷新按钮态并如实展示原因，**不得重试**。
6. 确认过程中禁止重复提交（按钮进入 loading 并禁用，配合 `Idempotency-Key`）。

### 6.4 通用视觉约束

1. **同一概念同名同色**：状态、等级、类型的中文名与颜色全部来自 `/api/dict`（P-06）与 §6.1 色表，禁止页面内自定义。
2. **AI 与人工必须可区分**：`review_record` 的 `actor_type` 在时间线中必须有明确视觉区分（AI 用灰底 + 模型名；人工用头像 + 姓名）。AI 产出的文本块统一加"AI 生成"浅色标签。
3. **加载与空态**：所有异步区块使用骨架屏，禁止使用全屏遮罩阻塞全部页面；空态文案区分"没有数据"与"定位信息不可用"。
4. **长文本**：`risk_text` 在列表中截断并 hover 展示全文；详情中不截断。Markdown 报告必须限制单行宽度（建议 80–100 字符）以保证可读性。
5. **可访问性**：颜色不是唯一信息载体——等级标签带文字"高/中/低"，状态标签带全称，置信度带数字。这正是 §6.1 要求形状差异的另一个原因。
6. **敏感信息**：前端**不得**把物料原文写入浏览器持久化存储（localStorage / IndexedDB）或上报到任何前端监控（AGENTS.md 第 12 条）。

### 7.2 状态管理（Pinia）分模块设计

**分工原则**：

| 类型 | 存放位置 | 理由 |
| --- | --- | --- |
| 身份、权限点、可见项目 | `user` store（持久化到内存，不落 localStorage） | 全局唯一，02 §5.1 要求由后端下发 |
| 字典（状态/等级/类型中文名） | `dict` store（会话内缓存，登录后拉一次） | 全部页面同源，避免各处硬编码 |
| 查询条件（筛选/分页/排序） | 对应模块 store + 路由 query 双向同步 | 支持分享与刷新还原 |
| 服务端实体详情（Case/Risk/Version） | **组件内 `ref` + `api` 直调**，不进 store | 详情是短生命周期数据，进 store 会带来失效与内存问题 |
| 长任务（上传队列、解析轮询） | `intake` store（需要在路由切换后存活） | 用户切页面时上传与轮询不能中断 |
| 当前选中风险 / 版本 / Diff 入参 | `feedback` / `finalReview` store | 跨组件（列表 ↔ 抽屉 ↔ 查看器）共享 |

**规则**：

1. store **只存 UI 状态与查询参数**，不存"业务判断结果"（例如不得在 store 里缓存"能否批准"的布尔值——必须来自后端 `impact` 端点）。
2. 模块 store **不得互相 import**（`feedback` 不得依赖 `finalReview` 的 state）；跨模块共享走 `user` / `dict`。
3. 切换项目（`user.currentProjectId` 变化）时，`intake` / `feedback` / `finalReview` 三个 store 必须 `$reset()`，避免跨项目的陈旧数据泄漏到界面。
4. 上传任务与轮询在 `beforeunload` 时给出提示，但**不阻止**离开（避免误以为数据会丢——服务端已接收的分片是持久的）。

### 7.3 API 层封装

```ts
// gw-web/src/api/http.ts
const BASE_URL = '/api'

export interface ApiError {
  code: number
  message: string
  traceId: string
  httpStatus: number
  details?: Array<{ field: string; reason: string }>
}

export async function request<T>(path: string, init: RequestInit & {
  idempotencyKey?: string
  traceId?: string
} = {}): Promise<T> {
  const headers = new Headers(init.headers)
  headers.set('Accept', 'application/json')
  if (init.body && !(init.body instanceof Blob)) headers.set('Content-Type', 'application/json')
  if (useUserStore().accessToken) headers.set('Authorization', `Bearer ${useUserStore().accessToken}`)
  if (init.idempotencyKey) headers.set('Idempotency-Key', init.idempotencyKey)
  if (init.traceId) headers.set('X-Trace-Id', init.traceId)

  const res = await fetch(`${BASE_URL}${path}`, { ...init, headers, credentials: 'include' })
  const traceId = res.headers.get('X-Trace-Id') ?? ''
  if (res.status === 204) return undefined as T

  const payload = res.headers.get('Content-Type')?.includes('application/json') ? await res.json() : null
  if (!res.ok || (payload && payload.code !== 0)) {
    throw normalizeError(res.status, payload, traceId)
  }
  return payload.data as T
}
```

**错误归一化与分级处理**：

| 情况 | 处理 |
| --- | --- |
| `400xx` 参数校验 | 表单字段标红（用 `details[].field`）+ 顶部 `ElMessage.error(message)`；不弹对话框 |
| `401` | 清空 `user` store → 跳登录并带 `redirect`；**不展示技术信息** |
| `40301` 缺少权限点 | 内联 403 提示 + **静默刷新 `GET /api/me/permissions`**（02 §5.1 的权限漂移场景：管理员刚调整过权限，前端列表过期）；不自动重试原请求 |
| `40302` 跨项目 | 提示"无权访问该项目的数据"并跳回列表；**记录 traceId 便于安全排查** |
| `409` 乐观锁冲突 | 提示"数据已被他人更新"，**自动重新拉取详情**并把冲突字段高亮；不做静默覆盖重试 |
| `422` 状态机拒绝（`43001` 等） | 展示 `message` + 当前实际状态（重新拉取一次详情）；刷新按钮可用态 |
| `43102` `REVIEW_SCOPE_FULL_REJECTED` | **这是编程错误而非用户错误**：前端不应传 FULL。展示通用错误 + 上报前端日志（但**不得上报物料原文**） |
| `429` / `5xxxx` | 统一提示"服务暂时不可用，请稍后重试"，**附可复制的 traceId**；允许用户手动重试 |
| 网络中断 | 提示"网络连接失败"；上传与轮询按各自策略恢复 |

**统一错误出口**：所有错误必须经过同一个 `handleApiError(err)`，保证用户看到的提示格式一致、traceId 一定可见。

**`Idempotency-Key` 生成规则**（`utils/idempotency.ts`）：

```ts
// 同一"用户意图"内复用一个 key；新的点击（新意图）生成新 key
export function newIntentKey(): string { return crypto.randomUUID() }
```

- 一次点击触发的多步调用（如"签名 → 关闭"）复用同一个 key；
- 提交失败后用户点"重试"**复用**原 key（这才是幂等的意义）；
- 用户修改表单后再次提交**必须生成新 key**。

### 7.5 大文件上传与断点续传

**流程**（对应 B-06 / B-07 / B-08）：

```
① 计算文件 SHA-256（Web Worker 分块计算，避免阻塞主线程；大文件显示"正在校验文件"）
② POST /api/intake/upload-sessions
     → { uploadId, partSize, uploadedParts[], existingVersionId? }
     └ existingVersionId 非空 ⇒ 秒传命中 uk_version_sha：直接提示"该文件已存在，已复用版本 Vn"，跳过 ③④
③ 对未上传的分片并发 PUT /api/intake/upload-sessions/{uploadId}/parts/{partNo}（幂等）
④ POST /api/intake/upload-sessions/{uploadId}/complete  { parts[], fileSha256, uploadReason? }
     → { materialId, versionId, versionNo, versionLabel, parseJobId }
⑤ 进入解析轮询（B-10）
```

**断点续传**：

- **会话恢复的幂等键用 `fileSha256` 而非 `uploadId`**：因为 `material_version` 的唯一键是 `(material_id, file_sha256)`（01 §4.3），同一文件天然对应同一结果。刷新页面后重新发起 B-06，服务端若已有同哈希的未完成会话则返回其 `uploadedParts`，实现续传；若已有完成版本则返回 `existingVersionId` 实现秒传。
- 上传会话应有过期时间（TTL **待确认**，§8 T-17）；过期后 40402，前端自动重新创建会话并从 0 开始（已上传分片由服务端丢弃）。

**并发与重试**：

- 分片并发数建议 3（**待确认**，需与后端连接池、Nginx 配置对齐）；
- 分片失败**只重试该分片**，指数退避（1s / 2s / 4s / 8s），最多 4 次；连续失败则暂停该文件并提示；
- 全部完成前**不得**发送 `complete`；`complete` 返回 45004（哈希不一致）时必须**重新计算并重传**，不得忽略。

**进度与用户感知**：

- 上传进度 = 已确认成功分片的字节数 ÷ 总字节数（**不使用 XHR 瞬时速率值作为最终进度**）；
- 合并、哈希校验、解析是**三个独立阶段**，必须分别展示，避免"进度条 100% 却还在等"的困惑；
- 解析阶段的进度来自 B-10 的 `parse_job.progress`，**必须是真实值**（AGENTS.md 第 14 条：向用户展示真实进度）；
- 支持暂停 / 继续 / 取消；取消调用 B-09（**仅对未完成的会话**）。

**安全**：

- 分片接口必须校验 `uploadId` 属于当前用户与当前项目（§1.9）；
- **前端不得传入或持有 `file_object_key`**；
- **推荐后端代理分片**（前端 → `gw-api` → MinIO），理由：统一鉴权与项目隔离、避免预签名 URL 泄露、便于审计与限流。前端直传（预签名 URL）可减少后端带宽压力，但需确认（§8 T-17）。

**轮询策略**（`usePolling`）：

- 解析进度：间隔 2s，连续 5 次无变化则退避到 5s、10s、30s（上限 30s）；`document.hidden` 时暂停，`visibilitychange` 恢复时立即拉一次；
- 全部物料的 `parse_status` 进入终态（`SUCCEEDED` / `FAILED` / `PARTIAL`）后停止轮询并刷新 Case 状态；
- 推送机制（轮询 / SSE / WebSocket）**待确认**（§8 T-15）；本文以轮询为兜底实现。
